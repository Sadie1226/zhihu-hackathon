## 一、三项：改了什么、怎么证

### 第 1 项 · 独立 `recordExchange` 的来源读取与写入不在同一事务

**A 的复现**：另一连接在读来源时把 Find 从 `fixture` 改成 `cache`，更新成功；实际来源是 `cache`，而 exchange payload 仍保存 `fixture`，调用未被拒绝。

**根因**：`recordExchange` 是独立导出的写入入口，自身不开事务。它做三次独立碰库 —— `getFindSource`（读来源）、`currentSeq`（算趟次）、`insertExchange`（写行）—— 三个间隔各是一个窗口。11-20 只把 `gift.send` 整段包进事务，等于只堵了「礼物」那一条路；直接调 `recordExchange` 仍可穿过。这是当时判断失误：**写入边界的保护不能设在调用方**。

**改法**：`recordExchange` 整段进 `store.transaction`，实际逻辑收进不导出的 `recordExchangeInTx`。顺序、错误码、返回值一律不变（`MISSING_IDEMPOTENCY_KEY` 仍在 `validate` 之后，保持原优先级）。

**证据**（`tx.concurrency.test.ts`）：

| 用例 | 修前 | 修后 |
| --- | --- | --- |
| C1 双连接：读到来源后另一连接改 `find.source_mode` | ❌ 攻击成功（`false !== true`） | ✅ UPDATE 被拦（`database is locked`），库里仍 `fixture`，payload 也是 `fixture` |
| C2 双连接：事务提交后另一连接能改 | ✅ | ✅ 证明拦的是「中途」，不是把库锁死 |
| C2b 嵌套调用：外层事务里调 `recordExchange`，来源查询照样在事务内 | ✅ | ✅ 外层已持写锁，攻击仍被拦，两条写都落下 |
| C2c 嵌套调用：内层来源不符而失败 | ✅ | ✅ 只撤内层，外层已写的那条留 |

嵌套一致性是这次的关键：`recordExchange` 自带事务后，`meet()` 和 C8 的「外层验权 + 内层写入」都会走到两层。`store.transaction` 支持嵌套（内层 `SAVEPOINT`），所以不会撞 `cannot start a transaction within a transaction`。

### 第 2 项 · `meet` 事务前的状态 / gate 检查有时序窗口

**A 的复现**：首次检查后、事务前从另一连接把 trip 改成 `done`，仍写入 1 条 exchange 和 1 次 met。

**根因**：`meet()` 在 `store.transaction()` 之前读 `hasDog` / `getTrip`（存在、归属、`running`）/ `isBlocked` / `gate`。这四类读决定「写不写」，但它们读到的是「事务开始前那一刻」的事实。

**改法**：三关抽成 `assertTripOpen` / `assertNotBlocked` / `runGate`，**外层与事务内调用同一段代码**（两处各写一份，改了外层忘改内层，重验就成了摆设）：

- 外层保留 —— 错误码优先级不变（`DOG_NOT_FOUND` 仍在 `NO_EXCHANGE_IN_MEET` 之前），能拒的尽早拒，不进事务；
- 事务内重验 —— `BEGIN IMMEDIATE` 已拿写锁，此时再读就是「写入那一刻的事实」，另一连接在事务期间改不了这些行。

`gate` 因此会被调用两次，**约定它必须无副作用**（纯判断、不计数、不打点、不改状态）。这条写进了 `runGate` 的注释，也写进了下面给 C8 的分工说明。

**证据**：

| 用例 | 修前 | 修后 |
| --- | --- | --- |
| C3 检查后、事务前把 trip 改 `done` | ❌ `Missing expected exception` —— 攻击成功且照样写 | ✅ 拒 `TRIP_NOT_OPEN`，exchange 0 行、relation 0 行 |
| C4 检查后、事务前把这一对拉黑 | ❌ 同上 | ✅ 拒 `BLOCKED_RELATION`，只留攻击插的那条拉黑记录 |
| C5 `gate` 调用次数 | ❌ 1 次（只在外层） | ✅ 2 次（外层 + 事务内） |

### 第 3 项 · 成功嵌套事务缺少 `RELEASE SAVEPOINT`

**A 的观察**：实测 `BEGIN IMMEDIATE → SAVEPOINT sp_d4_1 → COMMIT`，只有失败路径有 `RELEASE`。

**根因**：`transaction` 内层分支 `try { return fn() }` 成功路径直接返回，`finally` 只做 `depth -= 1`。savepoint 一直挂到外层 `COMMIT`（`COMMIT` 会清理，所以 A 说「本轮未证明数据丢失」—— 但语义已经变形：内层「结束」了而栈上还挂着它，且名字每次都是 `sp_d4_1`，同名会栈式叠加）。

**改法**：
1. 成功路径补 `RELEASE`；
2. savepoint 名用单调计数器 `sp_d4_<n>`，同一事务里多次内层各得其所；
3. 顺带修了一处同类问题：最外层原来只在 `fn` 抛错时 `ROLLBACK`，**`COMMIT` 本身失败**（如 `SQLITE_BUSY`）时事务仍开着。现在用 `committed` 标记，`COMMIT` 失败也回滚，且只对「本来就没有事务」这一种错误宽恕（其它错误照旧上抛）。

**证据**（判定手法：`RELEASE` 一个已释放的 savepoint 会报 `no such savepoint`；**不报错就说明它还挂着**）：

| 用例 | 修前 | 修后 |
| --- | --- | --- |
| C6 内层成功后立即释放 | ❌ `sp_d4_1` 仍可 RELEASE | ✅ 报 `no such savepoint` |
| C7 连着两次内层成功 | ❌ 两次同名 `sp_d4_1`，且都未释放 | ✅ 分别 `sp_d4_1` / `sp_d4_2`，各自释放，两条写都留 |
| C8 三层嵌套成功 | ❌ 三个都未释放 | ✅ 三个都释放，数据留 |
| C9 内层失败被外层接住 | ✅（原有正确行为） | ✅ 只撤内层，`sp_d4_1` 不留 |
| C10 外层失败 → 全撤 + 失败后复用 store | ✅ | ✅ `depth` 复位，后续事务正常 |

## 五、边界与分工（回应请求末段）

| 事项 | 现状 |
| --- | --- |
| 可信寄件身份 | d 无 session 概念，`SocialStore` 也没有也不该有。C8 负责 session → `fromDog` 的写权；d 侧验的是库层事实：`hasDog`、`isSample`（种子狗不得替主人说话）、`trip.dogId === dogId` 且 `running`、`isBlocked`、来源归属 `find ⋈ trip`。其中 trip 归属是结构性证明（从库读，不由调用方声明）。若 C 要求加 `assertWritable(sessionId, dogId)` 进 store 接口，按 C 的定义实现，不自造 |
| 显式 `null` 冲突即拒 | 11-20 已改：只有 `undefined` 算未声明；`null` 是明确声明，与库不符拒 `PROVENANCE_MISMATCH`。本次未改动 |
| 不从库派生 payload | payload 里的 `sourceMode` 由库证明后写入（`fixture`/`cache`/`live`/`null` 取自 `find.source_mode`），**接口形状与行为不变**，未暗改契约。要改成「读侧从库派生、payload 不存」是新契约，需走 C 的流程 |
| 种子狗未来出发 / 投递 | 属 C/D/E 接续。d 侧不预置 trip、不伪造主人回复、不提前写 `delivered_at`。发送时的趟次式子仍是「收件狗当前 seq + 1」 |
| `gate` 无副作用 | 新增约束：会被调用两次（外层快速拒 + 事务内重验）。C8 若在 gate 里做计数或打点，必须挪出去 |
| 来源的「状态」指什么 | `recordExchange` 核三样：find 的 id 存在、归属（`find ⋈ trip` 的 `dog_id` = 寄件狗）、`source_mode` 与声明一致。**不核 find 所属 trip 的 `status`** —— 把一趟已结束的出行里捡到的东西送人，是合法语义（礼物可以引用旧发现）。只有「相遇」要求自己的 trip 是 `running`（`assertTripOpen`），因为相遇必须发生在路上。若 A 要的是「来源必须还在进行中的出行里」，那是新规则，需明确 |
