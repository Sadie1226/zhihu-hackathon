```ts
expect('收尾：exchange 6 行', n('exchange'), 6)
```

## 二、初始化的清理责任

**原写法**：

```ts
const RUN_DIR = fs.mkdtempSync(path.join(os.tmpdir(), 'd4-e2e-'))
const DBFILE = path.join(RUN_DIR, 'd4_e2e.db')
const db = new DatabaseSync(DBFILE)              // ← 在 try 之外
db.exec('PRAGMA foreign_keys = ON')
db.exec(fs.readFileSync(…'contracts/schema.sql'…))  // ← 在 try 之外
…
try { main() } finally { db.close(); fs.rmSync(RUN_DIR, …) }
```

目录已经建出来了，但「谁负责删」是从 `main()` 开始算的。`new DatabaseSync` 或读 schema
任何一步抛错（schema 被改坏、磁盘满、权限不够），进程直接退出，**目录留在机器上**。

**现写法**：把初始化一起纳入 try，清理改成能应付「句柄还没建出来」。

```ts
const RUN_DIR = fs.mkdtempSync(path.join(os.tmpdir(), 'd4-e2e-'))
const DBFILE = path.join(RUN_DIR, 'd4_e2e.db')

let db: DatabaseSync | null = null

try {
  db = new DatabaseSync(DBFILE)
  db.exec('PRAGMA foreign_keys = ON')
  db.exec(fs.readFileSync(path.join(ROOT, 'contracts/schema.sql'), 'utf8'))
  main(db)
} finally {
  try {
    db?.close()          // 建库就失败时没有句柄可关，但目录仍然要删
  } catch {}
  try {
    fs.rmSync(RUN_DIR, { recursive: true, force: true })
  } catch {}
}
```

`main()` 改成收一个 `db` 参数，内部代码一行没动（参数遮蔽同名变量）。

## 三、证据：初始化失败前后

造法：把 schema 路径换成不存在的文件（`contracts/__no_such_schema.sql`），其余完全不变，
跑一次，数 `%TEMP%` 下 `d4-e2e-*` 的目录个数。

```bash
COUNT='const fs=require("fs"),os=require("os");console.log(fs.readdirSync(os.tmpdir()).filter(f=>f.startsWith("d4-e2e-")).length)'
```

| | 起点 | 跑之前 | 跑之后 | 退出码 |
| --- | --- | --- | --- | --- |
| **旧版**（`origin/main` 的 `scripts/e2e-d4.ts`） | 0 | 0 | **1（残留）** | 非 0 |
| **修复版**（本分支） | 0 | 0 | **0** | **1** |

两次都在同一台机器、同一时刻跑，只差初始化有没有在 try 里。旧版这次的残留目录已删除，
目录数回到 0 之后才跑的修复版。

失败输出（两版一致，都是 `ENOENT` 指向那个不存在的 schema）：

```text
Error: ENOENT: no such file or directory, open '…\contracts\__no_such_schema.sql'
```

区别只在跑完之后：旧版留下一个空的 `d4-e2e-xxxxxx`，修复版什么都不留。

## 四、三种退出码都还在

| 情形 | 结果 | 退出码 |
| --- | --- | --- |
| 正常跑 | `全部断言通过` | **0** |
| 断言失败（把「exchange 6 行」的期望改成 7） | `✗ 收尾：exchange 6 行：期望 7，实际 6` + `1 项断言未通过` | **1** |
| 初始化失败（schema 读不到） | `ENOENT`，无残留目录 | **1** |

顺带说明一个顺序问题：`finally` 里是**先 `db?.close()` 再 `rmSync`**，而且两个都各自
`try/catch`。如果在 `close` 抛错时直接往下走，`rmSync` 还是能执行；反过来把 `rmSync` 放在
一个会抛错的位置，就会出现「断言失败」被「清目录失败」顶替、退出码来源说不清的情况 ——
这个坑在 `tx.concurrency.test.ts` 里踩过一次。
