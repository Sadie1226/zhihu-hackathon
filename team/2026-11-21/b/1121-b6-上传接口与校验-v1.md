## 3.1 接口形状（事项 3）

```
POST /api/uploads/photo
入：multipart/form-data，单文件字段 file
出：{ "url": "/uploads/s_<完整session哈希>_<随机串>.<jpg|png|webp>", "bytes": 123456, "mime": "image/webp", "width": 1600, "height": 1200 }
错：
  413 太大（> 5MB）或服务端读头发现边长 > 1600px
  415 格式不支持（看文件头，只认 jpg/jpeg/png/webp）
  401 无有效会话
```
**落位**：代码在 `app/(b)/api/uploads/photo/route.ts`（route group 不进 URL，对外路径就是 `/api/uploads/photo`）。`app/api/` 归 C，不碰。

**存储与读取（11-19 修订，部署关键）**：

| 项 | 值 | 依据 |
| --- | --- | --- |
| 存储根目录 | `uploadDir()` = `process.env.UPLOAD_DIR \|\| './data/uploads'` | `app/(b)/b6-photo.ts` 唯一来源；写入/校验/读取三处共用 |
| 本地 | `./data/uploads`，`data/` 已在 `.gitignore:25` | 不进仓库 |
| 部署 | `UPLOAD_DIR=/var/lib/zhihu-hackathon/uploads` | service `ReadWritePaths` 已含该路径、`StateDirectory` 已建好父目录；写进 `/etc/zhihu-hackathon.env`，**service 文件不用改** |
| 对外 URL | `GET /uploads/<name>`，由 `app/(b)/uploads/[name]/route.ts` 读 `uploadDir()` 返回 | 存 `data/` 不在 `public/`，Next 不会自动 serve，必须有读取端，否则图片 404 |

> 为什么不用 `public/uploads/`：`1118-a:109,176` 原建议走 public，但那是本地 dev 视角。部署用 `ProtectSystem=strict` + `ReadWritePaths` 只放行状态目录，`next start` 代码目录只读，线上写 `public/` 会 EACCES。存 `data/uploads/` 既本地可写、又匹配部署的只读代码约定。

## 3.2 校验规则表（事项 3）——每行都能回答"不满足会怎样"

| 检查项 | 规则 | 不满足 |
| --- | --- | --- |
| 大小 | ≤5MB；上传前前端 canvas 压图，**服务端仍按字节数复核** | 413，界面就地提示，**已输入文字不丢** |
| 格式 | 只认 jpg/jpeg/png/webp，**服务端读文件头不看扩展名**，真实格式决定扩展名与 MIME | 415。`a.exe` 改名 `a.jpg` → 拒；JPEG/PNG 原字节不再伪装成 `.webp` |
| 尺寸 | 前端压到最长边 ≤1600px，**服务端读文件头复核边长**（不只信前端）；原始输入 ≤4000px 防解压炸弹 | 超限 413；不压就超 5MB 的图拒收 |
| 归属 | 必须带有效会话；文件名含**完整 64 位 session 哈希**，与当前会话哈希一致 | 无会话 401；哈希不符 401/冲突 |
| 文件名 | 服务端随机串，不含原文件名；扩展名取真实格式 | 出现 `IMG_*.jpg` → 拒；跨主人哈希 → 拒 |

> "看文件头不看扩展名"必须写进规则：只查扩展名等于没查，`a.exe` 改名 `a.jpg` 就绕过去了（A 在 `1118-a-给B:122` 实测这条能插进库）。11-19 收紧：前端压图只是省流量，服务端 `inspectPhoto()` 自己解 jpeg/png/webp 头拿格式与边长，不能只信前端（A 在 `1119-a-给B:29` 明确要求）。

### 我自己定的三个数（事项 3.3）

1. **上限 5MB**——沿用 b3 原值，A 也建议别改。
2. **压图：压，但服务端复核。** 手机原图常 3–8MB，前端 canvas 压到最长边 1600px 通常只剩几百 KB；代价是画质下降，演示场景接受。**只在浏览器端压**（`canvas` + `toBlob('image/webp', 0.8)`），服务端不重压（package.json 只有 next/react，无 sharp，不动共享依赖文件），但服务端**读文件头复核格式与边长**，不满足 413/415。
3. **文件名随机串**：`s_<完整session哈希>_<crypto.randomUUID().replace(/-/g,'').slice(0,16)>.<真实扩展名>`；session 哈希由 `sessionPhotoOwner()` 取 `sha256(sessionId)` 完整 64 位，不再用前 8 位。不用原文件名——`IMG_20261118_我家的猫.jpg` 会泄漏本地信息。

## 3.3 "怎么判断是不是本人传的"（事项 4 要求写清）

**这是 A 路径的全部安全边界**，三段判断，全过才把 `photoUrl` 写进 `reply.photo_url`：

```
① 形状：/^\/uploads\/s_([0-9a-f]{64})_([0-9a-f]{16})\.(jpg|png|webp)$/
   —— 只收本接口产出的路径形状。/assets/photos/x.jpg 之类一律不进 ②③，直接拒。
② 身份：正则捕获的 64 位哈希 === sessionPhotoOwner(readSessionId(request))
   —— 即 sha256 完整比对，别人 session 的地址拒；8 位前缀不再当完整凭证。
③ 存在：uploadDir() 下该文件名真实存在（fs.stat）
   —— 挡住"自己编一个格式对但不存在的地址"。写入/校验同一目录来源，不漂移。
```

代码在 `app/(b)/api/replies/route.ts` 与 `app/(b)/b6-photo.ts`，三段分别对应 `parseOwnPhotoUrl` / `sessionPhotoOwner` 哈希比对 / `uploadedFileExists`；**不改契约、不找 C**——`contracts/api.md:182` 标题就是"回应（b 实现，唯一）"。

## 事项 5：失败三态的界面表现（随 11-21）

b3 已有的"照片失败就地提示体积/格式上限、**已输入文字不丢**"保留；补齐三条：

| 状态 | 界面表现 |
| --- | --- |
| 上传中 | 不清空输入框、按钮禁用、显示可取消的进度（AbortController） |
| 上传失败 | 就地"图没传上去"＋具体原因（413 体积 / 415 格式）；**已输入文字不丢** |
| 回应提交失败 | 与上传失败**提示语不同**——"回应没发出去"；保留文字与已传图 url，可重试 |
| 断网 | 图可以先不发，**纯文字也能提交**（P0 第 6 条"能回文字或照片"的兜底） |

> 两次失败是不同动作：图没传上去 ≠ 回应没发出去，提示语必须能分辨。
> 位置：按你的选项写进本文件（事项 3 同一份），不另开 `1121-b6-回应失败三态-v1.md`。

## 事项 5 附：回应接口其余契约约束（别漏）

`POST /api/replies` 除 photoUrl 收口外，仍守 `contracts/api.md:182-200`：

- 恰好一个来源（exchangeId / invitationId 二选一），恰好一种以上内容（text / photoUrl）；
- 空回应 → CONFLICT；文字上限 200 字（trim 后 1–200，`schema.sql:426`）；
- 两条来源路径**都有唯一索引**，重复提交第二个返回 CONFLICT、前端当成功（幂等）——只做一条路径就是漏；
- 成功出 `{ reply: Reply }`，`kind` 由数据库推导，不写 'none'。
