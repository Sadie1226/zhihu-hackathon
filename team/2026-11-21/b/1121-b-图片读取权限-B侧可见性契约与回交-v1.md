## 二、B 的判断：能独立做什么、不能做什么

**当前实现事实**（远端 main 与 b5b6 同一份，`uploads/[name]/route.ts` blob `1c1e381a7d`）：

- 上传 POST `api/uploads/photo` 校验 `dog.session_id` 归属，只保护写入。
- 文件名 `s_<完整 session 哈希 64 位>_<16 位随机>.<ext>`，不可猜测。
- 读取 GET 只校验文件名形状 + 文件存在，凭链接可读——这是 **capability URL**。

**为什么 B 不单方在 GET 里加身份/场景鉴权**：

1. 直接踩红线：按 session 限「仅上传本人可读」，会让合法收件人（被邀请看图的狗/主人、exchange 收件方）看不到图。A 原文明确禁止。
2. 身份底座不可信：判定请求者是谁依赖 C 的稳定 owner，`STATUS.md:240` 明记「稳定 owner、过期/服务端撤销未完成，旧开发 cookie 重放仍 200」。用不可信身份做鉴权等于造假。
3. 场景归属是公共契约：`reply.photo_url` 反查 invitation/exchange、谁是合法收件方，牵涉 `exchange.to_dog` 投递语义与公共 schema，属 A/B/C 对齐范围，B 单方定会与 C 冲突。

**B 能独立、正确、可测落地的**：把 capability 可见性规则、文件名形状、缓存边界固化为契约级纯函数，并把读取路由的动作统一到该契约（消除三处正则漂移），配可复验测试；把「可读对象 / 过期 / 撤销 / 缓存边界」作为待对齐接口交出，供 A 接线。
