# d10 · 串味回归：快照里能不能读出主人说过的话

> 2026-11-28 · d
> 分支 `d10-leak-regression-1128`
> 基线 **`6bf08df`**（= 当前 main，产品代码零改动）
> 新增 `tests/d10-snapshot-leak.test.mjs` + `tests/helpers/text-leak-scan.mjs`

## 一、为什么今天做这个

规划表第 7 节 ⑤ 写着「11-28 回归时专门测『A 的私聊文本是否出现在 B 的设备上』」，红线第 2 条是串味（**最严重**）。

已有的覆盖只到一半：d7 有一层「原话只许命中 `exchange.payload`」的全库扫描，但它跑在**没有快照被写入**的场景里。而 `snapshot` 才是「别人看到你的狗」时读的那一份，串味在这里最贵。

所以补的是：**快照真的被派生并落库之后**，私密文本还在不在里面。

## 二、测了什么

三类私密文本走三条不同的路，分开测：

| # | 文本 | 该待的地方 | 谁写 |
| --- | --- | --- | --- |
| 1 | 主人通过狗捎出去的原话 | `exchange.payload.message` | d |
| 2 | 主人给礼物起的名字 | `exchange.payload.giftName` | d |
| 3 | 狗回家对主人说的话 | `message.text` | b（d 只读） |

链路是真链路，不是手搓快照：四条 `create → start → trip_event → finish`，快照由 `bindDepartureSnapshot()` 在出发事务内派生。

## 三、结果

```
ok 1 - d10 串味：原话 / 礼物名 / 狗对主人说的话，都不进快照
```

跑在 main `6bf08df` 上，1/1 绿。断言分三层：

1. **逐行**：`snapshot` 表所有版本行的 `recent_trips` / `waiting_for` 都不含三个标记串
2. **整库**：三个标记串各自只命中它该待的那一列（`exchange.payload` ×2、`message.text` ×1）
3. **反向对照**：公开事件文案 `墙根有一小片新绿。` 必须能在 `event.text` **和** `snapshot.*` 里找到 —— 证明不是「什么都被清空才显得干净」

前提自检也留着：`snaps.length >= 4`、甲最新快照的 `recent_trips` 非空、两边 `waiting_for` 各是预期模板。否则后面的断言就是空跑。

## 四、两条负验证（证明这两道断言真的锁住了东西）

**这次不是修 bug —— 代码本来就是对的。所以负验证的形式是「把实现改坏，看门禁红不红」。**

| # | 改坏哪里 | 结果 |
| --- | --- | --- |
| 1 | `waitingFor` 改成 `WAITING_TEMPLATE[kind] + payload.message` | **红**：`+ '等一句回话zz主-人-原-话-1128zz'` vs 期望 `'等一句回话'` |
| 2 | `summaries.push(summary)` 改成推 `message.text` | **红**：第 101 行逐行检查抓到 |

还原后 `lib/social/snapshot-derive.ts` 的 blob 回到 `7915e7ef…`（与原值逐字节相同），`git diff` 为空，重跑 1/1 绿。

**负验证时撞到一个意外发现，值得单说：** 第一次改坏是把整个 `payload` JSON 塞进 `waiting_for`，结果红在 `validateSnapshot：TOO_LONG @ /waitingFor —— 74 字，超过 40` —— 也就是说 `snapshot.ts` 的 40 字上限本来就是第二道防线，粗暴串味会被它先挡住。所以第二次改成「不超长但带内容」才验到我自己的断言。**两道防线都必须有，不能只靠长度。**

## 五、边界（别把这条读大了）

- **这是防回归门禁，不是修复**。`deriveSnapshot()` 的 `WAITING_TEMPLATE` 与「摘要只用 `event.text`」本来就没问题；这条测试只是把它锁住，防止以后有人为了「更生动」把礼物名拼进去。
- **快照目前没有对外读取入口**。`grep -rn "snapshot" app/` 零命中；唯一读它的是 `lib/trips/executor.ts` 的投递前校验。也就是说现在的串味风险是「设计上必须防」，而不是「已经漏了」—— 等 C/A 接「别人看到你的狗」那个接口时，这道门禁已经在那儿了。
- 没走真 HTTP，进程内真库。跨设备视角的 HTTP 取证是 d9 的地界（三边六字段），本项不重复。
- 只覆盖三类文本。照片（`exchange.payload.imagePath`）与城市/称呼没有专门造标记串测 —— 它们在 d1 口径里本就不进 payload，若要锁需另开一条。
- 扫的是「整库所有文本列」，包括将来新增的表。但 `LIKE %…%` 对超长文本、二进制列无效；文本列按 `CHAR/CLOB/TEXT` 类型筛。

## 六、顺手发现一处口径不一致（建议 C 改注释，不改结构）

`contracts/schema.sql:212` 对 `waiting_for` 的注释是：

> 当前在等什么，人话一句，**如「等一条围巾的回音」**。可为空。

而代码口径（`snapshot-derive.ts` 的 `WAITING_TEMPLATE`）是 `'等一份礼物的回音'` —— **不出现礼物名**。

注释里的例子正好教人把礼物名拼进去，而这正是串味的入口。建议把例子改成「等一份礼物的回音」。**不动表结构、不动触发器**，纯注释。
