## 真实入口

- `createTripExecutor(db, { now?, random?, provider?, cache?, conditions?, ownerObservations?, seedObservations? })`，返回 `owner(input)`、`seed(input)`。两者分别支持 `{action:'create'}` 和 `{action:'resume',tripId,retryDiscovery?}`。owner 使用经过服务端验证的原 Request 和目标 dog。seed 是受信内部调用，按 dog 和原 intent 核确定 Trip ID，数据库检查 sample/无主人。观察和条件由受信材料适配器提供。
- 主人走 C4 create 或 get，再 start 原 pending。C4 写锁内通过接缝重新核同一会话和目标狗，C7 写锁内复用授权。种子复用 C8 确定 ID 与 C4 生命周期。G3 Snapshot/start/seq 投递仍由原事务完成。
- 先返回终态，核隔离及回执，再核新执行所需的出发绑定。C7 在 start 提交后运行，若事件已冻结直接复用；选择写锁内再查回执以防竞态。材料、provider、cache 等待均在事务外。C6 独立写锁检查 running、授权、证据和最新屏蔽。种子候选只用 Scene 和固定 occurrence，零主人搜索及缓存。
- `complete` 可含零条当前可见成员，`confirmation.replayed` 区分首存与回放，`resumeAt:'return'` 交后续阶段。 `partial` 携合法可见材料，`unconfirmed` 代表重开仅知没有完整回执，需明确重试才继续。 `search-error` 保留标准错误及 AUTH 告警。 `pending` 保留原 Trip 和 start 冲突。 `held/unbound/terminal` 停止写入，授权与完整性故障显式失败。

## 边界和下一阶段

主人新建使用现有随机 Trip ID。若 create 已提交但响应丢失，调用方需先经授权核对在途 Trip，再按已知 ID 恢复。当前活跃冲突只防同时间重复，无法证明后来是同一次创建，C11 须用实际调度意图收口。对 running 无完整回执的显式恢复可以再次调用搜索。按 Trip 的首次完成唯一性由 C6 回执保证，外部调用数受并发时序影响。

旧 v7 隔离在任何材料、C7 或 C5/C9 前停止，原历史 GET 继续使用。如旧 Trip 尚无出发绑定，不补录历史。Phase 1 不引入调度或拨盘。 `now` 只用于现行业务钟和专项测试，Cookie 始终走鉴权的真实墙钟。未来 C11 不能把拨盘后的时刻传给 C9 的 TTL 或提供方时钟，混合时钟需单独验证。

Phase 2 依照 A 已定的 done + Message 原子提交。B 候选的 `createMessageStore.write` 仍独占一个 BEGIN，且按终态写多条，C4 finish 仍为 `message:null`。需要 B 提供可在已有写锁内同步调用的校验、插入与按精确 ID 读回能力。建议双方审查基于 owner/dog/Trip/intent 的命名隔离确定 Message 主键，核冲突和历史隔离，优先使用现有主键。C 建立自动 finish 的锁内复验和状态组合，先读回原确认再决定是否生成，使用同一回执投影再次核当前可见材料并保护引用。模型步骤在锁外。B6 waiting-first 仅复用仍在 waiting 的同源邀请，原子范围、容量分支和跨状态幂等按实际后续裁定接入。Phase 3 基于 Phase 1/2 复用现有上海自然日、配额和六小时间隔，另验调度及时间隔离。
