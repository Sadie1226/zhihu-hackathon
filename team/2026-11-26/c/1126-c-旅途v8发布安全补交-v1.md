## 旧历史切换

v8 候选迁移在 `user_version=7` 及原迁移事务内核验来源，创建 `trip_discovery_legacy_hold`，一次性捕获 running 且已有 Find 的 Trip。真实 v7 没有持久回执，带回执表但含回执行的 v7 标号库会被明确拒绝，以免误判不明来源。记录只含 `trip_id,dog_id,find_count,captured_at,source_version`。fresh 没有隔离行。失败时表、清单与版本一起回滚。

`finds.ts` 先核授权/运行状态，再在搜索读事务、所有主人写入的 `BEGIN IMMEDIATE` 和种子批写事务读取隔离记录。现有历史 GET 仍走原查询。新 v8 partial 从未进入迁移集合，重开后同 Trip 可正常补齐。先前已在候选库以未带隔离表的 v8 运行过的数据库，属于不同配对。应由 A 依据该库的版本/对象和停写来源另定处置，不能靠再次打开运行 v8 或按当前 Find 数量追溯补造隔离集合。

隔离用例由真实 v7 基线建表、使用 C4/C8 启动旅途，停写后才预检及迁移。隔离清单为 `legacy-owner-dog` 的 running Trip（2 Find）和 `legacy-seed` 的 running Trip（1 Find）。无 Find 的 running 或有 Find 的 done 均不在清单。一次实际比较验证迁移清单与预检逐 Trip ID/dog ID/Find 数量相等，隔离时间为迁移时刻，来源版本为 7。迁移前后 Trip/Find 逐行相同。历史 GET 200 返回原两条，回执为零，provider/cache read/cache write 均为 0。普通写入、已持有 proof 的 `writeVerified`、`commitSearchSelection`、批写和 seed 批写均拒绝，写锁正常回滚。新 partial 测试保持空清单，重开后补齐为三条 Find 与唯一回执。

### 停写操作

1. 停止所有旧服务实例和作业，排空已有应用读写事务。不要仅依赖迁移锁代替停写。记录原运行完整应用 SHA。
2. 对真实 v7 停写库运行 `node scripts/check-v7-discovery-cutover.mjs --db <v7数据库>`。JSON 含三列清单、总数及稳定 `inventory_sha256`。退出 0 为空，2 为 A 审查清单，1 为版本不符、无效输入或读失败。脚本的数据库连接只读。
3. 核对应用 SHA 与停写点一致备份，保留清单供 A 审查。非空时需 A 对具体历史行裁定。升级会保留旧 Trip 和 Find，由 A 决定是否按既有业务结束并另开，不执行自动收尾。

## 一致备份与回退

```text
node scripts/backup-sqlite-consistent.mjs --source <源库> --snapshot <新目录/backup.sqlite> --out-dir <新目录> --app-sha <当前运行完整SHA> --writes-stopped
```

`--writes-stopped` 是执行人确认所有实例已停止并排空事务。CLI 另取零等待的 `BEGIN IMMEDIATE` 检测并排除活动写者，不能替代运维核实全部实例和只读事务。独立只读连接执行 `VACUUM INTO`，不手工复制、删除 WAL/SHM。再独立只读打开快照检查 integrity 与 FK，校验回执 envelope/hash 并统计成员类型，计算规范化 schema hash 和快照 SHA-256。输出目录必须新建。manifest 用同目录相对 `backup_path`。 `app_sha` 来自停写部署记录，由执行人核对，其兼容性还需由对应 reader 演练。 `receipt_capabilities` 描述库中实际观察到的成员。

配对演练使用精确 `a6ad71d…` reader。首个 live 批次快照的 WAL 非空，快照仍含其中已提交 Find 与回执。配对数据库按原 v8 schema 去除隔离表后采集。之后在演练库新增 cache 批次，旧 reader 以 `DISCOVERY_RECEIPT_INVALID` 拒绝。停写点快照由原 reader 重放成功，逐行匹配备份时回执与 Find，provider 零调用。恢复丢失备份后第二趟 Trip、其快照和 cache 回执/Find，第一趟回到备份时的 running 状态。正式回退须先再次停写，另存当前一致快照、盘点差异、由 A 裁定处置，再恢复同点数据库和匹配应用。覆盖备份后的业务写入有损。

## 初始化竞态

- 在旧组合原始测试上连续跑 30 次，本机 30 次通过。增加分阶段诊断及进程屏障后，缺目录和文件 85 轮有 5 轮失败，预建目录 65 轮有 1 轮失败，预建空文件 65 轮有 1 轮失败。7 次均为 SQLite `errcode=5`、`errstr=database is locked`，发生在 schema/COMMIT 之后的 WAL 切换。典型子进程 PID 45992（缺文件）、30796（预建空文件）。本地诊断逐轮保留隔离路径、PID、错误及 directory/open/BEGIN/schema/COMMIT/WAL/close 事件。未观察到目录、首次建文件、schema 或独立关闭失败。WAL 切换是本机已定位的故障。
- 原测试使用首个 rejection 即结束的 `Promise.all`，失败时夹具可能在其他进程使用该库期间清理。测试现等待全部子进程 close 后才清理，加入同步释放屏障。A 的确切 `SQLITE_READONLY` 本机未复现，该错误与旧清理竞态的因果关系尚未证实。请 A 在原机器复测同一 SHA。
- 生产 bootstrap 只对 WAL 切换中的 `SQLITE_BUSY` 重试，使用单调时钟消耗原 5 秒预算，恢复原 busy_timeout。保留 schema 校验在 WAL 切换前，其他错误原样失败。复测 35 轮，共 70 个四子进程场景（缺目录/文件、预建空文件），每轮通过并检查 WAL、schema 版本、integrity/FK。
