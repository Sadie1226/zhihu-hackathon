## 2. 真实聊天：契约取用、接口形状与恢复语义

### 2.1 路由（app/(b)/api/chat/route.ts）
- **校验**：无查询参数；拒绝 `sec-fetch-site: cross-site` 与不匹配 `Origin`（只信请求自身 URL/Host，不信转发头）；`Content-Type: application/json`（可带 charset）；正文 UTF-8 限 16 KiB；严格 JSON 对象且三键不重复；再调用正式 `parseChatRequest`（dogId/clientMessageId/text 的形状、字符与长度口径全部由契约决定）。
- **身份**：仅 Cookie，经 `resolveAuthContext(request, db)` 取稳定 owner；事务外先解析、事务内回调重验（会话在事务开始时失效即 forbidden）。
- **事务**：`BEGIN IMMEDIATE` → 重验会话 → `dog.id=dogId AND dog.owner_id=ownerId AND dog.is_sample=0` → 按 `(owner_id, client_message_id)` 查重 → 同值回放 / 异值 409 / 首存 INSERT → `COMMIT` 后才回 200。
- **错误**：只返回契约三码——404 `NOT_FOUND`（会话无效/狗不存在/种子狗/跨主人，统一口径，先于幂等）、409 `CONFLICT`（校验失败或同键异值，不可重试）、503 `NETWORK`（写入/读取/表未就位等真实故障，可重试）；统一 `Cache-Control: no-store` + `Vary: Cookie`；不回显正文、token、owner、SQL、堆栈。
- **成功体**：严格四键 `id/dogId/text/createdAt`；`createdAt` 服务端 `Date.toISOString()`；不输出 `replyText`（生成另需契约，四句示例不得当服务端回复落库）。

### 2.2 幂等与失败（与本轮实测一致）
| 场景 | 服务端 | 客户端（send.ts + transport.ts） |
| --- | --- | --- |
| 首存 | 事务内 INSERT + COMMIT 后 200 四键 | 200 且回执 dogId/text 与本项一致才 `confirmed`，记服务端 id |
| 同键同值重试 | 回读首存，200 原四键，`createdAt` 不刷新 | 确认到同一服务端 id，`dedupeItems` 去重，不产生第二条 |
| 同键改文本/换狗 | 409 终态，库不变 | `conflict` 终态，不重试、不换键重发 |
| 未授权/种子狗/失效会话 | 404，先于幂等查询 | `forbidden` 终态 |
| 表未就位 / DB 故障 | 503 可重试，绝不 200 | `uncertain`，保留原键原文原 dog 重试（上限 5 次、退避 0/0.5/1/2/5s） |
| 已提交但响应丢失 | 数据库已有首存，重试回读同一行 | 结果不明按 `uncertain` → 原键重试 → 确认同一 id |
| 并发同键 | 两连接仅一条提交（唯一约束 + 防覆盖触发器） | 两侧确认同一服务端 id |
| 取消/卸载 | — | 在途项转 `uncertain` 保键，重开同键重试 |

## 3. B5 归来 Message：running 暂存 vs done 原子提交（请 A 裁定，B 不擅自选）

现状：`b5-share.ts` 的 `createMessageStore().write()` 由 C 的 `finish` 调用，写入时校验 `trip.status ∈ {done, failed, timeout}`（非终态不写），写事务内校验 trip 归属、同一 trip、多条历史按 `created_at DESC, id DESC` 取最新。**即当前实现是「done 终态才写、与 finish 同事务边界」**。以下两种方案供 A 裁定：

| 方案 | 恢复行为 | 代价 |
| --- | --- | --- |
| **A. 维持 done 终态原子提交**（当前实现） | 生成失败/进程重启时 trip 仍 running，Message 一行不写；重启后由 C 的 `finish` 重入重试写入，幂等键保证不重复。用户看不到半句话。 | 若生成在 finish 之后回调、或 finish 未重入，则这条归来话丢失且无自动补偿，需要 C 保证 finish 重试或 B 增加补写入口。running 阶段无法预览。 |
| **B. 允许 running 阶段暂存**（草稿态） | 生成先在 running 写入草稿行，终态再提交/发布；重启后按 tripId 读回草稿续写，可预览。 | `message` 需增状态列与「草稿不可读」过滤（改契约/迁移，归 C）；B5 读取、C 归来读取、E 展示都要区分草稿/正式；失败/取消/撤销需清理草稿，一致性面变大；与现有「多条历史取最新」口径冲突，须重定排序与可见性。 |

B 的建议（供裁定参考，不执行）：在无 C 迁移与读取方改造前，方案 A 代价更小、语义更干净；若选 B，需 C 先给出状态列与迁移、A 协调 D/E 读侧，B 再改写入与可见性。

## 4. B5/B6 事实分表与 B6 waiting 语义（不混表）

- **三类事实分表**（与契约第十一项一致）：B5 归来 `Message` 绑定 `tripId`、独立 `message` 表；`chat_message` 是主人与狗的私有聊天，只存首次确认的四键；对邀请/交换的一次回应写入既有 `reply`。聊天写入不得创建 wish、不得写 snapshot / find / message / exchange / reply / trip_event，不得复制给其他狗。三者互不混表、互不冒名。
- **B6 同源回读优先**：`create()` 现在先查 `based_on_find_id` 对应的 waiting 邀请并回读首存，再判 `v_invitation_state` 的 waiting 容量（上限 3）；容量满只对**新意图**返回真实已存在的 `wentAlone` tripId，不新造 trip、不改旧邀请状态。相同 Trip/intent、相同 Find 重试结果不随容量变化；生成失败/进程重启后重入仍回读既有 waiting 邀请或既有 trip，不重复新增。
- **唯一约束需求（交 C，B 不自建）**：`chat_message` 的 `UNIQUE(owner_id, client_message_id)` 与 `FOREIGN KEY(dog_id, owner_id)`、`id` 主键已由 C 的 v9/009 提供，B 路由只消费；B6 的同源去重靠既有 invitation + `v_invitation_state` 查询，无需新增列。若后续要为 B5 `message` 增加 trip 幂等键或草稿状态列，由 C 统一出契约与迁移，B 不另建第二套约束。

## 5. B8 状态（本轮不接线）

- 口径：v10 独立扩展 `wish.source='reply'` + 唯一 `origin_reply_id`，一个回应最多形成一份心愿；C 建议来源优先级 `owner > reply > collection`，reply 是否含 invitation/exchange 两类、是否只消费下一趟一次，尚待 A 确认。
