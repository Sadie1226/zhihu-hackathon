## 四、边界（比结论重要）

1. **"回"这一步走的是服务层，不是 HTTP。** 本分支没有 `POST /api/exchanges/:id/reply`（B 的回应 HTTP 未落地）。脚本里 `--reply-transport=service` 是默认且唯一选项，证据 JSON 里 `replyTransport.httpRoute` 明确写着"本分支尚无"。
   → **B 的回应路由合并后，把该开关打开重跑一次即可，其余步骤不用改。**
2. **本地登录走开发身份，不是生产。** `developmentEnabled()` 要求 `NODE_ENV !== 'production'` 且库名是 `a5-development*.sqlite`。这是护栏，不是坑 —— 换库名骗开关才是错。所以这份证据证明的是「本地真实服务 + 真实 HTTP 链路」，**不宣称生产知乎身份已验证**。
3. **单机两会话 ≠ 双设备。** 这里两个 owner 跑在同一个进程里。明天 d9 那两台真机器要验的是：会话互不串、网络重试、同一条消息在两台机器上显示一致。这份证据是它的**前置**，不是替代。
4. **"原话不泄漏"用的是整库文本扫描，不是派生快照。** d5 的 `snapshot-derive.ts` 在另一条分支、未合入本分支，所以这里换成更硬的做法：全库搜。等 G3 合 main 后可以再加一条"派生快照里不含原话"。

## 五、两个实测发现（都不是我改坏的，但要说）

### 1. 哈希陷阱：只对 `app.sqlite` 求 sha256 会盖假章

同一份脚本跑两轮，两次 `app.sqlite` 的 sha256 **一模一样**（`03ba4ba1…`），初始还以为是巧合。真相是：数据全在 `-wal` 里，主库文件一直停在"只有 schema"的状态。**只对主文件求哈希，等于对着一份不含任何消息的空壳盖章。**

这跟 A 11/25 那句更正完全对上：*空 WAL 可以忽略，非空 WAL 不能忽略*。

处理：先试 `wal_checkpoint(TRUNCATE)`，在 Windows 上撞 `SQLITE_IOERR_DELETE_NOENT`（进程刚被杀，`-shm` 还映射着，删不掉）；改用 `VACUUM INTO` 出一致快照再求哈希 —— 快照自包含、不含 WAL，哈希才有唯一含义。本轮：现场库 266240 + wal 0，快照 262144，`sha256 a0d161fc…`。且 `VACUUM INTO` 在进程刚退出时会随机 `SQLITE_IOERR`，脚本里加了 8 次重试。

### 2. `tests/db.test.mjs` 里「并行初始化同一新库」约 1/3 概率红（预存在）

`202 of 202` 里唯一一条常红：

```
not ok 28 - parallel processes can initialize the same new database safely
Error: attempt to write a readonly database   ← lib/db/bootstrap.ts:42
```

单跑该文件 3 次：1 红、2 绿、1 红。**与本分支无关**（我只新增了未跟踪文件），是既有竞态。这条用例本来就是为这个场景写的，它红说明保护没兜住。建议 C 看一眼（C 的库，我不动）。它对 d9 影响有限（两台机器各一个库文件），但会让 CI 随机红。

顺带一条环境噪音：本机沙箱的"安全删除"护栏会让测试清理临时目录时抛 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`（单轮 >50 文件），表现为**62 条 hook 失败**。用 `NODE_OPTIONS= node --test ...` 绕开后是 201/202。这不是代码问题，别照着它改代码。
