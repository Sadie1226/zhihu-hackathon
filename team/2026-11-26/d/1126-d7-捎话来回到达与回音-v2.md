## 四、边界（比结论重要）

1. **本地登录走开发身份，不是生产。** `developmentEnabled()` 要求 `NODE_ENV !== 'production'` 且库名是 `a5-development*.sqlite`。这是护栏不是坑 —— 换库名骗开关才是错。所以这份证据证明的是「本地真实服务 + 真实 HTTP 链路」，**不宣称生产知乎身份已验证**。
2. **单机两会话 ≠ 双设备。** 两个 owner 跑在同一个进程里。明天 d9 要验的是：会话互不串、网络重试、同一条消息在两台机器上显示一致。这份证据是它的**前置**，不是替代。
3. **「原话不泄漏」用的是整库文本扫描，不是派生快照。** d5 的 `snapshot-derive.ts` 不在本分支；等 G3 合 main 后可以再补一条「派生快照里不含原话」。
4. **回应路由是 B 的 `(b)` 路由组里的，我没改它。** 若 B 后续调整其 body 形状或状态码，证据脚本要跟着改，届时重跑即可。

## 五、两个实测发现（都不是我改坏的，但要说）

### 1. 哈希陷阱：只对 `app.sqlite` 求 sha256 会盖假章

同一脚本跑两轮，两次主文件 sha256 一模一样。真相：数据全在 `-wal` 里，主库停在「只有 schema」。**只对主文件求哈希，等于对一份不含任何消息的空壳盖章。** 与 A 11/25 那句更正完全对上：*空 WAL 可忽略，非空 WAL 不能忽略*。

处理：先试 `wal_checkpoint(TRUNCATE)`，Windows 上撞 `SQLITE_IOERR_DELETE_NOENT`（进程刚被杀，`-shm` 还映射着）；改用 `VACUUM INTO` 出一致快照再求哈希 —— 自包含、不含 WAL，哈希才有唯一含义。本轮：现场库 266240 + wal 0，快照 262144，`sha256 d6f4b362…`。`VACUUM INTO` 在进程刚退出时会随机 `SQLITE_IOERR`，脚本里加了 8 次重试。

### 2. `tests/db.test.mjs` 的「并行初始化同一新库」约 1/3 概率红（预存在）

```
not ok 28 - parallel processes can initialize the same new database safely
Error: attempt to write a readonly database   ← lib/db/bootstrap.ts:42
```

单跑 3 次：红/绿/红。**与本分支无关**（我只新增未跟踪文件），是既有竞态。这条用例本就是为这个场景写的，它红说明保护没兜住。建议 C 看一眼。对 d9 影响有限（两台机器各一个库），但会让 CI 随机红。

环境噪音另记一条：本机沙箱的「安全删除」护栏会让测试清理临时目录时抛 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`（单轮 >50 文件），表现为 62 条假红；`NODE_OPTIONS= node --test ...` 绕开后是 201/202。不是代码问题。
