## 稳定身份与恢复

可信服务器调用 `createTripScheduler(db).owner({request,dogId,intentId,retryDiscovery?})` 或内部 `seed({dogId,intentId,retryDiscovery?})`。事件生产方保留原始稳定键。主人 Trip ID 使用 `trip_owner_schedule_v1_` 加 `SHA256(JSON.stringify([ownerId,dogId,intentId]))`，种子沿用 `seedIntentTripId`。主人的真实会话和非种子归属、既有 ID、活动 Trip、资格、插入在同一 C4 写事务内按此顺序确认。两进程竞争依赖 SQLite 写锁和 Trip 主键。已提交但丢响应时，同键冷恢复回读原 Trip；已完成的旧意图同样回读。异常占用拒绝；普通 C4 创建保留随机 ID 并保留调度前缀。

C10 按稳定 Trip ID 恢复。pending 进入原 start，running 复用 Snapshot、occurrence 和既有回执；held 返回隔离，partial 由显式重试补齐。已确认但零可见成员仍保持 complete。终态无新搜索；精确自动归来确认可回读，不生成第二条。实际回归覆盖两 OS 进程、create 后退出、终态恢复、C4 资格和外键。竞争中的外部调用允许重复，最终持久事实依赖原有事务和约束。

实际 start 在 C4 写锁中重新检查上海自然日、每日两次实际出发、六小时间隔，并重新选取有效 Wish。主人优先于 collection，排除屏蔽与撤销记录。Wish 绑定和实际 trigger 同事务落库，历史不改绑，私人原文不进入出发 Snapshot。投递仍由下一次有效 start 的 seq 驱动。

## 时钟与失败

- 正常调度使用真实时钟；会话有效期独立于旅途传入的时钟。实测 C9 首次缓存采用在恰好 24 小时时拒绝，保留初选与提交两次 TTL 校验；已确认回执冷重放继续成立。
- `createTravelDial()` 仅面向显式隔离库，用同事件键与绝对 UTC 时间重放。它推进 C4 时间，可触发正常 Snapshot 和 seq 投递，禁用搜索 provider、缓存以及归来生成。v8 回执只有一个 `completed_at`，回放还校验 `fetchedAt`。未来旅途时间与在线缓存混用需要 A 裁定如何单独保存真实采用时刻及兼容旧 reader。
- Phase 2 归来在事务外生成，最终写锁复核人格标签、屏蔽、发现可见性与事实；生成超时用真实 Node 计时。可信调用可用 `expire:true` 按 C4 规则结束为 timeout，仍优先检查既有归来事实、隔离和终态。自动生产方的截止策略与触发频率待 A 裁定；无自动后台补跑。
