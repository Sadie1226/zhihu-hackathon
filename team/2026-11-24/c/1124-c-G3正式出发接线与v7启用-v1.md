# G3 正式出发接线与 v7 启用

交付分支 `c-d5-start-wire-1124`。唯一开发基线为 `a-d5-interface-ready-1124@582376e46de365dcd72ff324676662e2c3cdab75`。实现提交为 `8e81255c5f0c8a77a69357c526152fb6e864f06b`，本报告随后的文档提交承载门禁记录。

## 默认迁移与出发事务

- `lib/db/migrations.ts` 登记唯一一项 v7，直接引用既有 `TRIP_HISTORY_V7_SQL`。`d5InterfaceMigrations` 指向同一个注册表。默认 `getDatabase()` 通过 `openDatabase()` 使用该注册表。新库从基础 schema 运行正式迁移，v5 库按序升级 v6、v7。测试核对 v7 对象等价、20 只种子狗原装配、失败回滚到 v5 或 v6、重开幂等及 SQLite 完整性与外键。
- `lib/trips/departure-snapshot.ts` 的唯一正式 builder 同步调用 `deriveSnapshot(db, meta.dogId, { occurrenceFacts: readOccurrenceFact })` 和 `toFixedSnapshot(result, meta)`。C4 在归属、状态、配额和 6 小时间隔通过后调用它。绑定发生在 running、`started_at` 和本次交换投递之前，整段共享同一个 `BEGIN IMMEDIATE`。主人 HTTP 和可信种子入口走同一段逻辑。
- running 重试沿用原 Trip 和已有绑定。内部读者通过 `readDepartureSnapshot(db, tripId, dogId)` 读取绑定版本。旧 running 或终态 Trip 的历史绑定缺失仍读 `null`。新出发若需要无法核实的旧事件事实，HTTP 返回 409 / `CONFLICT`，detail 含 `HISTORY_UNVERIFIABLE`。失败的 Trip 保留 pending，快照、绑定及投递不留半份。
- 在隔离库的生产 HTTP 回归，Next 启动后通过真实请求从 v6 升到 v7。第一次 start 写入绑定版本 1，投递到期交换。重复请求返回同一 Trip 和空投递列表，只读连接核对只有一版。另有真实双连接主人及种子测试，均证实只有一个快照版本和一次投递。

## C7 种子事件

可信执行器在 `createSeedTripRunner(db)(dogId, intentId).start()` 成功提交后，可在同一意图调用 `selectEvent(conditions)`。C4 和 C7 使用同一个稳定 Trip ID 函数。C7 事务内验证意图、Trip、同狗、`is_sample=1`、无 owner、auto 和 running，再进入与真人共用的筛选、权重和冷却逻辑。普通 owner 或 seed Cookie 被拒。HTTP start 也拒绝客户端传入 `intentId`。选择器遇到调用方已有事务时明确拒绝。

专项使用标明的演练条件。空条件返回 `null`，有候选才记录 occurrence，v7 同一插入语句冻结代码和公开文本。重试同一意图复用 occurrence 和发生时间。修改模板后第二次出发的正式快照仍使用首次冻结文本，第一次绑定版本保持原样。第二趟无匹配时正常完成。测试也核对 seq 0→1、1→2 投递及已读、已回应字段。
