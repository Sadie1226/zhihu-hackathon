## 2. 生命周期（真跑出来的时间线）

```
第 1 天 09:00  甲寄出        deliver_after_trip_seq = 1   delivered_at = null   ← 在路上
第 1 天 10:00  乙出发        delivered_at = 10:00         ← 到达（乙的第 1 趟）
```

## 3. 今天新增的三个东西

### 3.1 `POST /api/exchanges`（契约已有，代码才补上）

```
POST /api/exchanges
Header  Cookie: <session>
        Content-Type: application/json
        Idempotency-Key: <这次提交的标识，1–128 个可见字符>
Body    { "fromDog": "dog_a", "toDog": "dog_b", "kind": "gift",
          "payload": { "kind": "gift", "giftName": "一小卷灰蓝色的毛线",
                       "note": "天气要冷了", "imagePath": null,
                       "sourceFindId": null, "sourceMode": null } }
出      { "exchange": Exchange }      // 与 GET 同一形状，deliveredAt 为 null
错      CONFLICT 409 / NOT_FOUND 404 / NETWORK 503（脱敏）
```

**只收 `gift` 与 `co_owner_message`。** `find` / `greeting` 是两条狗碰上时的当场产物，
必须有 trip 上下文；从这里放进来等于开一个「不用出门也能造一次相遇」的后门。

**`Idempotency-Key` 是必填的，服务端不替你生成。** 理由两条，都指向阻断缺陷：

- 服务端随机生成 → 用户超时重试就多一份一模一样的礼物，正是「重复投递」；
- 用内容哈希当键 → 真的想再送一份同样的东西时，会被判成重试而**静默丢掉**。

所以只能要一个显式的「这次提交」标识，重试复用同一个值。前端写法：点提交时
`crypto.randomUUID()` 生成一次，失败重试**复用**，成功后再换。

### 3.2 `isWaitingForReply(exchange)` —— 「在等回应」只有一个判定

```ts
deliveredAt !== null && repliedAt === null && (kind === 'gift' || kind === 'co_owner_message')
```

三条各自拦一种错：

- 没到不算等 —— 在路上的期待是另一回事，界面写「尚未送达」；
- 回过了不算等；
- `find` / `greeting` 没人等回音（相遇当场就给完了）。

**收件方不在这个判定里。** 收到东西 ≠ 欠一个回应（不变量三：不回应不惩罚）。
「等」只是寄件方一句陈述，不该变成红点、天数或进度条。

同一份判定在 `lib/social/snapshot-derive.ts` 里有一份 SQL 版（快照 `waiting_for` 用）。
两处条件必须逐字对应，改一边就得改另一边 —— 否则会出现「手账说在等、快照说不等」。
