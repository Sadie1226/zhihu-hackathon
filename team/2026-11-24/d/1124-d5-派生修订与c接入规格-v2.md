## 一、`waiting_for` 是寄件方的视角

```sql
-- v1（错）：这会让收件狗声称「我在等回音」，而它没寄过任何东西
WHERE to_dog = ? AND delivered_at IS NOT NULL AND replied_at IS NULL AND kind IN ('gift','co_owner_message')

-- v2：甲寄给乙，乙已收到未回应 → 甲在等
WHERE from_dog = ? AND delivered_at IS NOT NULL AND replied_at IS NULL AND kind IN ('gift','co_owner_message')
```

三条边界，每条一个用例：

- **未到达不算**（`delivered_at IS NULL`）：东西还在路上，谈不上等回音（S7）
- **已回应不算**（`replied_at IS NOT NULL`）：甲下一次新快照结束等待，**本趟已固定的版本不变**（S8）
- **`find` / `greeting` 不产生等待**：它们不需要回应（S9）

多条都在等时取**最早到达**那条 —— 等得最久的那件事最像「它还记着」。其余几条不丢，
记在 `otherPendingWaiting` 里只作证据，不进快照（S5）。

文案仍是**受控模板**，不拼 `giftName` / `message`：那是主人起的名字和原话。
`gift` → 「等一份礼物的回音」，`co_owner_message` → 「等一句回话」。

## 二、版本：不再由脚本「重跑覆盖」

v1 让脚本直接吐 `INSERT … ON CONFLICT DO UPDATE SET recent_trips = …`，版本写死 1。
那不是「重跑一次」，那是**把已经固定下来的旧经历改成今天的样子**。改成三层：

| 谁 | 做什么 | 在哪 |
| --- | --- | --- |
| D | 只读派生 + 输出证据 | `lib/social/snapshot-derive.ts` |
| C | 出发事务内分配新 version、插入、绑定本趟；已固定版本拒改 | 调上面这个入口 |
| A | 只看证据，不需要读 SQL | `--out` 的 JSON |

入口三个导出，C 直接用：

```ts
import { deriveSnapshot, toSnapshot } from '@/lib/social/snapshot-derive'

// C 的出发事务里（本函数不开事务、不写库）
const { body, evidence } = deriveSnapshot(db, dogId)
const snapshot = toSnapshot(body, { dogId, version: nextVersion(prev), createdAt: now })
// → 由 C 插入并绑定本趟；重复 start 不得重算或新增版本
```

万一还需要 SQL（演练库手工推进时），三条限制全在：

1. **必须显式给 `--version`**，没有默认值；不给就报错退出。
2. **只 `INSERT … SELECT … WHERE NOT EXISTS`**，没有 `UPSERT` / `ON CONFLICT`。
3. **SQL 单独落文件**（`--sql-out`），报告走 stdout —— v1 那种「报告和可执行 SQL 混一屏」，
   最容易发生的事就是有人把报告里的片段当 SQL 跑。

实测：生成的 SQL 连续执行两遍，`snapshot` 仍是 20 行、`dog_seed_07` 的 `recent_trips` 原样；
对已写入 v1 的库再跑一次派生器，20 只全部标 `SKIP`：

```
SQL：insert-v1-again.sql（20 条，SKIP 20 条；与报告分离，不混在一屏）
```

## 三、一致读取与可追溯

`--db` 走只读连接 + 单次读事务，一只狗的经历和挂念出自同一个时间点，读不到「写了一半」的中间态。
每条证据长这样（`--out` JSON 的 `dogs[].evidence`）：

| 字段 | 内容 |
| --- | --- |
| `trips[]` | `tripId` / `seq` / `status` / `startedAt` / `endedAt` |
| `trips[].event` | `id` / `code` / `happenedAt` / `text`（本趟最早一条；`eventCount` 给本趟总条数） |
| `trips[].summary` | 真正进 `recent_trips` 的那一句（就是 `event.text`，不改写、不套话） |
| `trips[].finds` | 这趟的 `find.id` / `kind` / `sourceMode` —— **只给标识，不给标题与摘要** |
| `waiting` | `exchangeId` / `kind` / `deliveredAt` / `template` |
| `otherPendingWaiting` | 还有几条也在等（不进快照） |
| `findCoverage` | 几趟有 Find / 几趟无 |
| `textSource` / `textMutable` | `'event.text'` / `true` |

**关于 `textMutable`**：`event.text` 是可变列，本入口读到的是「此刻」的文本。
所以它**只用于生成新版本**；旧版本的冻结靠 `(dog_id, version)` 主键 + 只插不改，
不靠「重新派生一次得到同样的话」—— 那句话在文案被改过之后就不成立了。
等 C 定了不可变事件版本（或 `trip_event` 落一份当时摘要），这里改成读那份、标注随之去掉。

**关于 Find**：`findCoverage` 单独出，因为事件链不等于 Find 链。一趟有 `trip_event` 不等于有 Find；
反过来 Find 也可能挂在没有事件的趟上。无 Find 就如实 0，不拿事件充当。

## 四、最近三趟（两处措辞改了）

- **3 是趟次数**，不是条数。最近三趟都没事件 → `recent_trips = []`，不往前捞（S11）
- **`timeout` 算一趟**，而且**有事件就照给**。v1 注释写「超时趟就是这种（没事件）」，把一种情况说成了全部（S4）
- **`failed` 不算「回来过」**，也不改变出发次数 / 间隔规则；但它会以 `failedTripsIgnored` 露出来 ——
  看到它、并明确没算，比静默忽略好（S12）

## 五、5 只首轮：到哪一步了（不夸大）

**C8 目前只跑出 1 只**：`dog_seed_07` 两趟（seq 1 `done` @ 00:00Z、seq 2 `done` @ 06:00Z），
事件与 Find 均为空。C 在 C8 交付里已公布这两个 `trip.id`，并写明 `D5_REAL_DERIVATION_PENDING`。

**D 这边做了一件补充**：用 C8 同一个入口 `createSeedTripRunner`（不是插行）在**自建隔离库**里
给 5 只各跑 1 趟，然后对这个库跑派生器：

```
dog_seed_01  回来过 1 趟，摘要 0 条 · waiting null · Find 0 有 / 1 无
dog_seed_05  …（同形）
dog_seed_07  …（同形）
dog_seed_12  …（同形）
dog_seed_18  …（同形）
小计：有真实旅途 5 只 / 无 15 只
```

结论如实：**5 只各有 1 趟真旅途，事件为空，`recent_trips` 就是 `[]`** —— 空结果保留，不补。

必须说清它**不是**什么：

- 不是 C8 验收。C 的验收库由 C 给，我这份是 D 自己开的隔离库。
- 不能算「5 只已验」。事件全空是因为 **C7 未入主干**（C 自己标 `EVENT_INTEGRATION_PENDING`），
  摘要要等事件真落库才可能出现。
- 也不证明业务库状态 —— 那是第三件事（见第七节）。

**需要 A / C 一句话**：验收库的路径（或由 C 指定一个固定路径）。给了之后一条命令出正式证据：

```bash
node scripts/d5-derive-snapshot.mjs --db <验收库> --out team/2026-11-24/d/d5-evidence.json
```

## 六、统一校验，不再复制常量

`toSnapshot` 把派生内容和版本拼好后**直接调** `lib/social/snapshot.ts` 的 `validateSnapshot`，
不过就抛错，不截断、不降级。而且用的是 `{...body, dogId, version, createdAt}` 展开 ——
万一有人往 `body` 里加了契约外的字段（比如塞一段主人原话），逐键抄会**悄悄丢掉**它然后一切看起来正常，
展开才能让键白名单把它挡下来。丢字段和拒字段，后者才是我们要的。

派生模块里现在**没有 40 这个数字**了（v1 自己复制了一份）。
