## 一、三句话结论

1. **E 说的五个已移除 ID（P03 蘑菇帽、P10 毛球帽、P11 条纹围巾、P14 黄色耳机、P17 滑板）在代码、契约、fixture、20 只装配单、30 条事件池里零引用** —— 因为 d 的装配单根本不用 P 编号，用的是四键枚举。已实跑验证，见第三节。
2. **「最小联调先用 S02」这件事，d 侧现在做不到**：S02 是单品披肩，而 `assembly.cloth` 的六值枚举里没有披肩，`parseAssembly` 会直接拒。**但库不会拒** —— 库只数键数，这是第二个「库拦不住」的坑（第一个是 `"none"`）。
3. 真正的阻塞不是「选错 ID」，是**两套体系的结构不一样**：四键（衣/帽/镜/脸）对 v5 的五组（套装或单品 / head / eyes / carry / back / 表情）。要不要迁、怎么迁，得 A/C 拍板。我建议**今天不迁**，S02 走 E 的独立页面，见第七节。

## 三、核对结果：零引用（可复跑）

```bash
# 在任意基于 main 的干净工作区
git grep -nE "P03|P10|P11|P14|P17|P21" origin/main -- lib contracts app scripts tests
```

命中只有二进制 PNG（像素里恰好有这几个字节序列），**文本文件零命中**。原因很简单：d 的装配单是

```json
{"cloth":"hoodie","hat":"beanie","glasses":"square","face":"happy"}
```

四键、九个枚举值，从头到尾没有 P 编号可写。

所以这条要求对 d 的现状**没有纠正对象**，它是给未来立的规矩。我先把它固化成可复查的事实，后面真换 ID 时照它查。

## 四、两套体系差在哪（这才是要拍板的东西）

| d 的四键 | 取值 | v5 对应 | 差异 |
| --- | --- | --- | --- |
| `cloth` | hoodie / jacket / sweater / raincoat / apron / scarf-coat（6） | `sets` 6 + `singles` 9 = **15 选 1** | 选项翻倍，且套装/单品是两种模式 |
| `hat` | beanie / cap / straw / none（4） | `head` 槽 3 个 + 空 | **草帽没有对应** |
| `glasses` | round / square / sun / none（4） | `eyes` 槽 3 个 + 空 | **方框镜没有对应** |
| `face` | happy / tired / hopeful / waiting（4） | 表情 10 个（F01–F10） | 10 → 4，只能语义收窄 |
| **（无）** | — | `carry` 槽 2 个（保温壶、星星包） | **四键没地方放** |
| **（无）** | — | `back` 槽 1 个（蓝翅膀） | **四键没地方放** |

v5 的 `modeRules` 还定了三条 d 现在没有的规则：

- `outfit` 模式：**选套装时不带任何配饰**（`set:1, single:0, accessories:0`）
- `mix` 模式：一件单品 + 每个槽最多 1 个配饰
- 互斥：`F09-dark` 表情不能配 eyes 槽（自带深色镜片）；`F09-dark` 也不能配 `T07-striped-knit`（套装自带眼镜）

**最后一条最要紧**：d 现在每只狗都是「衣 + 帽 + 镜 + 脸」四样齐全（帽/镜可为 null，但键都在）。v5 是「套装模式下配饰全空」。这不是换个枚举值能解决的，是形状变了。

## 五、实测：库拦不住值，只拦键数

用真 schema 建库，插五种装配单（脚本跑完即删，未入库）：

| 试的输入 | 结果 |
| --- | --- |
| `{"cloth":"hoodie","hat":null,"glasses":"round","face":"happy"}` | ✅ 入库 |
| `{"cloth":"S02-leaf-cape", ...}` | ✅ **入库**（库不认识这个值） |
| `{"cloth":"随便什么", ...}` | ✅ **入库** |
| 五键（加 `carry`） | ❌ 被触发器拒：必须恰好四个键 |
| 三键（去 `glasses`） | ❌ 被拒 |

`contracts/schema.sql:91` 的触发器只做两件事：`json_valid` + 数键数 + 四个键存在。**枚举值一个字都不查。**

结论，给 c 一句话：**「换 ID」这件事必须在 `parseAssembly`（`lib/adoption/development.ts:121`）里加白名单，不能指望库。** 现在是 `allowed.cloth = [hoodie, jacket, sweater, raincoat, apron, scarf-coat]` 硬编码，任何 wardrobe ID 都会在读写时炸 —— 但库里可能已经躺着一行脏数据，等下次读才暴露（和 `"none"` 那个坑完全同型）。

## 六、S02 为什么现在装不进去

`S02-leaf-cape` / 叶片披肩 / `singles/`，在 E 的最小装配里是两层：`base-front.png` + `S02-leaf-cape.png`，偏移 (0,0)，画布 1024×1024，脚底 (522,950)。

换成 d 的四键，它只能塞进 `cloth`：

```json
{"cloth":"S02-leaf-cape","hat":null,"glasses":null,"face":"happy"}
```

- 库：**收**（只数四键，见第五节）
- `parseAssembly`：**拒**（`S02-leaf-cape` 不在六值里）
- 渲染层：拿不到 `cloth` 对应的图，兜底会走缺图分支

也就是说，**只跑 S02 这一只，也得先动 `parseAssembly` 的白名单**。这是最小改动，但它仍然是一次契约侧的改动，不该由 d 擅自做。
