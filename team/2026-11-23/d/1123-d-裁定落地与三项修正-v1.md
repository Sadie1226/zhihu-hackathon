## 二、事件条件：`place_tags='[]'` 里有一条在撒谎，不，两条

C 的口径是「原场景全部保留，无合适事件就不展示事件、旅途继续」。那 `place_tags='[]'` 就必须真的等于「任何场景都成立」——它不能当兜底用。而实际有两条写着场景：

| code | 原文 | 原条件 | 问题 | 现在 |
| --- | --- | --- | --- | --- |
| `spring_first_green` | 墙根的草冒了一点绿，昨天还没有。 | `[]` | **要有墙**。沙丘、白桦林、湖心都没有 | `["street","stall"]` |
| `summer_cicada` | 树上的蝉叫得整条街都听见，忽然一起停了。 | `[]` | **要有街**。同上 | `["street"]` |
| `autumn_birds` | 天上有一队鸟往南飞，队形一直没散。 | `[]` | 真的不限 | 不动 |
| `any_moon_ring` | 月亮边上有圈淡淡的光，据说第二天要起风。 | `[]` | 真的不限 | 不动 |

**为什么收紧条件而不是改文案。**「墙根」「整条街」是这 30 条里少数有画面的细节。为了迁就 `[]` 把它们改成「路边」「树上的蝉」，是拿文本质量换表格整齐。条件该说实话，文案不该降级。

**代价明摆着**（同一个脚本跑出来的）：

| | 修正前 | 修正后 |
| --- | --- | --- |
| riverside 场景（5 张）每张可出 | 8 条 | **6 条** |
| 3 张无标签场景每张可出 | 4 条 | **2 条** |
| 平均每张场景 | 11.4 条 | **10.1 条** |
| `place_tags='[]'` 条数 | 4 | **2** |

也就是说，鸣沙山、白桦林、酒馆内景现在各自只剩 2 条能读通。这是收紧的必然结果，不是 bug。要么接受（C 说的「不展示事件，旅途继续」），要么给这 3 张配 2–3 条**真不限地点**的新事件（我出文本，30 条的口径要 c 点头）。

**幂等**：两条 UPDATE 都带 `AND place_tags = '[]'`。第二次执行影响 0 行；日后若有人改过这两条，补丁不会覆盖他。

## 三、覆盖脚本：从「12 张」变成「读清单」

原来硬编码 `12` 和「四值」，E 一交新图就红。改四处：

## 五、给 C 的一条：室内事件现在没有表达手段（**先别加值，等 E 的图**）

派生规则写清楚，等数据到位就能一键生成（不给手写留位置）：

```sql
-- recent_trips：该狗最近 3 次正常回来的出行，每次取一条事件文本
SELECT e.text
  FROM trip t
  JOIN trip_event te ON te.trip_id = t.id
  JOIN event e       ON e.id = te.event_id
 WHERE t.dog_id = ? AND t.status = 'done'
 ORDER BY t.seq DESC, te.happened_at ASC
 LIMIT 3;
-- 一次出行有多个事件时只取最早的一条；文本超 40 字截断（schema CHECK 与 snapshot 同口径）
-- 没有 done 的 trip → recent_trips = []，不是编三条

-- waiting_for：该狗作为收件方、东西已到但还没回应的那一条
SELECT x.kind, x.payload
  FROM exchange x
 WHERE x.to_dog = ? AND x.delivered_at IS NOT NULL AND x.replied_at IS NULL
 ORDER BY x.delivered_at ASC
 LIMIT 1;
-- 没有就 NULL。
```
