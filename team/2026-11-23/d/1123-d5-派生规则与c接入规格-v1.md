## 一、给 c 的接入规格（现在就能照着做）

### 1.1 方向不能反过来

```
错：  场景地名  ∩  event.place_tags        ← 交集恒为空
对：  场景地名 → tags（换算表）→ event     ← 两跳
```

`place_tags` 只有四个值：`street` / `stall` / `riverside` / `bookstore`。e2c 给的是「长白山天池」「南头古城」这类具体地名。拿中文地名去和这四个值求交集，SQL 不报错，结果恒为空，最后只剩 `place_tags='[]'` 的两条会出——**看起来像「事件池太小」，实际是匹配写反了**。

### 1.2 三份输入，顺序不能乱

| 顺序 | 输入 | 位置 | 作用 |
| --- | --- | --- | --- |
| ① | 事件条件补丁 | `team/2026-11-23/d/1123-d2c-事件条件修正-v1.sql` | 把两条假「不限」收紧。**不跑这步，后面算出来的都是修正前的数字** |
| ② | 场景 → tags 换算表 | `team/2026-11-23/d/scene-place-compat.json` | 12 个地名各自能用哪些标签 |
| ③ | 场景清单与脚底点 | `team/2026-11-22/e/e2c/scene-map.json` | 只有 place / file / 脚底点，**不含 tags** |

补丁幂等：两条 `UPDATE` 都带 `AND place_tags = '[]'`，重复执行影响 0 行。

### 1.3 可直接粘的匹配 SQL

```sql
-- :scene_tags 来自 scene-place-compat.json —— 每张场景一个 tags 数组
WITH scene(place, tags) AS (
  VALUES ('长白山天池', '["riverside"]'),
         ('南头古城',   '["street","stall"]')
         -- …其余 10 行照换算表抄，别手改
)
SELECT s.place, e.code, e.text
  FROM scene s
  JOIN event e
    ON e.enabled = 1
   AND (
     json_array_length(e.place_tags) = 0                    -- 真·不限地点，补丁后只剩 2 条
     OR EXISTS (SELECT 1 FROM json_each(e.place_tags) t
                 WHERE t.value IN (SELECT value FROM json_each(s.tags)))
   )
 ORDER BY s.place, e.weight DESC;
```

`json_array_length = 0` 那个分支要留着——它现在是「任何场景都成立」的正经语义，不是「还没填」。补丁前有 4 条，补丁后 2 条（`autumn_birds` / `any_moon_ring`）。

### 1.4 这个表只管一维

换算表只解决 **place**。`event` 还有 `season` / `weather` / `time_of_day` 三个条件列和 `weight` / `cooldown_days` 两个调度列，都不在这张表里，也不该由 d 替 c 定。c 的匹配做四维交集时，place 这一维用本表，其余三维按 c 自己的调度逻辑。

### 1.5 现在的实际后果（c 会看到的现象）

| 场景 | tags | 能出的事件数 |
| --- | --- | --- |
| 天池 / 喀纳斯 / 三亚 / 盘锦 / 漓江（5 张） | `riverside` | 各 6 |
| 南头古城 / 深夜街角 / 北京路（3 张） | `street` + `stall` | 各 23 |
| 社区公园（1 张） | `street` | 16 |
| 鸣沙山 / 白桦林 / 酒馆内景（3 张） | `[]`（无标签） | 各 2 |
| **书店（室外 / 室内）** | `bookstore` | **0（E 的图还没进清单）** |

合计 121 条次 / 12 张（同一事件可落在多张场景，所以不是 121 条不同事件），平均每张 10.08 条。

`bookstore` 目前 0 张场景 → 3 条书店事件永远出不来。E 补两张图后填进换算表即可，**换算表加两行，脚本自动重算，不用改代码**。

建议给 a 的一个判断：**没有合适事件就不展示事件、旅途继续**（C 已定口径）。所以缺 `bookstore` 场景时不需要造事件，跳过就行——现在唯一要防的是「因为匹配写错导致所有场景都只剩 2 条」，那种情况下「旅途继续」看起来会像「事件池坏了」。

### 1.6 自查一条命令

```bash
node scripts/d2c-scene-coverage.mjs
```

它会报：30 条事件的标签分布、12 张场景逐文件比对、多少条永远出不来、每个标签几张场景。**E 交新图后这个脚本会红**，因为换算表和 `scene-map.json` 张数对不上——这是有意的，避免两张清单各走各的。

## 二、D5：派生规则与「证据生成器」

### 2.1 为什么不交五条手写摘要

A 的原话是「5 份手写夹具已读，后者仅样例，不是已跑出真实经历的 D5 完成」。这个判断对。手写摘要有两个问题：

1. **它可能和库里的事实不符**，而且这种不符在界面上看起来完全正常——跟 11-22 那次青椒标签写错是同一类。
2. **它不可复跑**。c8 种子触发一通，谁去重写这五条？

所以这次交的是**派生器**：`scripts/d5-derive-snapshot.mjs`。每一句摘要都能指回一个 `trip.id` 和一条 `event.code`，指不回去就输出空。

### 2.2 三条口径，每条都有反例

| # | 口径 | 反例（脚本里就这么断言的） |
| --- | --- | --- |
| 1 | **3 是趟次数，不是条数** | 最近 3 趟全超时 → `recent_trips = []`，不许往前捞「最近三次有收获的」 |
| 2 | **timeout 算一趟，failed 不算** | 超时是正常结束（契约原话），失败是系统故障，主人看到的是重试不是「它回来了」 |
| 3 | **摘要用 `event.text`，不用 `message.text`** | `event.text` 是「发生了什么」，第三方可见；`message.text` 是「它对主人说的话」，进快照就把主人语境带出去 |

第 1 条最容易被写错：直觉会写成「取最近 3 条有事件的出行」，那样快照会声称「最近三次」而实际是「最近三次有收获的」——**把没发生的经历补上了**。

### 2.3 `waiting_for` 怎么从 exchange 推

```sql
SELECT id, kind, created_at FROM exchange
 WHERE to_dog = ?
   AND delivered_at IS NOT NULL      -- 已经收到了，才谈得上等回音
   AND replied_at IS NULL            -- 还没回应
   AND kind IN ('gift','co_owner_message')
 ORDER BY created_at ASC LIMIT 1;
```

映射成一句：`gift` → 「等一份礼物的回音」，`co_owner_message` → 「等一句回话」。
`find` / `greeting` 不产生等待——它们不需要回应。

**不拼 `giftName`**：那是主人起的名字，属于「主人原话不进 snapshot」的地界。快照里只说「在等一份礼物的回音」，不说等的是什么。

### 2.4 现在是 0 趟，这不是失败

```
$ node scripts/d5-derive-snapshot.mjs
  dog_seed_01   0 趟·0 条摘要  waiting null
  …
  dog_seed_20   0 趟·0 条摘要  waiting null
小计：有真实旅途 0 只 / 0 趟 20 只

⚠ 20 只没有可用的 trip：它们的 recent_trips 只能是 []，waiting_for 只能是 null。
  这不叫「做完 d5」，叫「机制就位、缺真实数据」。真实 trip 只有 c8 能写。
```

种子狗 `is_sample = 1`、`session_id = 'seed'`，没有一行 `trip`。A 说的「种子服务端触发仍待」指的正是这个缺口。我不拿 fixture 里的 `trip_seed_01` 冒充——那是夹具，不是它走出来的。

**c8 一通，一条命令出真证据：**

```bash
node scripts/d5-derive-snapshot.mjs --db <真库路径>          # 看报告
node scripts/d5-derive-snapshot.mjs --db <真库路径> --sql    # 出 UPSERT，附来源 trip.id / event.code
```

输出里每只狗会带着 `seq1 done evt_xxx <摘要原文>` 这样的行，`waiting_for` 后面跟着 `← gift ex_xxx`。那就是 A 要的「实际旅途 / Find 来源到摘要的证据」：**摘要 → 事件 → 趟次 → 狗**，四级都能倒查。

### 2.5 自检 10 条（跑的是机制，不是经历）

```bash
node scripts/d5-derive-snapshot.mjs --selftest
```

10 条全绿，覆盖：三趟都算、超时趟留痕不贡献摘要、每趟取最早事件、`waiting` 三种排除（没到达 / find / 已回应）、最近三趟全空时 `[]`、`failed` 不计入、超 40 字报错不截断。

**S10 值得单说**：`event.text` 有 `CHECK length(text) <= 40`，`snapshot.recent_trips` 单条上限也是 40。两侧口径一致，所以这一关正常情况下永远不响。留着是因为它防的是「哪天 C 放宽事件文本」——那时候如果这里悄悄截断，快照上的话就和事件原文对不上了。**不截断，报错，让人来对齐。**

## 三、「可信未来出发衔接」是怎么成立的

A 问的这条，链条是这样的：

```
送出        deliver_after_trip_seq = 收件狗当前 seq + 1     （c 算，d 不传）
   ↓
下一趟出发   trip.seq >= 该值 且 started_at 非空              （投递判断的唯一正确写法）
   ↓
投递        delivered_at 由投递器写一次，不再写               （c 写）
   ↓
未被回应     replied_at IS NULL                              （b 写）
   ↓
写进快照     waiting_for = 「等一份礼物的回音」+ 来源 exchange.id
   ↓
再下一趟出发 snapshot 里这句话就是「它带着什么挂念出门」
```

衔接点只有一个，而且是**时间顺序上的**：**快照必须在 trip 开始之前生成**。如果生成时机在 trip 创建之后，`waiting_for` 里就会混进这趟刚收到的东西，时间线错位，而界面上完全看不出来。

这条我只能指出来，落不落实在 c8 的触发时机——**需要 A 给一句**：snapshot 是在 `createTrip` 之前由种子触发顺带生成，还是独立一次写入？
