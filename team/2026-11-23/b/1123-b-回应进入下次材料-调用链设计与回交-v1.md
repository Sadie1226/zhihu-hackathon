## 1. 现状核实（基于 main@dd5f53e 真实代码，非推测）

先把「回应」到「下次出行」之间**实际存在的**与**不存在的**链路列清，避免设计悬空。

| 环节 | 真实代码位置 | 现状 |
|---|---|---|
| 回应落库 | `lib/replies/idempotency.ts:writeReply()` | B 写 `reply` 表；同来源唯一约束幂等（重复返回 `duplicate`+库中真实行，HTTP 200）；exchange 来源同时写 `exchange.replied_at`（WHERE 保留首次时间） |
| reply 表结构 | `contracts/schema.sql:501-542` | 列：`id / exchange_id / invitation_id / text / photo_url / kind(生成列) / created_at`。**没有 dog_id、没有 category、没有"下次材料"字段、没有来源可搜索文本标记** |
| 心愿落库 | `contracts/schema.sql:226` wish 表、`lib/wishes/contract.ts` | B 写；`text`(1–200) + `category`(六类目) + `revoked_at` + `source IN ('owner','collection')` + `source_url`。**source 枚举里没有 'reply'** |
| 心愿被选出 | `lib/wishes/contract.ts:selectActiveWish()` | C 的 C5/C6 选择边界，在 trip-start 写事务内调用；只从 `v_wish_active`（`revoked_at IS NULL`）读；排序 owner 优先，再 `created_at DESC, id ASC`，LIMIT 1 |
| 出行绑定心愿 | `lib/trips/service.ts:start()` :117-119 | `trigger='wish'` 时在写锁内 `selectActiveWish()` 并写 `trip.wish_id`；撤销中（pending 期间被 revoke）的心愿不会成为 provenance |
| 发现生成 | `lib/trips/discover.ts:discover()` :23-40 | **当前只选一个候选**：`trigger='wish'` 用 `readTripWish().text` 当 query；否则遍历 `dog.interest_categories` 取第一个未被 blocked 的关键词。**完全不读 reply / message / 上次材料** |
| 归来一句话 | `app/(b)/b5-share.ts:createMessageStore().write()` | B 写 `message`；`mentions_find_id` 指向本趟 find；schema :416 注释「c 只读，用来做**经历改写兴趣**」——这是 a3 的通路，归 A |
| finish 接 B 写入 | `lib/trips/service.ts:finish()` :62-77 | `finishResult()` 返回 `{trip, finds, message: null}`；**没有调用 `createMessageStore().write()`**，真实生成闭环仍未接 |

**结论**：reply 与 wish 是两张独立表（都 B 写），C6 只消费 wish 不消费 reply。因此「回应进入下次材料」目前没有现成数据通路，需要设计一座桥。

## 2. 选定方案：以 wish 作桥（B 侧回应 → 可搜索心愿 → C6 既有通路）

选择理由：C6 `discover()` 已经完整支持「wish → query → 搜索 → find」，并且 `start()` 已在写锁内锁定 wish provenance。把回应里**可被搜索的意图**转成一条 wish，就能复用整条已验链路，不必改 C6 主流程、不必碰 C 状态机。

### 2.1 端到端调用链（目标态）

```
① 主人回应（文字/照片）→ b `writeReply()` 写 reply（既有，幂等不变）
        │
        ├─ 来源 invitation：reply.invitation_id → invitation.dog_id 得归属狗
        └─ 来源 exchange：reply.exchange_id → exchange.to_dog 得归属狗（收件狗）
        │
② 【新增·B】回应成功落库后，在同一可信服务端流程内，
   从 reply.text 提取"可搜索意图"，另写一条 wish，source='reply'：
     wish.text       = 从回应文本提取的搜索意图（≤200 字，去掉语气/称谓）
     wish.category   = 归类到六类目之一（用确定性规则，不调 AI）
     wish.source     = 'reply'        ← 需 C 在 schema 加此枚举（见 §3）
     wish.source_url = NULL
     wish.revoked_at = NULL
   关联键：以 reply.id 作为幂等/溯源锚点（见 §2.3）
        │
③ 下一次出行（trigger='wish' 或 C6 入选）→ `start()` 调 `selectActiveWish()`
   选中这条 reply-wish → 写 `trip.wish_id`（provenance，写锁内）
        │
④ `discover()` 用 `readTripWish(db, tripId).text` 当 query 搜索 → 落 find
   （blocked_topics 过滤在 ③ 前后都生效：屏蔽优先级高于回应材料，符合手册 b7）
        │
⑤ 主人看得见因果：这条 find 来自 `trip.wish_id` → wish.source='reply'
   → reply.id → 原回应。三次之内可回看"我上次说的"如何变成这次的发现。
```

### 2.2 字段映射（回应 → wish）

| wish 列 | 取值 | 谁定 | 说明 |
|---|---|---|---|
| `text` | 回应文本中的可搜索意图 | B（确定性提取） | 只取能当搜索词的部分；纯情绪/称谓/照片无文本 → **不生成 wish**，不凭空造来源 |
| `category` | 六类目之一 | B（确定性关键词归类，复用 `CATEGORY_KEYWORDS`） | 归类失败 → 不生成或回交 A 由用户显式选；**不调 AI 猜测** |
| `source` | `'reply'` | **需 C 扩枚举** | 当前 schema CHECK 只允许 `owner/collection`，见 §3-1 |
| `source_url` | NULL | B | 回应不是知乎授权收藏，不填 |
| `revoked_at` | NULL | B | 走既有撤销入口，可撤销（撤销后 C 不再读，符合 `v_wish_active`） |
| `dog_id` | 由 `reply` 反查归属狗 | B | invitation→dog_id；exchange→to_dog |

### 2.3 幂等与溯源（关键设计点）

- 一次回应最多产生一条 reply-wish。用 `reply.id` 作幂等键。
- **需要一个关联列**（如 `wish.origin_reply_id TEXT REFERENCES reply(id)` + 唯一约束）才能做到：重复提交不产生第二条、可溯源回原回应、撤销/重放幂等。
- 当前 wish 表**没有这个列**。加列属「加字段」，按 K 契约「别人不许自己加字段」，**必须 C 改 schema 迁移**（见 §3-2）。在 C 未加之前，B 不写任何绕过列（不把 reply id 塞进 text 或 source_url——那会污染搜索词和 provenance）。

### 2.4 与 A6 的关系（不把字数当差异）

A6 准备明确：B 表达消费**实际选中结果**，不把「话痨/寡言字数不同」当选择差异；必须保留候选来源、标签输入、选择理由和真实选中 Find ID。本方案中：

- 回应意图转 wish 是**候选材料供给**，不是「选择」本身；选择发生在 C6 `discover()`/A6 选择器。
- B 侧只保证：wish.source='reply' 可标识来源、`origin_reply_id` 可回溯、`trip.wish_id` 可查到本次用了哪条材料。选中 Find ID 由既有 `find.id` + `message.mentions_find_id` 承载。
- 性格标签只在 B5 `write()` 的话长区间上生效（话痨 20–35 / 寡言 8–15），**不参与"回应→材料"的内容取舍**，避免把语气差异冒充选择差异。

## 4. B 现在能落地 / 本回交换交什么

**本回交只交设计，不改代码、不提代码补丁、不动 schema**。理由：桥的两端都卡在 §3 的 C 前置（source 枚举 + 溯源列），在 C 未变更前写任何 B 侧代码都会被迫用错误来源或绕过列，反而制造需要返工的脏数据。

B 可以立即交、且不依赖 C 的部分（供 A/C 裁定后实施）：

1. **调用链与字段映射**（本文 §2）——已交。
2. **回应意图提取的确定性规则草案**：从 `reply.text` 去称谓/语气、按 `CATEGORY_KEYWORDS` 归类、失败不生成的边界（含"纯照片/纯情绪不生成"）。可先在测试里用 fixture 验证规则，不落库。
3. **验证口径**（不改代码即可定义）：见 §5。

B 不交、明确回交给上游的：schema 加枚举/加列（C）、C6 候选接入（C）、A6 选择与回看（A）、真实生成→finish→store 闭环（A/C 共同，v9 仍未接）。

## 6. 一句话回交

回应进入下次材料（b8）的桥已设计清楚：**B 在 `writeReply()` 成功后把回应里的可搜索意图转成一条 `wish.source='reply'`，复用 C6 现成的 wish→query→find 通路**，即可满足"回应内容出现在下一次出行、三次之内能看出因果"。但桥的两端需 C 先做两件事——`wish.source` 加 `'reply'` 枚举、wish 加 `origin_reply_id` 溯源/幂等列（§3-1/2）——B 不自行加字段。在 C 变更前，B 交此设计不交代码，避免造出需返工的脏数据。相关方：C 前置 schema/C6、A 前置 A6 选择与回看、A/C 共同接真实生成闭环。
