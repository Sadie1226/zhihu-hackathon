## 一、先钉三条（a 已定，我只执行）

1. **一次出行只遇一只狗**（a《给D-邻居池》匹配第 4 步）。不许一次遇三只。
2. **一切都不是即时的**。交换的东西经 `deliver_after_trip_seq` 到达，不即时，不写 `now > x`。
3. **关系类事实只有 d 写**：`relation` 全表、`exchange` 的 `from_dog/to_dog/kind/payload/deliver_after_trip_seq/created_at`、`snapshot` 全表。别人只读。

## 二、换什么：只有四种，多一种都得 c 改 K

`ExchangeKind` 就四个值。**加第五种要 c 改 `contracts/`，不许谁自己塞一个字符串。**

| kind | 换的是什么 | payload | 内容从哪来 |
| --- | --- | --- | --- |
| `find` | 一条沿途发现 | `findTitle` / `findExcerpt` / `sourceUrl` | **必须是这次出行 `find` 表里真实存在的一条**，不许编 |
| `greeting` | 一句近况 | `line` / `weather` | 按双方标签生成，不带任何主人的信息 |
| `gift` | 一件纪念物 | `giftName` / `note` | **必须能在 find 或事件池里找到出处**，不许凭空的礼物 |
| `co_owner_message` | 主人托狗带的一句话 | `message` / `fromOwnerOf` | 主人在 e6 写，d 负责投递 |

**`gift` 的出处这一条写进验收**：`giftName` 不能是模型现编的。狗不会凭空拿出一卷毛线——那卷毛线得是它这趟在某条 find 或某个事件里真碰到的。理由是不变量四：不是这条经历里的东西，就不许当成经历的一部分。

## 三、回合怎么算（d1 里唯一需要精确定义的东西）

**一次相遇 = 一回合 = 两条 `exchange` 记录。** 不是多轮对话，不追求对等。

```
A 出门（trip.seq = n）
  └─ 匹配到 B
       ├─ 记录 1： A → B   一条 A 想给的东西
       └─ 记录 2： B → A   一条 B 想给的东西
```

### 三个时刻，各写什么

| 时刻 | 写什么 | 谁写 |
| --- | --- | --- |
| 相遇当场 | 两条 `exchange`（含 `deliver_after_trip_seq`）、`relation` upsert | **d** |
| 下次再遇 | `relation.met_count + 1`、`last_met_at` 更新 | **d** |
| 到达 | `delivered_at` | **c 的投递器**，d 只读 |

`relation` 按 `dog_a < dog_b` 存（schema 有 CHECK），同一对关系只存一行，所以 upsert 前先按字典序排好两个 id。

### 不回算不算失败

**不算，而且永远不算。** 交换是狗和狗之间自动发生的，不需要任何人回应。

- `replied_at` 永远是 `NULL`，是**正常终态**，不是待办。
- 交换记录不进「未读」「待回应」任何计数。
- 界面上不出现「还没回你」「已读未回」。

这是不变量三在 d 这边的全部含义：**没有任何东西在等主人回话。**

### 老关系不许反复遇

匹配第 2 步：**优先 `relation` 里还不存在的对**。全池都遇过了，才允许重访（那是 4.3，P1，第一个被砍）。
实现上一句话：`relation` 表里有这对的行 → 这次不进候选；只有候选筛完是空集，才退回「全池随机」。

## 四、10 个示例（e 直接拿去当文案底本，c 拿去当 fixtures 正例）

格式：**发送狗（标签）→ 接收狗（标签）**，payload 是原样的 JSON，可以直接进 `exchange.payload`。

### 1 · find · 看物的狗给对方看一个物

`石头（好奇/看物/当下） → 豆子（恋家/慢热/寡言）`

```json
{ "kind": "find", "findTitle": "修鞋摊旁边的搪瓷缸",
  "findExcerpt": "缸沿上磕了两个口，茶还是满的。", "sourceUrl": null }
```

**为什么这样写**：find 只搬它自己看到的东西，不加评价、不加邀请。看物的狗不会说「你应该去看看」，那是在替对方决定。

### 2 · find · 看人的狗注意的是人

`老周（慢热/看人/怀旧） → 小满（恋家/婉转/怀旧）`

```json
{ "kind": "find", "findTitle": "修鞋的老陈今天没出摊",
  "findExcerpt": "工具箱还在，上面压了块砖。", "sourceUrl": null }
```

**为什么这样写**：同一条街，看物的狗给的是缸，看人的狗给的是人。这是 a2「同主题两只狗说得不一样」在 d 这边的落点——差异在**选了什么**，不在语气。

### 3 · find · 带真实出处的知乎内容

`慢慢（恋家/看物/寡言） → 三毛（好奇/自来熟/看人）`

```json
{ "kind": "find", "findTitle": "为什么井盖是圆的",
  "findExcerpt": "因为圆的怎么转都不会掉下去。",
  "sourceUrl": "https://www.zhihu.com/question/000000000/answer/000000000" }
```

**为什么这样写**：`sourceUrl` 有值就必须能在界面上点开。若这条 find 的 `source_mode = 'fixture'`，文案上要标示例——拿假数据装 live 是踩不变量四。

### 4 · find · 风景是最不容易出错的一种

`秋秋（好奇/看物/怀旧） → 团子（恋家/看人/寡言）`

```json
{ "kind": "find", "findTitle": "河面上的雾",
  "findExcerpt": "七点还没散，对岸的楼只剩轮廓。", "sourceUrl": null }
```

**为什么这样写**：`sourceUrl: null` 是对的，风景是自家拼的（`kind='scene'`，`source_mode` 必须为 null）。别给风景硬塞一个知乎链接。

### 5 · greeting · 话痨的狗说天气

`吵吵（自来熟/话痨/当下） → 叮当（自来熟/话痨/直给）`

```json
{ "kind": "greeting", "line": "这边下了两天雨，路上全是水，你那边呢。", "weather": "雨" }
```

**为什么这样写**：话痨 20–35 字是 b 的数法（`LEN_RANGE`），greeting 的 `line` 也照这个区间走，两只狗数出来才是同一个答案。句末用句号，不用问号逼人回答。

### 6 · greeting · 寡言的狗只有一句

`阿盐（慢热/寡言/婉转） → 灰灰（慢热/寡言/看物）`

```json
{ "kind": "greeting", "line": "我这边晴。", "weather": "晴" }
```

**为什么这样写**：寡言 8–15 字。**不要为了凑字数加「你最近好吗」**——那就变成了催回应，违反不变量三。短句本身就是这两只狗的性格，不是没写完。

### 7 · gift · 婉转的狗送东西要带一句轻的

`年糕（恋家/婉转/看人） → 麦子（慢热/婉转/看物）`

```json
{ "kind": "gift", "giftName": "一小卷灰蓝色的毛线", "note": "天气要冷了" }
```

**为什么这样写**：`note` 是陈述不是请求。婉转的狗不说「你收下吧」「记得用」，那是把人放在必须回应的位置上。这卷毛线必须是它某趟真遇到的（见第二节）。

### 8 · gift · 直给的狗连解释都省

`铁蛋（好奇/直给/看物） → 冒冒（好奇/直给/话痨）`

```json
{ "kind": "gift", "giftName": "一块被水冲圆的石头", "note": null }
```

**为什么这样写**：`note: null` 是合法的，直给的狗不写解释。空 `note` 不等于「话没说完」，界面不许补一句「它好像还想说什么」。

### 9 · co_owner_message · 主人托狗带话

`豆子的主人 → 石头（好奇/看物/当下）`

```json
{ "kind": "co_owner_message", "message": "楼下的桂花开了", "fromOwnerOf": "dog_douzi" }
```

**为什么这样写**：`fromOwnerOf` 填的是**狗 id，不是人的名字**。对面看到的是「豆子的主人说」，不是「某某说」。这样一个人永远不知道对面那个人是谁——不变量一的实现方式。

### 10 · co_owner_message · 收件方是种子狗

`小满的主人 → 石头（种子狗，is_sample = 1）`

```json
{ "kind": "co_owner_message", "message": "下次路过那家书店，帮我看看有没有植物图鉴", "fromOwnerOf": "dog_xiaoman" }
```

**为什么这样写**：这条**永远不会有回应**。`石头.replied_at` 会一直是 `NULL`，因为种子狗没有真人主人。界面在发出去的那一刻就要写「这是一位示例伙伴，可能不会回话」。
**AI 假装石头的主人回一句 = 阻断缺陷。** 这条没有讨论空间，也不要「给点安慰性的回复」。

## 五、白名单：什么永不交换

`snapshot` 是白名单（api.md 第四节），`payload` 是它的下游，所以 payload 能装的东西更少。

**允许**：性格标签、兴趣类目、最近三段经历的一句摘要、正在等什么、find 的标题与摘要、礼物名、一句问候、主人托带的那句话。

**永远不允许**（出现在任何 payload 里都是阻断缺陷）：

| 不许 | 为什么 |
| --- | --- |
| 主人聊天原文 | `snapshot` 唯一的禁止项，也是 4.4 最容易破的地方 |
| 心愿原文 | 只许折算成**类目**过去（`interest_categories`），原文留在 `wish` 表 |
| 照片原图 | 回应里的 `photo_url` 只对 b 可见，不进 exchange |
| 主人的称呼、城市、任何身份信息 | `fromOwnerOf` 只填狗 id |
| `chat_summary` 这类「摘要」 | 摘要也是原文派生的，一样串味（api.md 明写不行） |
| 被 `blocked_topics` 命中的任何内容 | 屏蔽高于一切，被屏蔽的不进结果集，也不解释为什么 |

## 六、种子狗的边界（最容易做错的一处）

| 能做 | 不能做 |
| --- | --- |
| 被匹配到、和真狗交换（payload 来自预置数据） | 生成「主人的回应」 |
| 出现在 `relation` 里、`met_count` 正常累加 | 显示「刚刚活跃」「回复率」 |
| 作为收件方收礼物、收捎话 | 让 AI 代它写一句回复 |

**一句话区分**：**交换是狗的事，可以自动发生；回应是主人的事，种子狗没有主人。**

`is_sample = 1` 时四处标注由 e 负责（来信、交换记录、朋友圈、手账），d 只保证这 20 只的 `is_sample` 全是 1。

## 七、到达时机：按契约就是「跨一趟」，d 不需要额外动作

**先撤回一条。** 本文件初版曾建议 c「投递器在 `finish` 也跑一次」，理由是我以为 `deliver_after_trip_seq` 会等于**当前这次**的 seq，导致这趟遇到的朋友带不回来。重读 `api.md` 第 190 行后确认：**那个判断是错的，这条建议作废，c 不要改投递器。**

### 契约怎么算

`api.md` 原文：**「d 不自己算 `deliver_after_trip_seq`。d 说『寄给谁、寄什么』，c 查收件狗当前 seq 再加一。」**

所以：

```
A 第 n 次出行途中遇到 B
  ├─ A → B   c 查 B 的 seq（= m），写 m + 1   →  B 第 m+1 次出门时才到
  └─ B → A   c 查 A 的 seq（= n），写 n + 1   →  A 第 n+1 次出门时才到
```

**两边都是「下一次出门」，对称。** 这正是「跨一趟出行」的定义，不存在「条件满足了但没人投」——条件根本不可能在这次出行内满足。

### d 这边要守的两条

1. **不传 `deliver_after_trip_seq`。** 入参只有 `{ fromDog, toDog, kind, payload }`，这个字段由 c 算。d 再算一遍 = 两个口径。
2. **不写 `delivered_at`。** 那是 c 独占（api.md 列级拆分）。

### 如果真把投递器挪到 `finish` 会怎样

`deliver_after_trip_seq = n + 1`，而 `finish` 时当前 seq 仍是 n，`WHERE deliver_after_trip_seq <= n` **不会命中**——改了也白改。

更要紧的是别让它往反方向改：如果有人为了把「这趟带回来」做成真的，**把 `+1` 去掉**，交换就变成当场到达，不变量二（一切都不是即时的）当场破。这条要盯住，**换任何人提都不行**。

### 体验上怎么向 e 解释

「出门遇到朋友，回来两手空空」不是 bug，是节奏：**这趟给出去，下趟带回来。** 来信界面写「在路上」而不是「已送达」，就是这件事的界面表达。
