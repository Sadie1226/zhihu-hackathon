## 一、现在缺什么

`api.md` 第一节的「谁写谁读」表里有这一行：

```
| 事件池 | d | c |
```

`schema.sql` 里没有对应的表。十张是：`dog` `snapshot` `wish` `trip` `find` `exchange` `message` `invitation` `reply` `relation`。

事件也放不进 `find`：`find` 挂在 `trip_id` 上，是**已经发生的一次出行里的东西**；事件池是**还没发生、等着被抽中**的候选。两者的写入时机、生命周期、写入方都不一样，合表就会出现「find 有一半是空的候选」这种脏结构。

## 二、建议的表（你定，我只给需求）

```sql
-- ---------------------------------------------------------------------------
-- event · 事件池（3.3 偶然事件 / 4.4 季节与天气）
-- 写入方：d。只读：c（出行时抽签）。
-- ---------------------------------------------------------------------------
CREATE TABLE event (
  id            TEXT PRIMARY KEY,

  -- d 写。稳定标识，素材与文案都挂它。如 'summer_icecream'。
  code          TEXT NOT NULL UNIQUE,

  -- d 写。一句话，≤40 字。界面上直接显示。
  text          TEXT NOT NULL CHECK (length(trim(text)) BETWEEN 1 AND 40),

  -- d 写。季节。any = 不限。
  season        TEXT NOT NULL CHECK (season IN ('spring','summer','autumn','winter','any')),

  -- d 写。天气。any = 不限。
  weather       TEXT NOT NULL CHECK (weather IN ('any','clear','rain','snow')),

  -- d 写。时段。any = 不限。
  time_of_day   TEXT NOT NULL CHECK (time_of_day IN ('any','morning','dusk','night')),

  -- d 写。需要的地形/道具标签。**e2c 没有这个素材，这条就不许出。**
  -- 形状：["street","stall","riverside","bookstore"]，可为 '[]'（任何场景都成立）。
  place_tags    TEXT NOT NULL DEFAULT '[]'
                CHECK (json_valid(place_tags) AND json_type(place_tags) = 'array'),

  -- d 写。命中的狗兴趣类目，可为 '[]'（与兴趣无关）。
  match_tags    TEXT NOT NULL DEFAULT '[]'
                CHECK (json_valid(match_tags) AND json_type(match_tags) = 'array'),

  -- d 写。基础权重。越大越常见。
  weight        INTEGER NOT NULL DEFAULT 30 CHECK (weight > 0),

  -- d 写。同一只狗多少天内不重复。默认 7。
  cooldown_days INTEGER NOT NULL DEFAULT 7 CHECK (cooldown_days >= 0),

  -- d 写。渲染要用到的素材引用，c11c 场景合成器读。
  -- 形状：{"scene":"street_02","prop":"icecream_stand","face":"hopeful"}
  asset_refs    TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(asset_refs)),

  enabled       INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0,1)),

  created_at    TEXT NOT NULL
);

CREATE INDEX idx_event_season ON event(season, weather, time_of_day, enabled);
```

`types.ts` 里对应加一个 `Event` 接口和两个枚举（`Season` / `EventWeather`），跟现有六个枚举同一个写法。

## 三、为什么这几个字段

| 字段 | 不加会怎样 |
| --- | --- |
| `season` | 冬天出冰淇淋。a 的验收原话是「夏天必出冰淇淋但不每次出」，没有季节这一列就做不到「必出」 |
| `weather` / `time_of_day` | 晴天写「雨里站了很久」，一眼假 |
| `place_tags` | 抽到「冰淇淋摊」但这次出行没有摊位素材，c11c 拼不出来，只能硬塞或丢弃 |
| `match_tags` | 兴趣命中就出不去手（一只爱植物的狗从没遇到植物相关的事） |
| `weight` + `cooldown_days` | 两条验收都靠它们：**夏天必出但不每次出**（权重）、**同事件不连续重复**（冷却） |

## 四、c 抽签时的查询（照这个写，d 那边不再实现一遍）

```sql
-- 输入：当前 trip 的上下文（季节/天气/时段/可用素材）、这只狗近 N 天出过的事件
SELECT * FROM event
 WHERE enabled = 1
   AND season  IN (:season, 'any')
   AND weather IN (:weather, 'any')
   AND time_of_day IN (:timeOfDay, 'any')
   AND NOT EXISTS (
     SELECT 1 FROM trip_event te          -- ← 见下，这张表也要有
      WHERE te.dog_id = :dogId
        AND te.event_id = event.id
        AND julianday(:now) - julianday(te.happened_at) < event.cooldown_days
   )
 ORDER BY (-ln(1 - abs(random()) / 9223372036854775807.0) / weight) ASC
 LIMIT 1;
```

上面那句是按权重抽签的标准写法（`ORDER BY -ln(U)/weight`），不是我要你照抄——**SQLite 没有 `random()` 的归一化，你选一种可靠的加权随机即可**，只要满足「`weight` 大的更容易出现」。

### 还需要一张记录表，否则冷却做不到

「同一只狗 7 天内不重复同一个事件」必须记下「哪只狗在哪次出行遇到了哪个事件」。建议：

```sql
CREATE TABLE trip_event (
  trip_id     TEXT NOT NULL REFERENCES trip(id),
  event_id    TEXT NOT NULL REFERENCES event(id),
  dog_id      TEXT NOT NULL REFERENCES dog(id),
  happened_at TEXT NOT NULL,
  PRIMARY KEY (trip_id, event_id)
);
CREATE INDEX idx_trip_event_dog ON trip_event(dog_id, happened_at);
```

写入方 **c**（它是唯一知道「这次出行发生了什么」的人），d 只读。
