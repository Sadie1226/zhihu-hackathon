### ① `fixtures/exchange.json` 的 payload 里没有 `kind`

| 来源 | payload 长什么样 |

| `fixtures/exchange.json` | `"kind": "gift"` 在外层，`payload: { "giftName": ..., "note": ... }` ← **不带** |

**影响（直接卡明天）**：`rules.ts` 按 `types.ts` 的判别联合（discriminated union）写，第一条判断就是 `payload.kind`。拿 fixture 当测试数据，**4 条全部报「缺 kind」**，10 个用例一个都跑不起来。改代码没用——是数据错。

**要求**：c 把 `fixtures/exchange.json` 四条 payload 各补一个 `kind` 字段。**只加不删，`schema.sql` 和 `types.ts` 不用动。**

### ② `snake_case` 与 `camelCase` 之间那层映射，没人认领

| 概念 | `schema.sql` / `fixtures` | `types.ts` / `api.md` |

| 性格标签 | `personality_tags` | `personalityTags` |
| 是否种子狗 | `is_sample` = `0`/`1` | `isSample` = `false`/`true` |
| 是否拉黑 | `is_blocked` = `0`/`1` | `isBlocked` = `false`/`true` |

**这是刻意设计**（数据库行 vs JSON 对象），不是错误。但**没有人写过这层转换归谁**，于是有三种可能，必须选一种：

| 方案 | 谁做映射 | 代价 |
| --- | --- | --- |
| A（我建议） | **d 的 `rules.ts` 只吃 camelCase**；fixture 读进来先过一层 `fromDbRow()`，`0/1` 转 `false/true` | d 多写 30 行映射；好处是校验逻辑和 API 入参同形，`POST /api/exchanges` 的 body 可以直接喂给校验器 |
| B | c 的接口层做映射，d 的校验器只认得 camelCase，测试数据由 c 提供转换后版本 | d 省事，但 d 的测试数据不再是「真实的库行」 |
| C | d 全都用 snake_case，接口层再转 | **不要**——`api.md` 入参是 camelCase，等于 d 在每个调用点手写一次转换 |

**要求 c 确认选 A**。不确认的话我按 A 写，并在 `rules.ts` 顶部注明「camelCase 是唯一入口」。

### ③ payload 里没有出处字段，但「礼物必须有出处」是 d 自己写的验收项

d1 第 31 行、d3 第 28 行都写了：**`giftName` 必须能在这趟的 `find.title` 或事件池里找到对应，找不到就不许寄。**

问题：`gift` 的 payload 是 `{ giftName, note }`，`find` 的 payload 是 `{ findTitle, findExcerpt, sourceUrl }`——**两边都没有 `id`**。

后果：
- 想验证「这卷毛线来自哪条 find」，只能拿中文标题做字符串比对。标题改一个字就断，且无法区分两条同名 find
- 这条验收**现在无法自动执行**，只能靠肉眼。而 11-20 的 d4 要求「假记录跑通全流程」，验收过不去

**要求 c 在 payload 里加一个可空字段**：

```jsonc
{ "kind": "find", "findTitle": "...", "findExcerpt": ..., "sourceUrl": ...,
  "sourceFindId": "find_seed1" }   // ← 新增，可空

{ "kind": "gift", "giftName": "...", "note": ...,
  "sourceFindId": "find_seed1" }   // ← 新增，可空
```

**为什么必须可空**：`greeting` 不需要出处；`find` 本身是「第一次把这条发现给人看」，它可能就来自这趟的 find 表，也可能来自更早的行程摘要，所以不能强制。

**这是加字段，我只能申请，不能自己加**（红线 5）。如果 c 拒绝，那我就得把 d1/d3 里「出处是硬的」这条降级成「建议」，并在验收表里改成人工核对——**这会掉分，所以请优先考虑加。**

### ④ `snapshot.interest_categories` 是 `NOT NULL`，但 `dog.interest_categories` 允许 `NULL`

| 表 | 约束 | 行号 |
| --- | --- | --- |
| `dog` | `interest_categories` 可 NULL（**NULL = 全都要**） | `schema.sql:64-66` |
| `snapshot` | `interest_categories` **NOT NULL**，且必须 2–3 个 | `schema.sql:136-138` |

**影响**：一只狗如果领养时没选类目（合法，代表「全都要」），它的快照**写不进去**。11-23 给 20 只种子狗造快照时必撞。

**两个解法，要 c 选一个**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 快照允许 NULL，语义同 `dog`（全都要） | 改 `schema.sql` 一行；e 读的时候要处理 null |
| B | d 写入时把 NULL 展开成全 6 个类目 | 不动契约；但「全都要」在快照里变成「恰好都要这 6 个」，语义漂了一点 |

我倾向 **A**（语义准），但 B 不动契约、今天就能落地。**c 拍。**
