## 一、池子只有一个，不做第二套

a 给的来源是三档（队员养的狗 / 其他参赛者的狗 / 预置种子狗），但**实现上只有一个池子：`dog` 表**。

种子狗就是 `dog` 表里 `session_id = 'seed'`、`is_sample = 1` 的 20 行。理由：

- 匹配函数只有一段代码，不分「真狗路径」和「种子路径」。分两套就一定有一边先腐坏。
- a 的第 5 步「候选为空 → 落到预置 20 只」自动成立：种子狗本来就在候选里，永远不会空集。
- 排除同 session 时，`'seed'` 和任何真实 session 都不相等，所以真狗之间不会互撞，真狗和种子狗正常相遇。

**唯一要守的**：种子狗的 `session_id` 必须正好是 `'seed'`，且 20 行 `is_sample` 全是 1。

## 二、匹配函数（a 的五步 → 五处代码）

| a 的第几步 | 落在哪 | 对应字段 |
| --- | --- | --- |
| 1 排除自己、同 session、已拉黑 | `WHERE d.id <> me.id AND d.session_id <> me.session_id AND NOT EXISTS(拉黑)` | `dog.id` / `dog.session_id` / `relation.is_blocked` |
| 2 优先没交换过 | 先只在 `relation` 里不存在的对里取 | `relation` |
| 3 标签有交集的桶内真随机 | `overlap >= 1` + `ORDER BY RANDOM() LIMIT 1` | `dog.personality_tags` |
| 4 一次只遇一只 | `LIMIT 1` | — |
| 5 候选为空 → 种子狗 | 天然成立，见第一节 | `is_sample` |

### 主查询（SQLite，可直接跑）

```sql
-- :me = 当前狗 id。返回 0 或 1 行。
WITH me AS (
  SELECT id, session_id, personality_tags FROM dog WHERE id = :me
),
cand AS (
  SELECT d.*
  FROM dog d, me
  WHERE d.id <> me.id
    AND d.session_id <> me.session_id
    AND NOT EXISTS (
      SELECT 1 FROM relation r
      WHERE r.is_blocked = 1
        AND ((r.dog_a = me.id AND r.dog_b = d.id)
          OR (r.dog_a = d.id AND r.dog_b = me.id))
    )
),
fresh AS (
  SELECT c.* FROM cand c, me
  WHERE NOT EXISTS (
    SELECT 1 FROM relation r
    WHERE (r.dog_a = me.id AND r.dog_b = c.id)
       OR (r.dog_a = c.id AND r.dog_b = me.id)
  )
)
SELECT id, is_sample FROM (
  SELECT f.id, f.is_sample,
         (SELECT COUNT(*) FROM json_each(f.personality_tags) jt
           WHERE jt.value IN
                 (SELECT value FROM json_each((SELECT personality_tags FROM me)))
         ) AS overlap
  FROM fresh f
)
WHERE overlap >= 1
ORDER BY RANDOM()
LIMIT 1;
```

**返回 0 行怎么办**（全池都遇过了，或标签全不重合）：把 `fresh` 换成 `cand`，再跑一次同样的 `SELECT`。**只退这一步，不许退到「不再排除已拉黑」**——拉黑是硬的，不能为了凑一个结果破它。

### 两个「不许」

```sql
-- 错：按 id 取第一个。同一批用户每次遇到的都是同一只，演示一眼看出来
ORDER BY id LIMIT 1

-- 错：按 overlap 排序取最大。那就是 a 明说不做的「最相似」
ORDER BY overlap DESC LIMIT 1
```

`ORDER BY RANDOM()` 是硬要求，不是风格问题。

### 相遇后写关系（两条 exchange 之外的那一笔）

```sql
-- :id 用 uuid；字典序小的放 dog_a（schema 有 CHECK dog_a < dog_b）
INSERT INTO relation (id, dog_a, dog_b, first_met_at, last_met_at, met_count, is_blocked, blocked_at)
VALUES (:id, MIN(:dogA, :dogB), MAX(:dogA, :dogB), :now, :now, 1, 0, NULL)
ON CONFLICT(dog_a, dog_b) DO UPDATE SET
  met_count   = met_count + 1,
  last_met_at = excluded.last_met_at;
```

`uniq_relation_pair(dog_a, dog_b)` 是这个 upsert 的前提，已有的索引正好够用，**不需要 c 加东西**。

### 禁止相撞的三种情况（写进测试）

| 情况 | 期望 |
| --- | --- |
| 同一个 `session_id` 养了两只狗 | 两只永远不互相遇 |
| 一对关系 `is_blocked = 1` | 双向都不进候选（`dog_a`/`dog_b` 两个方向都查） |
| 已经遇过一次的一对 | 不进 `fresh`，只在整个池子都遇过之后才可能再遇 |

## 三、`blocked_topics` 放在哪一步

匹配阶段**不按 `blocked_topics` 排除**——它是内容过滤器，不是关系过滤器，两只狗本身没有「被屏蔽」这回事。

正确位置：**挑 payload 之前**。挑出来的 find / gift / greeting 先过两句狗的 `blocked_topics`，命中就换下一条；全命中就退成一句中性 greeting，不带任何内容。

被屏蔽的东西**不进结果集、不算错误、界面上什么都不显示、不解释为什么**（api.md 第五节）。

## 六、`snapshot` 什么时候写

匹配到对方后，`GET /api/dogs/:id/neighbor` 要返回 `{ dog, snapshot }`（api.md 第八组）。所以**每只种子狗要预先有一份 `snapshot`**，否则第一次相遇就是空的。

种子的 `snapshot` 内容规则：

| 字段 | 种子狗怎么写 |
| --- | --- |
| `personality_tags` | 与 `dog` 一致 |
| `interest_categories` | 与 `dog` 一致 |
| `recent_trips` | **2–3 条一句话摘要**，从种子狗的性格出发写，不写「示例」二字（标注由 `is_sample` 在界面做，不写进内容里） |
| `waiting_for` | 一句话，或 `NULL`。**写了就必须真的在等一件事**，否则又是编 |

`recent_trips` 的 20 组摘要在 d5（11-23）出，和「5 只有真实经历的狗」一起交。今天只交这 20 只的身份与装配。
