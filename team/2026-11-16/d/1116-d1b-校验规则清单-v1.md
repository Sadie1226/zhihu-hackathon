>
> 一件事先说清：**这份表里所有数字区间都是 d 暂定的，契约没有规定 payload 的长度。** 标了 `【暂定】` 的行，如果 a 或 e 觉得不合适可以改，改一处就够。

## 零、这个校验器管什么、不管什么

| 管 | 不管 |
| --- | --- |
| 一条 `exchange` 草稿的**形状**对不对 | 数据库能不能插（`CHECK` 会拦，不用重复） |
| `payload` 的键集合是否**恰好等于**契约允许的 | 内容好不好、像不像狗说的话（那是 a/b） |
| `d` 有没有越权写别人的列 | `deliver_after_trip_seq` 该是多少（c 算） |
| 内容层红线（键名黑名单、`blocked_topics` 命中） | 「主人聊天原文」这种语义判断（做不了，靠结构堵） |

**核心设计：白名单靠「键集合严格相等」实现，不靠关键词匹配。**

`payload` 只允许契约里那几个键，**多一个键就拒**。这样「塞一段主人聊天原文进去」就没有地方放 —— 这比写一堆正则去猜「这句话像不像聊天记录」可靠得多。

## 一、输入与输出

### 输入：`ExchangeDraft`

```ts
interface ExchangeDraft {
  fromDog: string
  toDog: string
  kind: ExchangeKind
  payload: unknown          // 故意用 unknown，进来先验形状
}
```

**只有这四个键。** 出现 `id` / `deliverAfterTripSeq` / `deliveredAt` / `repliedAt` / `readAt` 中的任何一个 → **直接拒绝**（见第四节「越权字段」）。

### 输出

```ts
type Verdict =
  | { ok: true; value: NormalizedExchange }
  | { ok: false; code: RuleCode; path: string; reason: string }
```

- `path` 用 JSON Pointer 风格：`/payload/giftName`，方便定位
- `rule.ts` **不返回 HTTP 错误码**。`errors.md` 那七个码里没有「参数格式错」，硬套 `CONFLICT` 会误导前端。**接口层自己映射**，本层只给结构化的 `code`

### `RuleCode` 枚举（九个，够用即可）

| code | 含义 |
| --- | --- |
| `MISSING_FIELD` | 必填键不在 |
| `UNKNOWN_KEY` | 出现了契约外的键（**白名单主防线**） |
| `WRONG_TYPE` | 类型不对 |
| `EMPTY_STRING` | 必填字符串是空串或全空白 |
| `TOO_LONG` / `TOO_SHORT` | 超区间 |
| `BAD_KIND` | `kind` 不在四值里，或 `payload.kind` 与 `kind` 不一致 |
| `SELF_EXCHANGE` | `fromDog === toDog` |
| `FORBIDDEN_KEY` | 命中内容层黑名单键名（`chatSummary` 等） |
| `BLOCKED_TOPIC` | 命中 `blockedTopics` |

## 二、校验顺序（fail fast，撞到第一条就返回）

顺序不是随便排的 —— **便宜的检查在前，需要外部数据的在后**。

| 层 | 检查 | 为什么放这个位置 |
| --- | --- | --- |
| 1 | 顶层键集合 ⊆ `{fromDog,toDog,kind,payload}` | 先挡越权字段，后面就不用防了 |
| 2 | 四个键齐全 + 类型 | 不齐全就不用往下看 |
| 3 | `kind` ∈ 四值 | 后面按 kind 分支，必须先确定 |
| 4 | `fromDog !== toDog` | 一行判断，DB 也会拦，但先给好错误 |
| 5 | `payload` 是纯对象（非 null、非数组） | 后面的键集合检查依赖这个 |
| 6 | **`payload.kind === kind`** | 见下节，这条最容易漏 |
| 7 | 按 kind 校验 payload 键集合 + 逐字段 | 主体 |
| 8 | 内容层黑名单键名 | 键集合已经收窄，扫一遍很便宜 |
| 9 | `blockedTopics` 命中（**可选**，不传就跳过） | 需要外部数据，放最后 |

## 三、`payload.kind` 与 `kind` 的一致性 —— 这条必须显式写

契约三处（`types.ts:220`、`api.md` 第三节、d1 十例）都把 `kind` 放在 payload 里，形成判别联合。但 **`fixtures/exchange.json` 的 payload 里没有 `kind`**（已报 c，见 `d0b` A3）。

所以校验器分两步：

1. 进 `normalize()` 时，若 `payload.kind` 缺失而外层有 `kind` → **补进去**（兼容 fixture）
2. 进 `validate()` 时，**`payload.kind` 与外层 `kind` 必须相等**，不等就报 `BAD_KIND`

**为什么不能省第 2 步**：补进 payload 的动作只解决「缺」；如果两边都有但不一样（`kind: 'gift'` 配 `payload.kind: 'find'`），说明上游已经错了，必须拒，不能选一个当真。

## 四、越权字段（`d` 只许写六列）

`api.md` 列级拆分：`d` 写 `id / from_dog / to_dog / kind / payload / deliver_after_trip_seq / created_at`。

但**这一层只接四个**：`deliver_after_trip_seq` 由 c 算（`api.md:193`），`created_at` 和 `id` 由调用方/写入层生成。

| 键 | 出现时 |
| --- | --- |
| `deliverAfterTripSeq` / `deliver_after_trip_seq` | **拒**，`FORBIDDEN_KEY`，理由「由 c 算，d 不许传」 |
| `deliveredAt` / `delivered_at` | **拒**，理由「c 独占」 |
| `repliedAt` / `replied_at` | **拒**，理由「b 独占」 |
| `readAt` / `read_at` | **拒**，理由「e 独占」 |
| `id` | **拒**，理由「写入层生成」 |
| `createdAt` / `created_at` | 允许，但**不进 payload 校验**，透传 |

对比词里带不带下划线都要拦 —— 上游可能给 snake_case。

## 五、四种 kind 的字段表

`必填` 指键必须在；`可空` 指值可以是 `null`。**「可空」不等于「可以没有这个键」** —— 键必须在，值可以 null。这是契约里最容易误解的一处。

### 5.1 `find`

| 字段 | 类型 | 键 | 值 | 区间 |
| --- | --- | --- | --- | --- |
| `kind` | `'find'` | 必填 | 非空 | — |
| `findTitle` | string | 必填 | 非空 | 1–30 `【暂定】` |
| `findExcerpt` | string \| null | 必填 | 可 null | ≤ 120 `【暂定】` |
| `sourceUrl` | string \| null | 必填 | 可 null | 非 null 时必须 `https://www.zhihu.com/` 开头 |
| `sourceMode` | `'live'\|'cache'\|'fixture'` | **待 c 批**（`d0b` B1） | 非空 | — |
| `sourceFindId` | string \| null | **待 c 批** | 可 null | — |

**额外规则**：
- `sourceUrl` 非 null 时 `sourceMode` 必须非 null（`schema.sql:find` 的 CHECK 是同一逻辑，但这里给出可读错误）
- `sourceMode: 'live'` 时 `sourceUrl` 不能为 null —— 没链接的「知乎内容」不可能是 live

### 5.2 `greeting`

| 字段 | 类型 | 键 | 值 | 区间 |
| --- | --- | --- | --- | --- |
| `kind` | `'greeting'` | 必填 | 非空 | — |
| `line` | string | 必填 | 非空 | 1–40 `【暂定】` |
| `weather` | string \| null | 必填 | 可 null | 非 null 时 1–4 字 `【暂定】` |

**没有 `sourceMode`** —— 问候是狗自己生成的话，不属于「知乎内容是否新鲜」那一套。别顺手给它加。

### 5.3 `gift`

| 字段 | 类型 | 键 | 值 | 区间 |
| --- | --- | --- | --- | --- |
| `kind` | `'gift'` | 必填 | 非空 | — |
| `giftName` | string | 必填 | 非空 | 1–20 `【暂定】` |
| `note` | string \| null | 必填 | 可 null | ≤ 40 `【暂定】` |
| `sourceFindId` | string \| null | **待 c 批** | 可 null | — |

**`note: null` 必须合法**（d1 第八节验收第 5 条专门数这个）。不许因为 `note` 空就要求补一句 —— 空着是对的。

### 5.4 `co_owner_message`

| 字段 | 类型 | 键 | 值 | 区间 |
| --- | --- | --- | --- | --- |
| `kind` | `'co_owner_message'` | 必填 | 非空 | — |
| `message` | string | 必填 | 非空 | 1–60 `【暂定】` |
| `fromOwnerOf` | string | 必填 | 非空 | **必须是狗 id，不许是人名** |

**`fromOwnerOf` 的判定**：它必须能在 `dog` 表里查到（或至少符合 `dog.id` 的形状）。**不许是「豆子的主人」「小林」这种**。

自动判定只能做到「看起来像 id」：允许的字符集 `[A-Za-z0-9_-]`、长度 2–64、不含空白与中文。**含中文一律拒** —— 名字一定是中文，狗 id 一定不是。

这条检查很土，但它拦得住最容易犯的那个错。

## 六、内容层黑名单（键名，不看值）

`payload` 的键集合在上一步已经收窄成「契约允许的那几个」。**这一步针对的是有人偷偷加键**。虽然第 7 步的键集合严格相等已经能拦住，但错误信息要说得清楚，所以单独扫一遍。

**一律拒的键名**（大小写与下划线不敏感）：

```
chatSummary / chat_summary / chatLog / chat_log / conversation / dialogue
photoUrl / photo_url / photo / image / imageUrl / image_url / avatar
address / city / location / hometown
ownerName / owner_name / realName / real_name / userName / user_name
wishText / wish_text / wish
blockedTopics / blocked_topics
llmRaw / llm_raw / raw / debug / trace
```

**理由**：前四个对应 d1 第五节的禁止项（主人聊天原文、照片、身份信息、`chat_summary` 类摘要）。`raw`/`debug`/`trace` 那类是因为**调试字段会把模型输出原样带过去**，里面可能有任何东西。

## 七、`blockedTopics` 命中（可选参数）

`errors.md` 禁区二：`blocked_topics` 的过滤优先级高于一切，**d 的交换内容也要过**。

```ts
function validate(draft, opts?: { blockedTopics?: string[]; now?: string })
```

**不传 `blockedTopics` 就跳过这层**（函数保持纯，测试可以不带）。

判定方式：把 payload 里所有字符串值拼起来，做**小写包含匹配**。命中任一 → `BLOCKED_TOPIC`。

**这不是「合规审核」，只是「我这只狗明确不想碰的话题」**。命中后不解释、不显示（`errors.md` 的 `BLOCKED` 语义）。

**已知局限，写在这里免得以后被当 bug**：子串匹配会误伤（屏蔽「雪」，那「下雪了」也进不去）。这是故意的 —— 宁可少说一句，不许踩禁区二。

## 八、`normalize()` —— 上游数据的入口

```ts
function normalize(raw: unknown): ExchangeDraft
```

它做四件事，**全部只做形状转换，不做校验**：

| 做什么 | 为什么 |
| --- | --- |
| snake_case → camelCase（`from_dog` → `fromDog` 等） | fixture 和 DB 行是 snake_case（`d0b` B2） |
| `0/1` → `false/true`（`is_sample`、`is_blocked` 这类，若出现） | DB 用整数，类型用布尔 |
| 外层 `kind` 补进 `payload`（若 `payload.kind` 缺失） | 兼容当前 fixture（`d0b` A3） |
| 不认识的键**保留**，交给 `validate()` 去拒 | normalize 不替校验做决定 |

**这两步要分开的原因**：`normalize` 的偏差是「可以容忍的输入形态差异」，`validate` 的拒绝是「真的不合规」。混在一起，以后 c 改了 fixture，你分不清是哪一层在报警。

## 十、不做什么（防止写着写着越界）

| 不做 | 理由 |
| --- | --- |
| 不查数据库 | 校验器是纯函数，好测、能并行、换存储不用改 |
| 不算 `deliver_after_trip_seq` | `api.md:193`，c 算。d 再算一遍就是两个口径 |
| 不判断内容好不好、像不像狗说话 | 那是 a 和 b 的活 |
| 不做「主人聊天原文」的语义识别 | 做不了。靠结构堵，已经在第八节说明 |

| 不顺手写 `delivered_at` / `replied_at` / `read_at` | 列级拆分，越权 |

## 十一、`【暂定】`的那些数字，依据是什么

不是拍脑袋，是照现有数据的实际长度留了余量：

| 字段 | 现有最长 | 暂定上限 | 余量 |
| --- | --- | --- | --- |
| `findTitle` | 12 字（"北京初雪一般落在什么时候"） | 30 | 2.5× |
| `findExcerpt` | 45 字（`fixtures/find.json` 的 `find_z1`） | 120 | 2.6× |
| `line` | 19 字（"这边下了两天雨，路上全是水，你那边呢。"） | 40 | 2.1× |
| `giftName` | 9 字（"一小卷灰蓝色的毛线"） | 20 | 2.2× |
| `note` | 5 字（"天气要冷了"） | 40 | 8× |
| `message` | 20 字（"下次路过那家书店，帮我看看有没有植物图鉴"） | 60 | 3× |

**计数方式照 `types.ts` 的 `countChars()`：只去掉空白，标点算一个字。** 不按汉字数、不按词数。

`note` 的余量给到 8× 是故意的 —— 它是可空的，卡太紧会逼着人硬编。

## 十二、给写代码的人一句话

先让 `normalize()` 把 fixture 的形状差异吃掉，再让 `validate()` 只认一种形状。

**跑绿的标准不是「10 个用例过了」，是「16 号反例被拒，且理由是 `UNKNOWN_KEY` 而不是 `FORBIDDEN_KEY`」。** 前者说明白名单结构生效了，后者说明你在靠关键词猜 —— 猜是会漏的。
