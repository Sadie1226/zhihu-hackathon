# B 档 · 卡 11-20 到 11-23

## B1 · 申请给 payload 加字段，其中 `sourceMode` 我认为是必须的

**现状**：`find` 的 payload 是 `{ findTitle, findExcerpt, sourceUrl }` —— **没有 `sourceMode`**。

**为什么这是硬伤**：一条 find 从 A 传到 B，再传到 C，任何一环都看不出它到底是 `live`、`cache` 还是 `fixture`。

- e 的界面没法标「示例内容」
- 这是**不变量四**，也是**五种阻断缺陷第 4 条**（伪造真实用户内容）
- `find` 表里存了 `source_mode`，但没进 payload —— 跨狗传递时就丢了

**申请的形状**：

```jsonc
// find 的 payload
{ "kind": "find", "findTitle": "...", "findExcerpt": ..., "sourceUrl": ...,
  "sourceMode": "live" | "cache" | "fixture",     // 必填
  "sourceFindId": "find_z1",                      // 可空，出处
  "authorityLevel": 1 | 2 | 3 | 4 | null,         // 可空，e 要不要显示你定
  "voteUpCount": 0 }                              // 可空，同上

// gift 的 payload
{ "kind": "gift", "giftName": "...", "note": ...,
  "sourceMode": "live" | "cache" | "fixture",     // 可空
  "sourceFindId": "find_z1" }                     // 可空，出处
```

**`sourceFindId` 为什么需要**：d1 和 d3 都写了「`giftName` 必须能在这趟的 `find` 里找到出处，找不到不许寄」，这是我给自己写的验收项。但现在两边 payload 都没有 id，只能拿中文标题做字符串比 —— 改一个字就断，两条同名 find 也分不出来。这条验收现在只能人眼核。

**后两个（`authorityLevel`/`voteUpCount`）不确定要不要**：`find` 表里存了，payload 没带。如果 e 要显示「赞数」「来源权威度」，就得带；不显示就不用。

**这是加字段，按禁区三我只能申请。**

**不答我能先做什么**：`rules.ts` 先不验 `sourceMode`，把它当可选字段；等批了再加一条必填校验。
