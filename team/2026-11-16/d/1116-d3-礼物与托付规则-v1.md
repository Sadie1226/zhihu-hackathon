# d3 · 礼物与托付规则

> 出 d，2026-11-16。对应 01 的 **4.4 礼物与托付**，P0 第 8 条（延后礼物）与第 9 条（捎话）。
> 字段与接口以 `contracts/` 为准。本文只回答三个问题：**什么能寄、多久到、不回怎么办**——外加一条 e 做界面必须有答案的：**入口从哪儿进**。
>
> 用法：**e** 拿第二节和第六节做来信页与捎话入口；**c** 拿第三节核对 `deliver_after_trip_seq` 的算法；**b** 拿第五节核对「回应」的边界；**a** 拿第八节验收。

---

## 一、一句话

**狗在路上得到的东西，可以捎给另一只狗；到了之后就在那里等着，等到什么时候都行，也可以永远不等。**

礼物与捎话都走 `exchange` 一张表，只是 `kind` 不同（`gift` / `co_owner_message`）。**投递机制是 c 的，业务内容是 d 的。**

---

## 二、什么能寄（以及入口从哪进）

### 狗寄给狗的：`gift`

| 能寄 | 不能寄 |
| --- | --- |
| 它这趟在某条 find 或某个事件里**真碰到**的东西：一小卷毛线、一块被水冲圆的石头、一张旧明信片 | 凭空生成的东西（模型现编一件礼物 = 踩不变量四） |
| 沿途捡的、摊上换的、别人给的 | 车票、钥匙、主人自己的物品 |
| 一个东西 + 一句 `note`（可空） | 食物（会坏，狗的设定里没有冰箱） |

**出处是硬的**：`giftName` 必须能在这趟的 `find.title` 或事件池里找到对应。找不到就不许寄，宁可不寄。

### 主人寄给对面主人的：`co_owner_message`（捎话）

**入口只能从「已经认识的那只狗」进**，不存在「我要给某某捎句话」这种入口。

```
错：一个输入框 + 一个收件人选择器        ← 这就是人直接操作人（不变量一），当场违规
对：来信里某只狗的那条记录旁边，一个入口「写句话让它带回去」
```

为什么必须这样：

- `exchange.to_dog` 是必填，没有「收件人还没定」这种状态。要允许先写后选，就得给「未投出的话」找个暂存表——**d 不许自己建表**，而且那等于给「人指定另一只狗」开后门。
- 从已发生的关系进入，`to_dog` 天生确定，契约零改动，一个人永远碰不到另一个人。

**所以 e6 的捎话入口挂在这三个地方，不在全局导航里**：来信里狗的记录旁、交换记录下方、手账里回看这段关系时。三处都是「已经见过这只狗」的语境。

### 两种东西的边界

| | 礼物 `gift` | 捎话 `co_owner_message` |
| --- | --- | --- |
| 谁写的 | 狗自己 | 主人写，狗带 |
| payload | `giftName` + `note` | `message` + `fromOwnerOf` |
| 长度 | `giftName` ≤ 20 字，`note` ≤ 40 字 | `message` ≤ 200 字 |
| 有回应 | 可以（b 的回应能力） | 可以（对面主人在来信里回） |
| 对方是种子狗 | 能收，不会回 | 能收，**永远不会回** |

## 三、多久到：不是「明天到」，是「它下次出门带回来」

### 算法（d 不自己算）

```
发送那一刻： deliver_after_trip_seq = 收件狗当前 seq + 1
谁算：       c（POST /api/exchanges 里算）
d 写什么：   只写 fromDog / toDog / kind / payload / createdAt
```

**d 绝不写 `deliver_after_trip_seq`，也绝不写 `delivered_at`。** 前者归 c 算，后者归 c 的投递器独占。

### 判到达（唯一写法，别自己写 `now >`）

```ts
isDeliverable(deliverAfterTripSeq, recipientTrips)   // contracts/types.ts
```

```sql
exists (select 1 from trip
         where dog_id = exchange.to_dog
           and started_at is not null
           and seq >= exchange.deliver_after_trip_seq)
```

**写成时间戳比较，演示时延后礼物永远不会到。** 时间拨盘拨的是出行次数，不碰时钟。

### 等待期间界面什么都不说

| 位置 | 在路上时显示 |
| --- | --- |
| 寄件方 | 什么都不显示（不是「已寄出」、不是「等待中」） |
| 收件方 | 什么都不显示（不是「有一件在路上」） |
| 来信页 | 只有已到的才出现在列表里 |

理由：不变量二要求「有一段在等」，但那段等待**不是给人看的进度条**。给寄件方看「对方还没收到」，就变成了社交压力。等这件事自己发生，不用宣布。

**唯一例外**：e 的来信页可以有「在路上」这个分区（api.md 的 `filter=onTheWay`），但那分区里的记录**不显示寄件狗名字**，只显示「有东西在路上」。原因见下一节。

## 四、不回怎么办：什么都不做，而且永远不做

这是 4.4 最容易被做成打卡的地方，逐条钉死：

| 不许 | 为什么 |
| --- | --- |
| 红点、未读数、角标 | 不变量三 |
| 「它还在等你的回应」「已经 3 天」 | 同上 |
| 「已读未回」状态 | 回应不是义务，已读不等于欠一句 |
| 任何按「未回应天数」的排序 | 同上 |
| 30 天后把礼物移走或折叠 | 移走等于催，「它不再等你了」比催更伤人 |

**`replied_at` 永远是 `NULL` 是正常终态。** 手账能翻到这段关系，礼物就一直在那儿。第 100 天也一样。

**回应的次数**：一件东西只能被回应一次（`uniq_reply_exchange` 兜着，2026-11-15 由 a 实测补上）。重复提交返回 `CONFLICT`，前端当成功处理。

**谁写 `replied_at`**：只有 b。d 只读。**d 绝不在投递器或交换写入里顺手写 `replied_at`**——那会出现「礼物到了但显示已回应」的错状态。

## 五、在途上限与幂等（d 的写入端自己守）

### 在途上限：每只狗作为收件方，在途 ≤ 3

```sql
SELECT COUNT(*) FROM exchange
 WHERE to_dog = :toDog AND delivered_at IS NULL AND kind IN ('gift', 'co_owner_message')
```

超过 3 就不新建，返回 `CONFLICT`。**这是 d 的写入端拦截，不改表、不加约束**——上限是个产品手感，不是数据完整性。

为什么是 3：一只狗同时在等三件东西已经到了「有点热闹」的边上。再多就不是偶尔捎东西，是快递站。

### 幂等：id 由 d 生成

`exchange.id` 是 d 生成的 uuid。**同一个 id 插第二次必然 PK 冲突，返回成功即可**（幂等），不要报错给用户。连点两次只到一份，靠主键，不靠前端 disable。

### 发不出去的时候

| 情况 | 返回 | 界面 |
| --- | --- | --- |
| 在途已满 3 件 | `CONFLICT` | 「等它这趟回来再说」——不催、不解释规则 |
| 对方被拉黑（`relation.is_blocked = 1`） | `BLOCKED` | **什么都不显示**（api.md：被屏蔽的不解释） |
| 内容命中任一方 `blocked_topics` | `BLOCKED` | 同上 |
| 网络失败 | `NETWORK` | 「没发出去，可以再试一次」 |

## 六、四态映射（e 直接用这张表，别自己再推一遍）

| 界面状态 | 判定 | 界面表现 |
| --- | --- | --- |
| 在路上 | `delivered_at IS NULL` | 只在「在路上」分区，不显示寄件狗名字 |
| 新到 | `delivered_at` 非空 且 `read_at IS NULL` 且 `replied_at IS NULL` | 正常一条，有回应入口 |
| 待回应 | 已读、未回应 | **与新到无视觉差异**，不许加「待办」标记 |
| 已回应 | `replied_at` 非空 | 能看出它记下了，不是「发送成功」四个字 |

**`replied_at` 也算已读**（a 已裁定）：回应过一件东西必然是看过了，否则出现「已回应但未读」。e 查三态时要把 `replied_at` 一起算。

`read_at` 只有 e 能写，**进页面不算、滚动过不算、点开那条内容才算**。

## 七、种子狗：能收，永不回

| 能做 | 不能做 |
| --- | --- |
| 收礼物、收捎话，正常出现在来信里 | 生成任何回复 |
| 让用户看到自己寄出去的东西到了 | 显示「对方已读」之后又出现一句回复 |

**发出去的那一刻界面就要写**：「这是一位示例伙伴，可能不会回话。」

**AI 代种子狗回一句 = 阻断缺陷。** 也不要「给点安慰性的回复」「至少回个谢谢」——那正是最容易被评委戳穿的地方。

## 八、验收（可数）

| # | 项 | 期望 | 怎么测 |
| --- | --- | --- | --- |
| 1 | 寄出不出现 | 寄出后 0 秒、来信页无这条 | 直接看 |
| 2 | 跨一次出行才到 | 收件狗 `seq` 加一后其 `started_at` 不为空 → 到 | 用 `isDeliverable` 单测 |
| 3 | 连点两次只到一份 | 同 id 插两次 → 库里 1 行 | 直接插库 |
| 4 | 不回不阻断 | `replied_at` 为 `NULL` 时，来信页、手账、首页无任何提示 | 跑全站，搜「等」「还没」 |
| 5 | 在途上限 | 第 4 件返回 `CONFLICT` | 插 4 条 |
| 6 | 已回应不能回两次 | 第二次返回 `CONFLICT` | 插 2 条 reply |
| 7 | 种子狗不伪造回复 | 给种子狗捎话 100 次，`replied_at` 全为 `NULL` | 手动 + 看日志 |
| 8 | 主人原话不进快照 | `snapshot` 里搜 `message` 原文 → 0 命中 | SQL 查 |
| 9 | 拉黑后不再新寄 | 拉黑这对之后新寄返回 `BLOCKED` | 插一条 blocked relation |
| 10 | 已在途的照常到 | 拉黑前寄出的，拉黑后仍按时到 | 不撤回 |

第 4 条的自查命令（在 `app/(d)/` 下跑）：

```bash
grep -rnE '还没回|已读未回|等你回|等待中|它还在等|已经 ?[0-9]+ ?天' app/\(d\)/ components/ui/
```

## 九、一个决定、一个待确认

**决定（第三层，我自己定，会牵动 e）**：**拉黑之后，已经在途的东西照常到达，不撤回。**
理由：撤回等于惩罚对方，也等于主人的一个动作直接改写了狗之间已经发生的事。拉黑只作用于「今后不再新寄、不再匹配」。

**待确认（问 c）**：投递器在 `finish` 要不要再跑一次，见 `1116-d1-交换规则十例-v1.md` 第七节。这件事同时影响礼物：A 出门遇到 B，B 当场给 A 的东西，能不能这趟就带回来。
