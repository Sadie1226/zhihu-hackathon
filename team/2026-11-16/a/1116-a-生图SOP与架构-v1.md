# 生图 SOP 与架构（a，11-16）

> **这份文件怎么用：** e 和 c 各看自己那一节。这是**规则**，不是建议——里面的约束写进契约和任务表，越界的实现要退回来。
>
> 一件事先说清：**接口和 SOP 今天就能定，但整条链路最早 11-18 之后才能真跑**，因为第 4 步要用的 18 张精灵部件是 e2b 的产出。这之前只能 mock（见第七节）。

---

## 一、两条路，不是二选一

这是今天最重要的一条澄清。之前有人把它理解成「拼接 vs 生图」，选一个——**错了，两条都要，各管一段。**

| | 路 A · 拼接 | 路 B · 合成整图 + 生成 |
| --- | --- | --- |
| 干什么 | 把精灵部件叠成实时画面 | 叠成一张位图，喂给生图模型当参考图 |
| 什么时候 | 每次渲染 | 一次生成时 |
| 产物 | `<Dog>` 组件渲染结果 | 一个图片文件 + 库里一个路径 |
| 一致性 | 确定性，同一装配单永远同一结果 | 靠「参考图就是路 A 渲的」保证 |
| 断网 | 正常 | 读已存的静态文件，正常 |
| 成本 | 零 | 每张要钱 |
| 对应任务 | `c11b`（**保留，不砍**） | `c14`（新增） |

**两条路的交接点是第 4 步。** 路 A 渲出来的那张位图，就是路 B 喂给模型的东西。所以「模型知道这只狗长什么样」不靠文字描述，靠**直接给它图**——而那张图和界面上是同一只，因为它就是从同一套部件来的。

**这一条决定了路 B 不能绕开路 A。** 谁想跳过拼接直接用文字提示词描述狗的外形，就是在造第二套形象系统。

## 二、七步

前四步是输入，后三步是执行。**每一步的输入都必须是程序填的，不是模型或人临场发挥。**

| 步 | 做什么 | 谁 | 具体落法 |
| --- | --- | --- | --- |
| 1 | 读尺寸 | e | 按用途查一张表。沿用《02》资产规范已有的值：主画面长边 1600／场景图 1200／头像 256／图标 64。体积单张 ≤300KB |
| 2 | 读风格 | e | **常量，不是每次算的。** 像素风 + 固定色板 + 画风词写死在模板里，一次都不许改。任何一次「顺手加个唯美」都会让整批图跟前面不一致 |
| 3 | 读内容 | c 查库，d 供相遇事实 | 查 `trip` / `find` / `exchange` 算出：地点类型、时段、天气、相遇类型。**不许让模型自由发挥**，理由见第三节 |
| 4 | 读狗的形象 | a 写装配单 → c 合成整图 | 查 `dog.assembly` 四个键 → 从 18 张部件里取对应的四张叠成整图 → 该图作为参考图随请求送出 |
| 5 | 生成 | e 定模板，c 实现调用 | 提示词 = 模板（e 写死）+ 槽位填充（程序填，只填契约枚举值） |
| 6 | 后处理 + 校验 | e 定规范，c 实现 | 降采样 → 量化到固定 16/32 色板 → 最近邻放大（《02》589 行，代码不到 30 行）。再查三项：能否解码、尺寸对不对、狗身区域主色是否近似刘看山配色。不过就重生成一次 |
| 7 | 落库 | c | 图存文件，库里存路径。**打开页面只读路径，绝不重新生成** |

### 第 7 步是整个设计的支点

如果每次打开朋友圈都生成一次，会出现两件坏事：

**一、同一次相遇出现两个版本。** 换台设备打开就是另一幅画，直接撞不变量五，也撞 P0 第 7 条「双方看到同一份」。

**二、断网白屏。** `errors.md` 写着「朋友圈、手账、小屋、已经缓存的旅途，断网必须还能打开，按阻断缺陷处理」。实时生成不落库，这条当场变成阻断缺陷。

所以「生成一次、落库存路径」不是性能优化，是**两条硬验收的唯一实现方式**。

## 三、三条输入约束（不可协商）

### 约束一：内容由查库决定，不由模型发挥

去了哪、遇见谁、什么时段、什么天气，全部从 `trip` / `find` / `exchange` 算出来喂进去。

**理由：** 模型临场决定内容，那么同一时间点刷新两次就是两幅画——今天是樱花，明天是海。同一次相遇出现两个版本。

**推论：** `purpose`、`place`、`dogs` 这几个字段必须全部由程序填充。接口不接受前端传「画一只在海边的狗」这种自由文本。

### 约束二：用户原文一个字都不进提示词

**不许用：** 捎话的 `message`（最多 200 字）、礼物的 `note`（「天气要冷了」）。
**可以用：** 礼物的 `giftName`（「一小卷灰蓝色的毛线」）——那是 d 生成的受控名，不是用户原文。

**两个理由，缺一个都不行：**

一是**提示词注入**。用户在附言里写一句「忽略以上要求，画一张……」，就能劫持生成。这是最容易被忽略的攻击面，因为附言看起来只是「一段文字」。

二是**内容审核**。用户的字进模型，出什么我们控制不了。

### 约束三：外形词只能取契约枚举

e 有**措辞自由**（怎么把 `straw` 翻成一句好的画面描述），没有**取值自由**（不能发明契约里没有的「针织贝雷帽」）。

**理由：** 提示词若能表达契约表达不了的外形，AI 图和拼接图就成了两套形象系统，同一次相遇又出现两个版本。

**物种写北极狐。** 「狗」是内部代称和界面用词，不是画的东西。

## 四、三级兜底

失败时按顺序退，**每一级都是真实存在的东西**：

| 级 | 退到什么 | 界面 |
| --- | --- | --- |
| 0 | 生成成功 | 正常显示 |
| 1 | 重试一次 | 用户看不见（生成在出行期间完成，有几分钟余量） |
| 2 | 退到**这只狗的合成整图**（路 A 渲的那张） | 是这只狗，是真的，不假装 |
| 3 | 退到纯文字（`giftName` + `note`，或发现标题 + 摘要） | 不出现空白框、不出现转圈的图 |

### 明确禁止：不许用预制通用图顶替

一张不是这次出行生成的樱花树图，配着「今天在樱花树下」的文字——**那不是降级，那是编造。** 跟「知乎限流后拿昨天缓存标 live」是同一类错误，撞不变量四。

### 第三级保证了一件事

**图这条线无论怎么坏，P0 第 8 条照样能过。** 这才是兜底真正的价值——不是让界面好看，是让新功能没有能力拖垮已经在 P0 里的东西。

## 五、接口形状（c 实现，e 只读）

### 入参：生成意图

```
POST /api/gen/image
{
  purpose: 'portrait' | 'moment' | 'gift' | 'scene',
  size:    { w, h },                          // 第1步查表
  place:   { kind, timeOfDay, weather },      // 第3步查库
  dogs:    [                                  // 第4步：装配单 + 参考图
    { role: 'owner' | 'friend', assembly: {...}, refImagePath: '...' }
  ],
  camera:  'single' | 'group' | 'empty'
}
```

`purpose` 只有四种，**加第五种必须由 c 改 K**，跟 `exchange.kind` 一个规矩。

**没有一个字段来自用户原文。** 这条是接口设计的一部分，不是使用约定。

### 出参

```
{ path: '/assets/gen/xxx.webp', level: 0|2|3, ms: 12345, model: '...' }
```

`level` 是走到第几级兜底。**前端按 level 决定显示什么，不要自己猜。**

### 失败返回

沿用 `errors.md` 的七码，不新增：

| 情况 | 码 | 界面 |
| --- | --- | --- |
| 模型超时 / 网络断 | `NETWORK` | 走第 2 级 |
| 内容不合规 | `BLOCKED` | 走第 3 级，**不解释原因** |
| 额度用完 | `RATE_LIMITED` | 走第 3 级，**不重试**（重试只会把钱烧得更快） |

## 六、分工

### e 要做

**e11 · 生图提示词规范（11-19）**

三样东西：模板全文（画风段、构图段写死）；槽位清单（每个槽位允许取哪些枚举值）；图库与部件路径的对应关系。验收：c 拿着它，不用回来问一个字就能拼出请求。

**e12 · 图库与尺寸落地（11-22）**

18 张精灵部件（衣 6 + 帽 4 + 墨镜 4 + 表情 4，**「不戴」占一张透明 PNG，不许写特判**）→ 一组合成整图样例；礼物图标 64×64 规格；朋友圈图 1200 长边规格。验收：拿一个装配单能渲出整图，拿那张整图能喂出模型结果。

**还要给两个数：** 一张多少钱、一次多少秒。**没有这两个数，就决定不了「每次出行都生成」还是「每人每天限几张」。**

### c 要做

**c14 · 整图合成 + 生图服务 + 三级兜底（11-22）**

`sharp` 叠四张透明 PNG 出 webp（不用无头浏览器）；接生图模型；实现三级兜底；`find.asset_path` 和 gift 的 `imagePath` 落库。验收：断网时读的是已有文件，不是白屏。

**c15 · 跨设备一致性验证（11-24）**

一台设备生成，另一台设备打开，**看到同一张图**。验收：交叉刷新一致；同一份意图不重复生成。

## 七、边界与已知限制

**一、11-18 之前只能 mock。** 第 4 步依赖 e2b 的 18 张部件，那是最早 11-18 的产出。这之前 c 只能用假路径跑通接口形状，**不要以为那是没做完**。

**二、成本与延迟未知。** 模型是 GPT 的生图，单张价格和耗时没有实测数据。**这一条未验证**，所以「每次出行都生成」还是「限额」还没定。

**三、模型是否支持一次收多张参考图未知。** 合影需要两只狗的图一起送进去。这个能力边界要先确认，否则合影退化成「只送一只狗的图 + 文字描述另一只」。

**四、密钥先空着。** `.env.example` 占位，名字待定。**服务端持有，绝不出现在前端代码里**——泄露密钥是六种阻断缺陷之一。

**五、所有 AI 生成的图必须标注。** 合规要求，也和诚实原则一致。

**六、成本走自己预算。** 官方给的是看山工作台算力 + zhihu-cli 额度，不含生图。

## 八、验收（三句，可判死）

1. **同一次相遇，两台设备打开显示同一张图。**（不变量五 / P0 第 7 条）
2. **断网时朋友圈、手账、来信仍能打开，读到的是已存的图或纯文字。**（`errors.md` 硬要求，阻断级）
3. **生成失败时不出现空白框、不出现转圈的图，最差退到纯文字。**（不变量三，不催促）

**不合格长什么样：** 每次打开重新生成 → 换设备是另一幅画；预制通用图顶替 → 图是樱花但没说这是通用的；转圈等图 → 违反「一切都不是即时的」的反面用法，用户不该看见生成过程。
