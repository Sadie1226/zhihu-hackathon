# 事务同步守卫去掉副作用 —— 拒绝就是拒绝，不替调用方执行

2026-11-22。分支 `d4-async-guard-1122`，从 `d615a67`（main v8-1122）切。
代码提交 `3b19738`。只改 `lib/social/store.ts`、`lib/social/sqlite-store.ts`、
`lib/social/store.contract.test.ts` 与本文档。不动生产规则、不动契约、不动 `contracts/`。

## 一、A 11-22 的要求，与这次的边界

A 在 v8-1122 的 D 条目里写明：

> E2E 收尾已合并；异步误用守卫暂缓，只需消除主动执行 thenable 的副作用并补针对性回归，
> 不要求扩展异步取消框架。

所以这次**只做两件事**：

| 做 | 不做 |
| --- | --- |
| 去掉「主动执行 thenable」的副作用 | 不建异步取消 / 中断 / 超时框架 |
| 补针对性回归（能抓住这个副作用） | 不扩 `transaction` 接口、不加参数、不改 C8 调用形状 |

`transaction(fn)` 是同步的、`assertSyncResult` 这条守卫本身**保留**（A 说暂缓的是
「扩展」）。守卫抓的仍是同一个错：async 回调让 COMMIT 跑到真正的写之前。

## 二、副作用到底是什么

上一版（`d4-async-guard-1121`，未合）在拒绝时多加了一句：

```ts
// 旧
try {
  void Promise.resolve(value as PromiseLike<unknown>).catch(() => {})
} catch { /* … */ }
throw new AsyncTransactionError()
```

当时的理由是「不挂 catch 会变成 unhandledRejection，把这行真正该看的错误埋掉」。
A 指出这句本身就是问题。机理分两层：

1. **`Promise.resolve(thenable)` 会调用它的 `then`。** 按规范，取值 `then` 是同步的，
   但 `then` 的**调用**排在紧随其后的一拍微任务里。也就是说，「检查一下返回值」这个动作
   会把那段本该被拒掉的异步操作真的跑起来 —— 真发请求、真写库都一样。
2. **它跑在事务之外。** 走到这一行时事务已经 ROLLBACK 或等着回滚，于是这段异步写
   落在 autocommit 上，库里多出一条没人认领的记录 —— 正是这个守卫本想避免的那种坏数据。

一句话：**守卫的职责是拒绝，不是执行。** 看见 thenable 就撒手，不要碰它。

## 三、改法

```ts
// 新：只读形状，不碰内容
export function assertSyncResult<T>(value: T): T {
  const maybe = value as { then?: unknown } | null
  if (
    value !== null &&
    (typeof value === 'object' || typeof value === 'function') &&
    typeof maybe?.then === 'function'   // 一次属性读取，不调用
  ) {
    throw new AsyncTransactionError()
  }
  return value
}
```

不接管这个 Promise 的后续：不挂 `catch`、不取消。两条理由都写进了代码注释：

- 它之后成或败，都改不了「事务已失败」这个结论；
- **吞掉它的 rejection 才是错的** —— 那会盖掉调用方真正的错误。取消需要一套配套框架，
  A 明确暂缓，这里不铺。

`sqlite-store.ts` 的两处调用点不变（COMMIT 之前、RELEASE 之前各一次）。

## 四、回归：为什么要拆成 20a / 20b

零散的「传个 async 回调要抛错」抓不住这个 bug —— 上一版的三条用例（17—19）在
带副作用的老写法下**全绿**，因为 `then` 的调用在微任务里，同步断言根本看不见。

所以用一个会记账的 thenable，把「有没有被执行」变成可断言的：

```ts
const probe = {
  thenCalls: 0,
  then(): void {                     // 一被调用就留下痕迹，并真的写一条库
    probe.thenCalls += 1
    store.insertExchange(exchangeRow('ex_async_side_effect', '不该被写进去'))
  },
}
```

- **20a**（同步）：`transaction(() => probe)` 必须抛 `ASYNC_TRANSACTION`，且行数不变；
- **20b**（让出一拍再断言）：`probe.thenCalls === 0`，且那条 `ex_async_side_effect` 不存在；
- **21**（正面，防误伤）：`{ then: '下一步' }` / `{ then: undefined }` / `42` 三种返回值
  都要正常放行 —— 判据是「then **可调用**」，不是「有这个键」。

测试文件为此加了一个 `checkAfterTick`：同步段跑完，`await` 一次 `setImmediate` 再跑
延迟队列，最后才打印汇总。这只影响这一个测试文件，不进生产代码。

### 反向验证（不是推理，是实跑）

把 `assertSyncResult` 临时改回带 `Promise.resolve` 的老写法，同一套用例跑出来：

```
✅ 20a 返回副作用型 thenable → 抛 ASYNC_TRANSACTION，事务不留写     ← 老写法也能过
❌ 20b 拒绝之后 then 一次都没被调用 → 检查动作把 then 调了 …        ← 两套实现都红
通过 42 条，失败 2 条
```

换回新写法：`通过 44 条，失败 0 条`。**20b 是唯一能区分新旧实现的那条**，
所以它必须留着 —— 后面谁再想在守卫里「顺手处理一下这个 Promise」，会立刻红。

## 五、一个诚实的边界

不接管 Promise 的代价：如果调用方传进来的是真会 reject 的 Promise，它之后的失败会以
`unhandledRejection` 的形式浮上来。**这是有意的**，不是漏了：

- 那是调用方第二处写错（既在事务里 await，又没处理失败）；
- 我们抛出的 `ASYNC_TRANSACTION` 是同步抛的，出现在调用栈上，第一现场看得见；
- 若我们替它 catch，反而是替一个错误的写法消音。

如果 A 认为线上必须零 `unhandledRejection`，那是另一件事（全局兜底），
不塞进这条守卫里。
