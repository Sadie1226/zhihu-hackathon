## 一、只做 5 只，不做 20 只

d5 的验收原话是「5 只性格经历各异的狗入池」，反例写的是「5 只话术一个味」。
20 只同款文案不是 4 倍工作量，是把同一个问题放大 4 倍。所以先用 5 只把「不一样」做对。

挑的是这 5 只（标签按仓库 `1117-d2b-种子狗装配单-v1.sql`，**不是工作区那份旧 SQL**）：

| 狗 | 标签 | 一句话 | 三条摘要合计字数 |
| --- | --- | --- | --- |
| 01 石头 | 好奇 / 看物 / 当下 | 见什么都新鲜，只说眼前，爱问为什么 | 56 |
| 02 豆子 | 恋家 / 慢热 / 寡言 | 能不说就不说 | **28** |
| 04 叮当 | 自来熟 / 话痨 / 直给 | 每条都有人、有对话、有态度 | 54 |
| 05 老周 | 慢热 / 看人 / 怀旧 | 看的是人，说的是「以前」 | 62 |
| 07 青椒 | 看人 / 婉转 / 当下 | 话到嘴边留一半 | 55 |

**覆盖度**：6 个互斥维度的两端各至少有一只狗 —— 好奇（石头）/ 恋家（豆子）、
自来熟（叮当）/ 慢热（豆子、老周）、话痨（叮当）/ 寡言（豆子）、看物（石头）/ 看人（老周、青椒）、
直给（叮当）/ 婉转（青椒）、当下（石头、青椒）/ 怀旧（老周）。12 个标签全部出现。

## 二、「不是一个味」长什么样

光说规则没用，看同一件事 5 只狗怎么说（烤红薯摊，**这张表只是示范，不入库**）：

| 狗 | 同一件事的说法 | 它凭什么这么说 |
| --- | --- | --- |
| 石头（看物·当下） | 红薯在桶里翻，裂开的地方冒白气。 | 只说眼前，不看人 |
| 豆子（寡言） | 很香。买了半个。 | 六个字能说完就不说七个 |
| 叮当（话痨·直给） | 大叔非让我尝一口，烫得我直甩头，他还笑。 | 有对话、有动作、有反应 |
| 老周（看人·怀旧） | 这个味道，跟我小时候巷口那个桶一样。 | 一定要拉回过去比一下 |
| 青椒（婉转·看人） | 围着的人都把手伸过去，我也想，但没挤。 | 先说别人，自己那半句放最后 |

五句话，五个视角，没有一个能换给别人 —— 这就是 d5 要的东西。

由此落成三条可执行的写法（写第 6—20 只时照这个来，不靠感觉）：

1. **话痨写动作，寡言写名词。** 叮当是「他说…我跟他聊…他还笑」，豆子是「楼下。猫在。」
2. **看人写人怎么动，看物写物怎么变。** 老周盯的是「灰外套换了件新的」，石头盯的是「云有三层」。
3. **直给说结论，婉转留半句。** 叮当「我站着听完了才走」，青椒「我说了谢谢——大概说了」。

字数本身也是证据：豆子三条 **28** 字，叮当 **54** 字。同样的三趟出门，一个是电报，一个是叙述。

## 三、一条差点照抄错的数据

青椒的标签，工作区那份 `seed_20.sql`（11-17 写的）是 **恋家 / 看人 / 婉转**，
仓库里 `1117-d2b-种子狗装配单-v1.sql` 已经改成 **看人 / 婉转 / 当下**（a 合并时对齐
`fixtures/dog.json` 的结果）。

我第一版文档按旧值写了「恋家」，跑真库时被 `JOIN dog` 的比对抓出来：标签是从 `dog` 表取的，
所以库里是「看人/婉转/当下」，而我注释写的是「恋家」—— **两者对不上，靠肉眼不一定看得见**。
于是顺手把青椒的第二条从「今天没走远」（恋家的口气）改成「门口有人蹲下系鞋带，系了很久」
（看人 + 当下，不评判，也不离家）。

**这条写在这里是为了记住：`_wip` 里的旧稿、工作区里的旧 SQL，都不能当事实。**
凡是要引用标签、装配单、类目，一律以 `origin/main` 的文件为准。

## 四、SQL 为什么从 dog 表取标签

```sql
INSERT INTO snapshot (dog_id, version, personality_tags, interest_categories, recent_trips, waiting_for, created_at)
SELECT id, 1, personality_tags, interest_categories, '["…"]', '…', '2026-11-22T00:00:00Z'
  FROM dog WHERE id = 'dog_seed_01'
ON CONFLICT(dog_id, version) DO UPDATE SET …
```

`personality_tags` 和 `interest_categories` 在 `dog` 表和 `snapshot` 表里是**同一份事实**。
手写两份，改一边忘一边，快照就会跟狗本身说的不一样 —— 而这种不一致在界面上看起来
完全正常，只有对比两张表才发现。所以这里只写「这只狗经历过什么」，身份字段一律 `SELECT` 出来。

幂等：`ON CONFLICT(dog_id, version) DO UPDATE`。重复跑不新增行、不改版本号 ——
snapshot 是版本化的，扩充新的经历应该写 v2，不是覆盖 v1。

## 五、这是怎么验的（四层，都能复跑）

| 层 | 验什么 | 结果 |
| --- | --- | --- |
| 1. 形状 | `snapshot.test.ts` 25 条：白名单、三标签三维度、兴趣 2–3 或 null、≤3 条、≤40 字 | 25/25 |
| 2. 真库 | 同一份值落进 `contracts/schema.sql` 的 snapshot 表，读回来一致 | 5 行全过 |
| 3. 幂等 | 同一份 SQL 连跑两次 | 两次都是 5 行，版本不变 |
| 4. 不脱节 | 把库里的 5 行读出来、转成 camelCase，再过一遍 `validateSnapshot` | 5 行全过 |

第 4 层是这次特意加的：SQL 里是 JSON 字符串，TS 里是对象，**两边可能各说各话**。
只有把「写进去的」再读出来过一遍校验器，才能证明「库里合规 = 代码认为合规」。

B 段（真库）里还有三条用例专门证明校验器不是多余的：库会拦的它也拦（4 条摘要、兴趣 `[]`），
库不拦的它也拦（三个不存在的标签 —— schema 的 CHECK 只数长度，照收）。

## 六、还有两件事没做，别以为 d5 完了

1. **第 6—20 只没写。** 先把 5 只给人看过、确认这个「味」对不对，再扩。一次写 20 只，
   改起来是 20 遍。
2. **`waiting_for` 现在是手写的一句话。** 按设计它应该从 exchange 表推（有没有没到的礼物、

不是文案库，这两件事别混。自动生成等 d6 之后再说。
