## 3. Snapshot NULL 语义

`Snapshot.interestCategories: InterestCategory[] | null`，对应 SQL `interest_categories TEXT`。

- NULL：未选择兴趣限制，与 dog 的语义一致，不转换成 [] 或六类数组。
- 非 NULL：必须是 JSON 数组，2–3 项，元素为现有六个类目。
- []、JSON null 文本、对象、无效 JSON、未知类目、数字/NULL 元素均拒绝；INSERT/UPDATE 同样校验。
- 不增加任何快照字段，保留原七个 SQL 列、复合主键、隐私白名单和历史版本。
- 整份快照不存在与快照存在但兴趣 NULL 不同，读取方不能混淆。

测试以兴趣 NULL 的狗插入 NULL 快照并建立合法 fixture exchange，证明数据库边界兼容；
没有冒充已执行 D4 的 NULL 兴趣匹配业务。D 的后续生成/匹配/展示不得用 `?? []` 或扩成六类来绕过。

## 4. 表重建与历史保留证据

基线依赖：snapshot 引用 dog；应用表没有指向 snapshot 的入向外键。
迁移先检查列定义、foreign_keys 和入向引用，再捕获 snapshot 显式索引与触发器定义。
旧库在 bootstrap 已持有的 **BEGIN IMMEDIATE** 中执行：

1. 将七列原值暂存至连接内 TEMP 表。
2. 按原名重建 snapshot，保留其他列约束和默认值、PK(dog_id,version)、dog 外键。
3. 创建新的类目校验触发器，原样回填所有快照版本。
4. 清理 TEMP 副本，恢复原表的显式索引/触发器，执行 foreign_key_check。
5. 由原 bootstrap 写 user_version=4 并提交。

不使用 ALTER RENAME，因此视图和其他表触发器继续引用原名；测试保留并执行相关视图查询，核对定义。
原自定义 INSERT 触发器在复制后恢复，回填不会重放业务副作用。
没有嵌套事务，没有事务内切换 foreign_keys，没有删除或重建应用数据库。
新库已包含可空定义和约束，不重建 snapshot；测试核对 rootpage/定义和 total_changes 不变。

| 升级路径 | 实际验证 |
| --- | --- |
| 新空库 → 4 | NULL 可存，七列/PK/FK/默认值保持，enum 约束生效 |
| v1 → v2 → v3 → v4 | 快照各列/多版本及 dog/trip/exchange 旧字段保留，外键检查为空 |
| v2 → v3 → v4 | 同上；不修改已部署事件迁移 |
| v3 → v4 | 同上；不修改已部署心愿迁移 |

| 升级后故意注入 INVALID SQL | v1/v2/v3 均回滚全部 schema、数据、版本；TEMP 表无残留，重试成功 |

若某个实际旧库已有非法类目，或未来另有表通过外键引用 snapshot，迁移安全失败并完整回滚，

## 5. Exchange 来源与历史兼容

find/gift 使用 `ProvenanceFields`：

```ts
type ProvenanceFields = {
  sourceFindId?: string | null
  sourceMode?: SourceMode | null
}
```

可选只服务于读取旧 JSON。新生成 payload 必须显式有两个键，不能省略；greeting/捎话不接受这些键。
没有 Find 来源为 null/null；非空 ID 必须真实存在、属于寄件狗的 trip，模式严格取该 Find 的 source_mode。
scene/moment 来源保持 null。事件本身不能虚构 Find ID；没有 Find 却声明 live/cache/fixture 的组合拒绝。
URL 不证明 live；交换和后续读取不重新刷新来源时效，历史缺键保持未知，不补 live。

新增 provenanceCases 引用既有 **find_seed1 → trip_seed_01 → dog_seed_07**，实际为 moment/NULL；
原四条历史 exchanges 保持原语义。没有将任何新增 fixture 标为 live。
两个新案例与全部来源字段、历史时间列均实际插入并 JSON 往返；NULL 快照夹具也往返保持 NULL。

`checkExchangeProvenance` 是 contracts/types.ts 中的契约级纯函数，不是 D4/C8 业务实现。
它接收可信服务端 JOIN find→trip 后得到的 id/dogId/sourceMode，校验 sender 一致、模式一致、
两个键齐全、历史缺键兼容及禁止未受信任来源声明。身份/会话权限仍由实际写入方先验证。
测试真实执行 SQLite JOIN 再调此边界，覆盖悬空/跨狗/伪造模式及不受信任 live。

**数据库原 payload 列只检查 JSON 语法，不自动检查来源所有权。**
有专门负例证明直接 SQL 绕过契约校验仍可写入无效来源，防止把契约测试误称为业务层安全保证。
收件人得到 sourceFindId 不会获得私人 trip/find 的读取权限；既有主人权限检查仍必须执行。
