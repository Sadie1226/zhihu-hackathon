# 领养需求变更与任务影响

日期：2026-11-17。来源：本轮用户明确指令。

本轮先核对需求和影响，不代表功能已经实现、契约已经更新或团队已经收到通知。旧存档保留，新需求优先于其中冲突的旧规则。

## 已确认需求

1. 必须注册，通过知乎账号授权获取用户信息。
2. 狗的名字必填，创建后允许改名。“名字可空、不填也能领养”作废。
3. 六类兴趣可以跳过；主动选择时选 2–3 类。
4. 服务端结合知乎用户信息和用户的初始性格调节，生成三个来自不同维度的性格标签。初始性格调节优先级更大；具体权重未指定。
5. 四键装配单是穿搭界面的选择结果，由用户自选，不再由服务端自行决定整套装扮。
6. 创建成功后进入小屋，生成用户自己的刘看山。内部简称“狗”，不改变角色 IP、体型或配色边界。
7. 用户补充确认：初始性格调节采用现有六组倾向——好奇↔恋家、自来熟↔慢热、话痨↔寡言、看物↔看人、直给↔婉转、当下↔怀旧。调节六组倾向不等于最终生成六个标签，最终仍为三个不同维度标签。
8. 用户补充确认：本次获取的知乎资料包含基础资料、收藏、关注、创作。后三类用于本次个性生成，不再属于可整体取消的 P1 输入接入；原“收藏内容转成目的地”仍是另一项 P1 功能，尚未升为本期必做。

## 流程草案

知乎授权注册 → 获取授权资料 → 填写狗名、可选兴趣、调节初始性格 → 服务端生成三个标签 → 用户选择四键外观 → 保存创建结果 → 小屋。

这里描述逻辑顺序，不冻结页面数。性格生成、穿搭预览可以在同一个创建流程中展示；布局待线框确认。

已有账号再次登录后应读取自己的狗，避免重走创建和重复生成；这是根据账号归属提出的实现建议，尚未确定一账号允许几只狗。

## 仍需核对

- 六组性格调节的维度已确认；具体控件、是否允许跳过、权重及选出三个维度的规则仍待设计。
- 知乎资料范围已确认；收藏、关注和创作的读取数量、摘要方式以及接口失败时如何继续需定义。用户本身没有相关数据与接口读取失败应区分，不能把失败伪装成无数据。
- “四键用户自选”包含 face；现有契约规定 face 在领养时固定。服装、帽子、眼镜是否后续可换，face 是否也可重新选择，待核对；不能自行撤销固定身份规则。
- 一账号允许几只狗，以及旧匿名狗是否迁移到账号，待定。
- 旧“两步内完成”指标需结合注册和穿搭流程重新定义，暂不擅自指定新步数。

## 知乎接入边界

本地提供的 `hackathon-oauth.md` 和 `hackathon-user-profile-api.md` 说明：

- 基础资料使用 OAuth access token 请求 `GET https://openapi.zhihu.com/user`；该接口不需要 Access Secret。
- 基础资料包含用户标识、昵称、头像、简介等；字段可能缺失或为空，不能当成收藏或兴趣数据。
- 收藏、关注和创作列表需额外调用用户数据接口，并同时使用 Access Secret 和用户 OAuth token。
- 本次已确认接入这些数据用于个性生成，因此 Access Secret 也成为这条资料获取链路的前置。创作按现有授权用户接口可读的创作列表与摘要设计；不能把仅支持 Access Secret 本人的全文、评论或统计接口当成所有授权用户均可使用。
- App ID、App Key 开发期领取方式仍待实际核实。此前“拿不到 OAuth 就整条不做”只适用于旧收藏夹 P1，不能用于取消本轮要求的注册领养。
- 本地接入资料要求公网 HTTPS 回调验证，当前部署方案为 IP 加非标端口。该方案是否满足登记、Cookie 与实际授权需 C 联调确认，不能只凭文档断言可用或不可用。
- 以上为本地参考资料的协议说明，本轮没有向平台验证实际接口和凭证可用性。
