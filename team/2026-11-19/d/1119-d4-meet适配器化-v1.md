## 二、`SocialStore` 现在有 10 个方法

c 给的是四方法（`insertExchange` / `upsertRelation` / `isBlocked` / `currentSeq`），后加的六个都有具体理由：

| 方法 | 为什么要 | 谁提的 |
| --- | --- | --- |
| `isSample` | 种子狗不能以自己主人名义说话，写入侧唯一能拦的位置 | d（`gift.ts` 需要） |
| `readExchange` | 幂等命中时不许回显本次 draft，必须回查库 | **a 的复核** |
| `readRelation` | 重放时要读回关系；不补就只能继续用 SQL | d（适配器化） |
| `hasDog` | 相遇前校验狗存在 | d（适配器化） |
| `getTrip` | 校验出行存在 / 归属 / 状态 | **a 的复核** |
| `transaction` | 「关系 + 交换」必须同生共死；不补就得把 db 句柄交回业务层 | d（适配器化） |

**多出来的全是只读 + 一个事务包装，没有一个能让 Mock 越权。** `transaction` 只收一个回调，不暴露 commit/rollback 句柄——「什么时候算落地」仍然不由 Mock 决定。这条是 c 明确要求的那条线。

## 四、一处形状变化

`relation.id` 从 `rel_<sha256 前 24 位>` 变成 `store.ts` 原有的 `rel_<dogA>__<dogB>`。

- 为什么：id 生成收敛到 store 一处，避免「业务层造一个 id、适配器造另一个」
- 安全性：`relation.id` 没有任何外部引用（api.md 里没有暴露，`ExchangePayload` 也不带），换形状不影响调用方
- 旧数据：如果 11-19 之前有人在本地库里写过 `rel_<hash>` 的行，`ON CONFLICT(dog_a, dog_b)` 仍然认得出来（冲突键是 `(dog_a, dog_b)`，不是 id），只是 id 列留着老值。demo 库是新拉的，不存在这个问题

## 五、给 c 的一句话

**C8 接的时候，实现这 10 个方法就够了，`meet.ts` / `gift.ts` 一行不用改。**

如果 C8 的接口形状和 `SocialStore` 不一致（比如 HTTP 而不是函数），写一个 `HttpStore` 适配器把 10 个方法映射过去即可——业务层看到的永远是同一个接口。

`transaction` 是唯一需要 C8 想一下的：HTTP 没有事务。可选做法是让 C8 提供 `POST /api/meets` 这种「一次调用落两样」的原子接口，适配器的 `transaction` 变成一个标记（内部所有写操作合并成一次请求）。这是适配器的事，不是业务的事。
