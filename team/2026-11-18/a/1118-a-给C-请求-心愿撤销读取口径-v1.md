## 一、我查到的事实（都实测过，不是推测）

### 1.1 字段全有，读法没定

`wish.revoked_at` 已经存在，注释也写清了：

```sql
-- b 写。撤销就填这一刻，**不物理删除**（手账还要能翻回去）。撤销后 c 不再读它。
revoked_at TEXT
```

**但「撤销后 c 不再读它」这句话，契约里没有任何东西替你回答。** 现在没有视图、没有函数，只有这一行注释。每个读 wish 的地方都得自己记得加 `WHERE revoked_at IS NULL`。

### 1.2 出行的目的地来源现在是空的

P0 第 2 条的验收句是「**能加能撤，撤销后下次出行不再围绕它**」。但 c4 的出行服务里 `wish` 表一个字都没出现：

```
lib/trips/service.ts:88   if (!['auto', 'wish', 'friend'].includes(trigger)) conflict(...)
                          # 'wish' 只是个字符串，没有任何代码去读 wish 表
```

所以这条验收今天**无法验证**。这不是 c4 的缺陷（c4 的交付说明里没声称做出行目的地拼装），是 c5/c6 之前必然会撞上的空档。**我只是想让你在建读取路径时手上有个现成的东西可用，别到 11-23 才发现要自己定过滤条件。**

### 1.3 契约现在对撤销几乎不管

我实测了四种情况（内存库 + 现有 `schema.sql`）：

| 试什么 | 现在的结果 |
| --- | --- |
| 撤销后再撤一次 | 不报错，但**时间戳会被覆盖**（不幂等） |
| 撤销一条不存在的心愿 | `changes = 0`，不抛错（这是对的，应用层返回 null 即可） |
| 已撤销的心愿还能改 `text` | **能改，契约不拦** |
| 撤销后从「生效心愿」里消失 | **没有视图，无从验证** |

第 1 和第 3 条要不要管，是你的判断；但**第 4 条我认为必须有**，理由见下。

## 二、请求的东西

### 2.1 加一个视图（这是核心请求）

```sql
-- 生效心愿：撤销过的不在这里。读心愿一律读这个视图，不要直接读 wish 表，
-- 免得每个调用点自己记得加 WHERE revoked_at IS NULL（漏一处就是 P0 第 2 条不过）。
CREATE VIEW v_wish_active AS
SELECT * FROM wish WHERE revoked_at IS NULL;
```

**为什么是视图而不是让调用方自己加条件**：`v_invitation_state` 已经是这个模式了——邀请三态（`waiting`/`replied`/`gone_alone`）不存列、由视图推。心愿的「生效/已撤销」是同一类问题，用同一种解法。**11-29 回归时最可能出的错就是「某处忘了过滤，撤销了的心愿还在影响出行」**，而那句正好是 P0 第 2 条的验收。

**我已经实测过这个视图能跑**（在现有 schema 上加一行，插两条心愿一撤一不撤）：

```
生效视图里应有 1 条（w1），实际: 1
wish 表本身应有 2 条（撤销不删），实际: 2
视图里是不是只有 w1: [ 'w1' ]
```

**唯一要你定的**：`SELECT *` 还是显式列清单。`v_invitation_state` 用的是显式清单（因为要算 `state`）。我倾向 `SELECT *` —— 心愿没有推导列，显式清单会在以后加列时变成第三处要同步的地方。**这条你定，我不坚持。**

### 2.2 加三条断言（照现有自检的格式）

放进 `scripts/check-contracts.mjs`，接在现有的「6. 邀请三态」后面，编号你自己排。三条都对应 P0 第 2 条那一句话：

```js
// ---------------------------------------------------------- N. 心愿撤销
console.log('\nN. 心愿撤销（P0 第 2 条：能加能撤，撤销后下次出行不再围绕它）')

// 前提：fixtures/wish.json 里 wish_003 已经是撤销状态（revoked_at 有值），
// wish_001/002 未撤销。以下三条直接用它，不需要新造数据。

// 1) 撤销的不在生效视图里，但仍在表里（手账翻得回去）
const activeIds = db.prepare('select id from v_wish_active order by id').all().map(r => r.id)
const allWishIds = db.prepare('select id from wish order by id').all().map(r => r.id)
if (!activeIds.includes('wish_003') && allWishIds.includes('wish_003')) {
  ok('wish_003 已撤销：不在 v_wish_active 里，但仍在 wish 表里（手账翻得回去）')
} else {
  bad('撤销的心愿要么还混在生效视图里，要么被物理删了 —— 前者会让下次出行仍围绕它，后者让手账翻不回去')
}

// 2) 未撤销的必须在生效视图里
if (activeIds.includes('wish_001') && activeIds.includes('wish_002')) {
  ok(`v_wish_active 里有 ${activeIds.length} 条生效心愿（wish_001/002）`)
} else {
  bad(`v_wish_active 漏了未撤销的心愿 —— 实际只有 ${activeIds.join('、')}`)
}

// 3) 重复撤销幂等（不许把第一次的时间戳覆盖掉）
const firstRevoke = db.prepare("select revoked_at from wish where id='wish_003'").get().revoked_at
db.prepare("update wish set revoked_at=? where id='wish_003' and revoked_at is null")
  .run('2099-01-01T00:00:00Z')
const afterRevoke = db.prepare("select revoked_at from wish where id='wish_003'").get().revoked_at
if (firstRevoke === afterRevoke) ok('重复撤销是幂等的（时间戳没被覆盖）')
else bad(`重复撤销把时间戳改了：${firstRevoke} → ${afterRevoke} —— 手账上的撤销时间会漂移`)
```

**第 2 条要注意：** 如果 `v_wish_active` 写成 `SELECT *`，上面直接可用；写成显式清单也行，断言只读 `id`。

**第 3 条的写法意味着一条口径要定：** 撤销用 `WHERE ... AND revoked_at IS NULL` 这种写法才幂等（我实测：这样写时间戳不变；直接 `UPDATE ... SET revoked_at=?` 会覆盖）。**如果你的实现是后者，第 3 条会红——这不是断言写错了，是真的不幂等。** 你按你的判断定要不要「撤销时间不许漂移」，我只负责指出实测结果。

### 2.3 （需要你判断，我不催）已撤销心愿还能改 text

实测：已经撤销的心愿，`UPDATE wish SET text='改一下'` 能成功。要不要拦，是产品判断——我倾向**不拦也不是缺陷**，因为撤销是 b 的写入方，他只要不写就行；加触发器反而增加复杂度。**这条我列出来只是让你知道现状，不建议为它改契约。**
