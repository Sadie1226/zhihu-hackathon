## 三、你真正要补的东西：照片上传（b6 里本来就有的活）

我把整条链查了一遍，结论是——

### 3.1 现在的实际情况

`contracts/api.md` 第 6 节，回应接口长这样：

```
POST /api/replies
入： { exchangeId?, invitationId?, text?, photoUrl? }
```

**`photoUrl` 是客户端直接传进来一个字符串。** 也就是说，前端说 `/assets/photos/a.webp`，服务端就存这个字符串。

而全仓库**没有任何上传路由**：

```
app/api/ 下只有：health、dogs/[id]/trips、trips/[id]、trips/[id]/start、trips/[id]/finish
没有 upload，没有文件的接收端
```

我实测了契约对 `photo_url` 的实际把关程度（内存库 + 现有 schema）：

| 塞什么 | 结果 |
| --- | --- |
| `/assets/photos/6mb.jpg`（声称 6MB） | **插进去了** |
| `/assets/photos/a.exe`（不是图片） | **插进去了** |
| `''`（空字符串） | **插进去了** |
| `javascript:alert(1)`（伪协议） | **插进去了** |
| `/assets/photos/a.webp`（正常） | 插进去了 |

**换成人类的话：现在任何人可以让回应里带一张根本不存在的图、一个可执行文件、或者一段脚本，数据库都照收。** 后果是界面上出现一个裂开的框。

**但要摆正这件事的分量：这不卡 P0 验收。** P0 第 6 条写的是「能回文字**或**照片」，照片是可选路径，纯文字也能过。它属于「该补、但不急」那一档，排在 d 的事件池返工和 c 的心愿撤销视图之后。我上一版把它写得比实际严重，这里更正。

### 3.3 你要交的东西（四个小件，都是文档，不写代码）

**（1）上传接口的形状——写到能照着实现的程度**

```
POST /api/uploads/photo
入：multipart/form-data，一个文件字段（建议名 file）
出：{ "url": "/uploads/xxx.webp", "bytes": 123456, "mime": "image/webp" }
错：
  413 太大（给出上限，例如 5MB）
  415 格式不支持（只允许 jpg/png/webp）
  401 无会话
```

**要你定的三件事**（我不替你定，因为这是你的模块）：

- **上限多少**——你在 b3 里写了 ≤5MB，我建议就用 5MB，别改
- **要不要压图**——手机原图经常 3–8MB，压到 1600px 长边可能只有 300KB。**我建议压**，理由是演示时网速不可控；但**压图会丢画质，这是产品判断，你定**
- **存哪儿**——放 `public/uploads/`（gitignore 已备好），文件名用随机 ID 不用原文件名（原文件名会泄漏用户本地信息，比如「IMG_20261118_我家的猫.jpg」）

**（2）校验规则，写成表**

每一条都要能回答「不满足会怎样」：

| 检查什么 | 规则 | 不满足时 |
| --- | --- | --- |
| 大小 | ≤ 5MB（或你定的值） | 413，界面就地提示，**已输入的文字不丢** |
| 格式 | 只认 jpg/jpeg/png/webp，**看文件头不看扩展名** | 415。看文件头是因为改扩展名太容易 |
| 尺寸 | 比如最长边 ≤ 4000px（防解压炸弹） | 拒绝或压缩 |
| 归属 | 必须带有效会话；只能传到自己的空间 | 401 |

「看文件头不看扩展名」这条要写清楚——只查扩展名等于没查，`a.exe` 改成 `a.jpg` 就过了。我在上面实测过 `.exe` 那条能插进去，就是这个原因。

**（3）失败时的界面表现（你 b3 已经写了一半，补齐即可）**

b3 修订版里你已经写了：

## 五、要不要给 c 写请求：三条路，你自己挑

这一节专门回答「我要不要去找 c」。**先说结论：大概率不用。** 三种做法，成本差很多。

### 路线 A：文件名带 session，不动契约（**我推荐这条**）

**怎么做**：上传时把文件命名成 `s_<sessionId前8位>_<随机串>.webp`，存进 `public/uploads/`。`POST /api/replies` 收到 `photoUrl` 时，检查文件名里的 session 是不是当前会话的。

**好处**：
- **完全不用找 c，一行契约都不用改**
- 不用加表、不用加迁移、不用等任何人
- 11-21 你一个人就能做完

**代价**：
- 靠文件名认人，不算严格。别人如果猜到了你的文件名，理论上能引用你的图
- 但你想想实际风险：session 是随机串，文件名也是随机串，猜中的概率可以忽略；而且这是演示产品，不是真上线。**P0 第 6 条只要「能回文字或照片」，这条完全够。**

### 路线 B：加一张 `upload` 表，要动契约（要找我）

**怎么做**：建表记录 `id / session_id / path / bytes / mime / created_at`，回应时查这张表确认「是你传的」。

**好处**：
- 认人严格，不靠文件名
- 以后要做「我的照片」列表、要清理孤儿文件，都有据可查

**代价**：
- **要动 `contracts/`**：加表、加迁移（现在数据库是 v2，要出 v3）、改 `types.ts`、改自检。**这些只有 c 能改**
- 要等我写给 c 的请求 + c 排期 + c 交付 + 你 pull，**最乐观也要多等一天**
- 多一张表就多一处要维护

### 路线 C：什么都不做，接受现状（**不推荐，但要说清**）

**怎么做**：`photoUrl` 继续让客户端自己传，不校验。

**后果**：我在第二节实测过——6MB 假地址、`.exe`、空字符串、`javascript:` 伪协议全都能存进去。界面会裂一个框。

**为什么仍然列出来**：因为 P0 第 6 条写的是「能回文字**或**照片」，**照片是可选路径**。如果 11-21 实在排不开，纯文字路径能让第 6 条过验收。**但这是最后手段，不是方案。**

- 「走 A」→ 我什么都不做，你照 A 做
