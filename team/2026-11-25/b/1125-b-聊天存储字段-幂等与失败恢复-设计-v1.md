## 1. 最小存储字段（给 C/A）

C 提案的 DDL 已满足 B 的全部需要，**B 不要求增加任何列**：

```sql
CREATE TABLE chat_message (
  id TEXT PRIMARY KEY NOT NULL,
  owner_id TEXT NOT NULL REFERENCES owner(id),
  client_message_id TEXT NOT NULL,
  dog_id TEXT NOT NULL,
  text TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE (owner_id, client_message_id),
  FOREIGN KEY (dog_id, owner_id) REFERENCES dog(id, owner_id)
) STRICT;
```

| 字段 | 来源 | B 为什么需要 | 不允许 |
| --- | --- | --- | --- |
| `id` | 服务端生成，不透明，建议 `chat_` + UUID | 200 回执里用它确认乐观上屏项；也是后续生成/回看的关联键 | 不得用客户端 `clientMessageId` 当主键；不得可预测 |
| `owner_id` | 仅来自有效未撤销的 owner 会话 | 与 `client_message_id` 组成幂等键；查询必须按 owner 作用域 | 不得来自请求体；不得跨 owner 查重 |
| `client_message_id` | 客户端为一次意图生成并保留 | 同键重放/冲突判定的唯一业务键；超时、丢响应、503 必须原键重试 | 不得服务端改写、修剪、重新生成；不设过期 |
| `dog_id` | 已授权的目标狗 | 同键同值比较的目标部分；复合外键约束归属 | 不得是种子狗/无 owner/跨主人狗 |
| `text` | 仅 `trim()` 后的原文 | 同键同值比较的内容部分；回显必须逐码元一致 | 不得存 trim 前文本、不得 Unicode 归一化/合并空白/改写 |
| `created_at` | 首次成功提交时的服务端 UTC，ISO 毫秒 `Z` | 重放必须回传首次时间，不能变成重试时间 | 不得客户端提供；不得重放时更新 |

**明确不要的列**：`status`、`replyText`、`updated_at`、`session_id`、`attempts`、任何生成结果列。状态是客户端瞬时概念（见 §3），不是持久化事实；首版成功体固定四键，回复生成另行定约。

**约束要求**：`UNIQUE(owner_id, client_message_id)` 是并发与重启后幂等的唯一保证；`FOREIGN KEY(dog_id, owner_id) REFERENCES dog(id, owner_id)` 复用现有唯一约束。授权检查、查重、比较、写入必须在**同一个 `BEGIN IMMEDIATE` 写事务**内完成，COMMIT 成功后才返回 200。

## 2. 幂等键语义

- 键 = `(owner_id, client_message_id)`；`client_messageId` 为 1–128 个 ASCII 字符，`^[A-Za-z0-9][A-Za-z0-9_-]*$`，**区分大小写、不修剪**。客户端一次用户意图生成一个不可预测键（如 `crypto.randomUUID()`），该意图的所有重试复用它。
- 同键同值 = 同一 owner + 相同键 + 相同已授权 `dogId` + 相同 `text.trim()` 逐码元相等 → **返回首次记录**（`id/dogId/text/createdAt` 全同）。
- 同键改 `dogId` 或改 `text`（含内部空白/Unicode 码元变化）→ **409 `CONFLICT`，不可重试**。用户明确「另发一条」或改了内容再发时才生成新键。
- **授权先于幂等**：目标狗不存在/种子/跨主人/会话无效一律 404，即使该 owner 已用过这个键；不得借幂等查询泄露其他 owner 是否用过同键。
- 同键不同 owner 各自独立，互不冲突，响应不暴露他人记录存在与否。
- 键不设过期；记录不覆盖；本契约不提供公开历史读取 API。

## 3. 消息状态（仅客户端，不落库）

`delivery` 与 `generation` 正交，都不写 `chat_message`：

| `delivery` | 含义 | 允许操作 |
| --- | --- | --- |
| `pending` | 已乐观上屏、拿到键、尚未发出 | 发送；取消（转 `uncertain`，保留键） |
| `sending` | 请求在途 | 等待结果；取消（转 `uncertain`，保留键） |
| `confirmed` | 收到 200，已用服务端 `id` 确认 | 只读；不再重发 |
| `uncertain` | 超时/断连/503/结果不明 | **用原键原文重试**；可继续等待；不可换键 |
| `conflict` | 409，同键改了目标或内容 | 终态；用户另发才生成新键 |
| `forbidden` | 404，会话或目标狗无权 | 终态；不重试、不换狗复用键 |

| `generation` | 含义 |
| --- | --- |
| `none` | 首版默认，没有回复生成 |
| `pending` / `failed` / `done` | 未来回复生成的独立状态；失败只改这一维，**不碰 `delivery`** |

去重按 `clientMessageId`：同键只保留一条乐观项；若同时存在 `confirmed` 与 `uncertain` 的同键项，`confirmed` 优先。

## 4. 失败与重试场景（重点）

### 4.1 发送已受理但持久化失败

这里区分两件常被混为一谈的事，处理相反：

1. **写事务未提交**（含数据库写入/读取故障）：服务端必须回滚并返回 **503 `NETWORK`（retriable）**，**绝不能返回 200**。客户端把该项置 `uncertain`，保留 `dogId`/`text`/`clientMessageId`，按退避重试；不得换键、不得另起一条、不得把乐观项直接标成已确认。
2. **已提交但响应丢失**（超时、连接中断）：服务端其实已成功，只是客户端没收到。客户端同样置 `uncertain` 并用原键重试；服务端命中同键同值返回首次 200，客户端用返回的 `id` 确认**原记录**，不会写第二条。

服务端事务顺序：同事务内复核会话 → 校验 `dog.id = dogId AND owner_id = auth.ownerId AND is_sample = 0` → 按 `(owner_id, key)` 查 → 比较 → 写入或回读 → COMMIT → 200。只有**目标唯一键冲突**可回读当重放；其他数据库异常一律 503，不得吞成成功。

### 4.2 重复提交

- 同键同值：服务端回首次记录；客户端按 `clientMessageId` 去重，界面不冒第二条，也不刷新 `createdAt`。
- 同键不同值：409 不可重试，客户端置 `conflict` 并提示用户「这条已发过且内容不同」，不自动改键重发。
- 并发同键：唯一约束保证只有一行；两个请求都可读回同一记录并各自返回 200，客户端各自按同键去重。
- 跨 owner 同键、以及未授权狗：按 §2 处理，不进入写入比较。

### 4.3 生成失败

- 首版 `ChatResponse` 无 `replyText`，**回复生成不属于 `POST /api/chat`**；四句本机示例不得当作服务端回复上屏或落库。
- 生成失败时：已确认的主人消息保持 `delivery=confirmed`，只把 `generation` 置 `failed`，展示独立的可重试提示；**不得回滚已确认消息、不得重发聊天、不得更换 `clientMessageId`**。
- 生成重试（待另约定）应以服务端 `id` 为关联键，不用 `clientMessageId`；在生成契约发布前，B 不写任何生成结果到 `chat_message`。

### 4.4 其他

- `503` / `NETWORK` / 超时：保留原键原文，`uncertain` → 退避重试（本轮设计上限 5 次，间隔 0/500/1000/2000/5000 ms 封顶）；超时本身没有 HTTP 错误体。
- `404`：终态，不重试；应提示会话或目标问题，不换狗复用键。
- `409`（非法请求或同键异值）：终态，客户端不盲目重试，交用户修正后另发。
- 面板卸载/切狗：在途项转 `uncertain` 并保留键；重开后按同键重试，不制造新意图。
