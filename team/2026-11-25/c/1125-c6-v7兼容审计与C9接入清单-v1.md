Cookie 会话是边界的身份凭据，持久化 Trip 及证明归属使用稳定 owner ID。引入后台任务时，A/C10 需决定如何从服务端保存并再次授权 owner 执行意图。来自同步 HTTP 的执行在最终写入前重验失效、撤销与归属。已验证的种子可以已有一趟，只有存在真实 occurrence 且事实可读时才可能有事件 Moment。非种子只有通过可信 C5 或后来核验的 C9 才能计入真实知乎来源。三种证据单独计数，样本无知乎来源本身不代表出行失败。

## C · 可信服务端执行顺序与重试

1. **C4 start** 先检查归属、状态、配额和间隔，在原事务中绑定出发前 Snapshot、落 `started_at` 并投递。只有已提交且仍 running 的 Trip 继续产生材料，终态回放只取历史。
2. **C7** 在 start 提交后独立抽取并落 occurrence。主人使用已授权 C7 路径，种子使用 `intent.selectEvent(conditions)`。无可信环境条件传 null。v7 trigger 在同一事务中捕获事实，已有同趟 occurrence 的重试复用原行。
3. **C5** 仅真人作用域发起。使用拆出的 `createTripDiscoverySearch`，保留绑定心愿、兴趣和前置屏蔽，仅传回一组进程内证明。旧 `createTripDiscoverer` 可继续供既有单条调用。组合执行器只走纯搜索入口，因此不会预写首条再批写。网络等待期间无 SQLite 写事务，禁止跨进程序列化 `WeakMap` 证明。
4. **C6** 短事务开始后重新核对运行状态、起止窗口、授权与最新屏蔽主题。同一事务读已核实的场景材料与冻结事件，校验证明作用域后统一写入。Trip 在网络期间转为 done、failed 或 timeout 时放弃本次批写。原文规范化 URL、稳定观察 ID 和冻结 occurrence ID 是三种来源键，按 `(trip,kind,source)` 稳定去重。事务内读取既有行后按上限追加，遇同源保留首次 ID、正文、时间和来源档位。
5. **C4 finish** 在批次提交后按现有规则结束。同意图重试复用已确认的观察集合及稳定来源。旧 C6 只保证同源幂等，空槽仍可被第二次搜索的新 URL 填补。C10 需把首次已提交的拼装结果视为同一轮执行的完成点。重启后若要严格区分「首轮提交完成」与「仍待补齐」，应由 A 定执行意图完成回执或受控二阶段补齐。验收前至少禁止对已提交完整批次或终态盲目重搜。失败后重试仅补原批次缺失来源，不把改变的搜索结果当作原批次重放。

旧 C6 还按历史物理行数占用五条配额，并可能为未来知乎预留一条。被屏蔽、旧 fixture 或同 URL 重复历史仍会占容量。保留历史行，合验需明确当前组合按可见、可验证来源判定 `complete/partial`。种子无需为真实知乎保留槽位，容量上限仍为五条。建议旧 cache 缺证明时可照常读历史及标签，不能靠 URL 和 `sourceMode` 字段单独证明新一趟达标。
