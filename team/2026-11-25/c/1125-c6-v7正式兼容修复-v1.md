### 冻结事件和旧行核对

批写使用唯一 `readOccurrenceFact`，按既定最早 occurrence 顺序，最多采用一条本趟、本狗且位于出发至提交窗口的事实。最早历史不可核验时跳过。视图缺失或事实存储不一致时回滚。额外的完整性检查区分迁移时的显式空事实与损坏缺行。冻结 `sourceId` 沿用旧 `trip-event:<event_id>` 键，事件 Find 的 `sourceMode`、`sourceUrl` 均为 null。

| 核对项 | 行为与证据 |
| --- | --- |
| 旧 Find 与冻结事实冲突 | `EVENT_FIND_MISMATCH`。受控库将同键 Find 的正文替换成后来模板，拼装排除旧行，Cookie GET 仍原样可读。A 可据该诊断核对既有旧行。 |
| v7 缺少发生时标签 | 冻结正文可执行当前文本屏蔽。当前存在非空屏蔽词且正文未命中时，因主题证据缺失跳过并返回 `EVENT_TOPICS_UNVERIFIABLE`。模板改 text、code 和标签后，冻结正文与同源 ID 稳定。 |

### 批次重放和 C10 提案

同源持久化重试保留首存 ID、内容、时间及档位。活跃服务进程内，同一 SQLite 文件的连接共享完整批次记录。重放跳过 C5，重新核验已确认成员，在途搜索的新 URL 无法扩充批次。终态在搜索前拒绝继续执行，从 Find GET 回看历史。重开可读针对持久化 Find。进程重启或活跃连接生命周期结束后，仍为 running 的完整批次须由 C10 提供持久回执。

建议 C10 以 `intentId + tripId` 唯一标识一次执行，将有序 Find ID 集合和完成时刻与 C6 完整写入原子提交，再用回执驱动 B5/Message、邀请及 finish。部分补齐记录首次确认的来源集合和缺失槽位，按同一服务端意图重放。若需新一轮搜索，由 A 确认补齐条件和 UI 语义。后台 owner 授权重验、完成回执存储与生命周期待 C10 联调。
