## 一、边界修正：只有 `undefined` 算未声明（C 第 1 条）

C 指出的漏洞是真的：原实现里 `claimedMode !== null` 这一条把**显式 `null`** 也当成了「没说」，
于是「传 `sourceMode: null` 配一条 `live` 的 find」会静默成功——调用方可以靠「说不清」绕过档位核对。

改后三态分明：

| 调用方传的 `sourceMode` | 含义 | 库里是 `live`/`cache`/`fixture` | 库里是 `null`（scene/moment） |
|---|---|---|---|
| 不传（`undefined`） | 未声明，**由库派生** | ✅ 落库为库里的值 | ✅ 落库为 `null` |
| `null` | **明确声明「没有档位」** | ❌ `PROVENANCE_MISMATCH` | ✅ 落库为 `null` |
| `'live'` 等 | 明确声明档位 | ✅ 相等才过，不等即拒 | ❌ 拒 |

落点：`provenance.ts::resolveProvenance` 最后一条判定改为 `claimedMode !== undefined && claimedMode !== src.sourceMode`。

**一处旧用例按新边界改了输入**：`meet.test.ts` 的「outgoing find 指向自己的真实发现」原来传
`sourceMode: null` 却断言落库为 `live` —— 那正是 C 要禁掉的静默纠正。现在改成不传该键（验「由库派生」），
断言不变。**测试跟着口径走，不是口径跟着测试走。**

新增/调整用例：

| 用例 | 断言 |
|---|---|
| gift `A11e`（改） | 来源是 scene，**显式传 `null`** → 通过，落库 `null` |
| gift `A11g`（新） | 显式 `null` + 库里 `live` → `PROVENANCE_MISMATCH` |
| gift `A11h`（新） | 不传（`undefined`）+ 库里 `fixture` → 派生 `fixture` |
| gift `B9d2`（新，真库） | 显式 `null` + 库里 `live` → 拒，且 `exchange` 0 行 |
| meet（新） | incoming 来源属于对方、库里 `live`、显式声明 `null` → 拒，关系与交换都不留 |
| e2e 7c（新） | 真文件库：`显式 null 被拒：PROVENANCE_MISMATCH` |

## 二、事务覆盖（C 第 3 条，A 的「事务覆盖证据」）

### 2.1 原实现的两个缺口

1. **`gift.send` 没有事务。** 一次发送碰三次库：`getFindSource`（来源）→ `currentSeq(toDog)`（趟次）→
   `insertExchange`（写行）。三次分开做，收件狗可能在 2 和 3 之间真出发一趟，写下的
   `deliver_after_trip_seq` 就少一趟 —— **礼物提前到达，且只在并发时出现，事后查不出来**。
2. **`store.transaction` 不支持嵌套。** C 要求「C8 在一次事务中验寄件权、调用 sendGift」，
   而 `sendGift` 自己也要事务；两个 `BEGIN` 撞在一起就是 SQLite 的
   `cannot start a transaction within a transaction`。

### 2.2 改法

- `gift.ts`：`send()` = `store.transaction(() => sendBody(...))`。整段「查来源 → 算趟次 → 校验 → 写入」在一个事务里；重放回查也在同一个事务里。
- `sqlite-store.ts`：`transaction` 加嵌套深度。
  - 最外层：`BEGIN IMMEDIATE` … `COMMIT` / `ROLLBACK`（保留原来先拿写锁的意图）
  - 内层：`SAVEPOINT sp_d4_<n>` … `RELEASE`；内层抛错只 `ROLLBACK TO` 自己，错误继续上抛
- `store.ts`（内存实现）：本来就是「每次调用拍快照、抛错恢复」，天然等价于 savepoint 语义，未改。

### 2.3 调用形状（给 C8 照着写）

```ts
// 礼物 / 捎话：C8 验寄件权 + D 的写入，同一个事务
store.transaction(() => {
  assertSenderAuthorized(session, fromDog)      // C8 的事：session → fromDog 的写权
  return sendGift({ store, fromDog, toDog, ... })  // 内层自己会 SAVEPOINT，不会撞 BEGIN
})

// 相遇：直接用 meet() 的事务，外面不要再包
meet({ store, dogId, otherDogId, tripId, ... })
```

两条纪律：

1. **不要吞内层错误。** 内层失败后外层若 `catch` 了还继续写，落库的是「一半发生」；要吞就必须自己决定这半笔怎么处理。
2. **不要在同一个连接上自己 `BEGIN` 再调进来。** 要包事务就用 `store.transaction`（可嵌套）。

### 2.4 证据

| 用例 | 验什么 |
|---|---|
| gift `C1`（真库） | 外层事务里包 `sendGift` → 不报 nested BEGIN，礼物照常 1 行 |
| gift `C2`（真库） | 外层在 `sendGift` 之后抛错 → 礼物也撤掉，`exchange` 0 行（原子性覆盖到 C8 那层） |
| gift `C3`（真库） | 内层 `sendGift` 失败、外层接住 → 内层那条撤掉，外层已写的留下 |
| store.contract `14` | 嵌套两层，两层写都留，内层返回值透传 |
| store.contract `15` | 内层抛错被外层接住 → 只撤内层（savepoint 生效） |
| store.contract `16` | 内层抛错不接住 → 整体回滚，外层已写的一起撤 |
| meet `事务性：incoming 来源查不到` | 关系与交换全回滚（原有） |

## 三、可信寄件权：分工与 d 能证明的部分

d 的实现里**没有 session 概念**，`SocialStore` 也没有「当前登录是谁」的入口 —— 这是有意的：
写入函数只认 `fromDog` 这个字符串，谁有资格代表它说话，必须在调用前由持有 session 的一方证明。

| 谁证 | 证什么 | 依据 |
|---|---|---|
| **C8（C）** | `session → fromDog` 的写入权；开发态用 Session 隔离，正式会话撤销另做安全验收 | C 第 3 条；C8 是唯一持有会话的地方 |
| **d（已实现）** | ① `hasDog(fromDog)` / `hasDog(toDog)` 存在性 ② `isSample(fromDog)` → 种子狗不得以主人名义捎话（`SEED_OWNER_SPEAKS`） ③ `meet` 里 `trip.dogId === dogId`（`TRIP_NOT_OWNED`）与 `status==='running'`（`TRIP_NOT_OPEN`） ④ `isBlocked` 双向 ⑤ 来源归属 `find⋈trip.dogId === fromDog` | 见 `meet.ts` 的「先拒后写」段与 `gift.ts::send` |

③ 是 d 侧唯一一处**结构性**的寄件权证明：trip 属于谁，是从库里读出来的，不是调用方声明的。
其余四项是「这只狗是谁」的性质，不涉及会话。

如果 C 认为 `fromDog` 的授权也应该由 store 兜一层（比如加 `assertWritable(sessionId, dogId)`），
这要动 `SocialStore` 接口——**d 不改，等 C 提**；加接口比在业务层各点自查贵，但比漏一处便宜。

## 五、种子狗延迟投递：接受 C 的口径，撤回我 11-19 的绝对说法

C 说 `seq=0→1` 与 `seq=1→2` 都能验延后投递，**这是对的**，我 11-19 那份文档里「只能验 `dog_seed_07`」说得太满了。

准确的条件只有一条：**发送那一刻，目标趟次还不存在。**

- `seq=0`：发送时算 `deliver_after_trip_seq = 1`；真实启动第 1 趟 → 到达。发送与出发之间是「在途」。
- `seq=1`：发送时算 `2`；真实启动第 2 趟 → 到达。
- 两者都验到了「不是即时到达」，区别只是演示时能等多久。

我用 `dog_seed_07` 是因为它已经有 `seq=1` 的 trip，**不用造数据就能演示跨一趟**；不是因为别的狗验不了。
要验 `seq=0→1`，只需 C 那边真启动一趟，d 这边不需要改任何代码。

不伪造、不预置虚假 trip、不提前标 `delivered_at`、不生成示例伙伴的真人回复 —— 这四条照旧。
