## 一、A 实测的两处不兼容，现在分别是什么行为

| A 的输入 | 旧行为（`4fbcd11`） | 现在 | 证据 |
|---|---|---|---|
| `sendGift` 显式传 `sourceFindId:null, sourceMode:null` | 返回 `inserted=true`，payload 里**没有**这两个键 | 两个键**都在**、值为 `null`，落库 | gift `A10`、e2e 步骤 7c |
| find payload 显式带两个 null | `UNKNOWN_KEY @ /payload/sourceFindId` | 通过；`null/null` 是无来源的合法写法 | rules `50`、gift `A10` |

原因一句话：旧实现把来源两键当成「可选、有才写」，K v4 要求的是「**新记录必须显式写两键**，无来源就写 `null/null`」。键在不在，是「这条记录有没有声明过来源」的证据；省略键等于没表态。

## 二、五项要求的落点

### 1. 新 find/gift 记录显式写两个来源键；历史缺键只做读取兼容

- 写入：`rules.ts` 的 `PAYLOAD_KEYS` 里 `find`/`gift` 含 `sourceFindId`、`sourceMode`，键集合**严格相等**——漏一个就是 `MISSING_FIELD`（用例 `42`/`43`），多一个就是 `UNKNOWN_KEY`。
- `provenance.ts::resolveProvenance` 返回值类型是 `{sourceFindId, sourceMode}` 两个非可选字段，调用方无处可省略。
- 读取：新增 `provenance.ts::readProvenance(payload)`，只取值不拒绝，并返回 `legacy`。`legacy=true` 表示「这条记录写下时还没有 K v4 契约」，与「新记录的明确 `null/null`」分开——混成一种，以后统计「多少礼物有出处」会把旧数据算成明确无出处。用例 `46`–`49`。

### 2. 从可信服务端 JOIN 解析来源，核对归属，派生真实档位

`lib/social/sqlite-store.ts::getFindSource`：

```sql
SELECT f.id, t.dog_id, f.source_mode FROM find f JOIN trip t ON t.id = f.trip_id WHERE f.id = ?
```

`find` 表没有 `dog_id`，归属只能经 `trip` 反查——这是唯一可信的算法，不认 URL、不认调用方自报。

`resolveProvenance` 四条判定，顺序有意（先便宜的、后查库）：

1. 无 id 却声称 `sourceMode` → `PROVENANCE_MISMATCH`（凭空造出处）
2. id 不是非空字符串 → `WRONG_TYPE`
3. 查不到 → `PROVENANCE_MISMATCH`（悬空来源）
4. 归属 ≠ 寄件狗 → `PROVENANCE_MISMATCH`；声称档位 ≠ 库里档位 → `PROVENANCE_MISMATCH`

第 4 条选择**拒**而不是「以库为准、静默改掉」：静默纠正会让调用方以为自己传的值生效了，下一个模块照着学就会写出「传 live 也能过」的代码。若 A 认为应改为静默派生，改一行即可，但现在必须是明确拒绝。

### 3. 顺序：解析来源 → 组装最终 payload → 完整校验 → 原子写入

- `gift.ts::send`：`resolveProvenance` → 拼 payload（两键必在）→ `validate`（整体，含键集合/字数/禁词）→ `store.transaction` 写入。
- `meet.ts`：来源核查**下沉到 `recordExchange`**——它是 exchange 的唯一写入口。写在 `meet()` 组装层时，直接调 `recordExchange` 能带假来源穿过（11-19 被用例抓到过一次，不再犯）。
- 只挪 `PENDING_KEYS` 或打开 `INCLUDE_PENDING_KEYS` 的做法已删除：那个开关的本质是「先落库、后补来源」，与 K v4 的「先证明再写」相反。

### 4. greeting/捎话不接收来源；重复请求回原记录；兴趣 NULL 不转空数组

- greeting/捎话的 payload 键集合不含来源：传了就是 `UNKNOWN_KEY`（rules `44`/`45`、gift `A11f`、`sendCoOwnerMessage` 的类型层已删这两个字段）。
- 重复请求：`recordExchange` 在 `changes===0` 时**回查库里的那一行**返回，不返回本次 draft；趟次也取第一次的（gift `B9e`/`B10`、meet `577`）。
- `snapshot.interest_categories` 的 NULL：d 今天不产出 snapshot（11-23 做），此处只承诺——**不把 NULL 归一化成 `[]` 或六类全选**，写 snapshot 时原样保留 NULL。

### 5. 仍按收件狗当前 seq+1；不写三个状态列；不为种子狗造下一趟

- `nextDeliverSeq` = `currentSeq + 1`，`meet` 与 `gift` 共用一个式子（gift `B3` 交叉验证）。
- `delivered_at` / `replied_at` / `read_at` 一律不写（gift `B1`、e2e 收尾表里三列全 NULL）。
- 19 只种子狗 `currentSeq=0`、给它们的东西第一趟就到 —— 这是 c 调度与跨模块呈现的待办，**没有改成即时到达**。口径见 `team/2026-11-19/d/1119-d4-给种子狗捎话-写入侧口径-v1.md`。
