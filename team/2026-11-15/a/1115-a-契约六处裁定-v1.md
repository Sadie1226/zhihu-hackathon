## 二、一条我实测出来的缺陷（要 c 改）

**`reply` 的唯一索引只覆盖了邀请，没覆盖礼物。** c3 的说明里写：

> b2 的「重复点击提交只产生一条回应」，我加了唯一索引 `reply(invitation_id)` 直接兜住，**b 不用自己写去重逻辑**。

我按 `schema.sql` 建了个内存库实测，两条路径结果不一样：

```
✅ 同一邀请提交两次 → UNIQUE constraint failed: reply.invitation_id   （拦住了）
🔴 同一礼物提交两次 → 两条都插进去了，库里出现两条回应                 （没拦）
```

`exchange_id` 上没有唯一索引（`schema.sql:441` 只有 `uniq_reply_invitation`）。

**为什么这是缺陷而不是小事：** b2 第 8 条要的是「重复点击提交 → 只产生一条回应」，它管的是**提交这个动作**，不区分来源。礼物（`exchange_id`）和邀请（`invitation_id`）是同一个提交能力的两个入口 —— 这是我在《给B》第四节拍的口径。现在一个入口有幂等保证、另一个没有，b 照说明写就会在礼物那条路径上漏。

**建议改法**（c 定，我不技术裁决）：

```sql
CREATE UNIQUE INDEX uniq_reply_exchange ON reply(exchange_id)
  WHERE exchange_id IS NOT NULL;
```

影响 b（不用自己写去重了，返回 `CONFLICT` 当成功）和 d（礼物不会被回应两次）。**改完在群里说一声，b 和 d 都要知道。**
